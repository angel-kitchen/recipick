## 1차

### 일반 회원

- **회원 탈퇴** (담당: 정윤 — 결제·환불·포인트·결제수단 연동, 탈퇴 기능: 채빈)
    - 로그인한 회원이 비밀번호를 다시 입력(재인증)해 탈퇴
    - 결제 대기·취소 처리 중인 주문, 정상 진행 중인 배송 미완료 주문, 미해결 결제·환불, 활성 멤버십(해지 예약 포함)·결제 대기 유료 이용권·전환 대기 체험 이용권이 있으면 탈퇴할 수 없으며 먼저 처리하도록 안내
    - 탈퇴 정산 확인은 3차까지 포함해 상품 결제(결과 불명·SYSTEM 환불·수동 확인), 멤버십 결제(구독·갱신·재시도·결과 불명·이용료 환불), 포인트(잔액 사전 안내·미정산 내역·소멸 처리), 자동결제(탈퇴 후 신규 청구 방지·결제수단 처리)를 확인 범위로 함
    - 각 영역의 실제 상태 판정과 정리 방식은 담당자와 합의해 연결하며, 일부 영역만 연결되거나 확인에 실패하면 탈퇴를 허용하지 않음. 장바구니·찜의 정리 계약도 별도로 확정
    - 카드 정리 스위치가 켜져 있으면 탈퇴 Facade는 별도 준비 트랜잭션에서 회원을 첫 DB 작업으로 잠그고 비밀번호·주문·이용권·4 Scope 연결을 확인한 뒤 WithdrawalPaymentMethodPreparer를 호출. 준비 단계는 개인정보·포인트·장바구니를 변경하지 않음
    - 카드 정리 접수는 준비 트랜잭션에서 커밋하고 PG 삭제는 외부 Worker가 트랜잭션 밖에서 수행. 대기·운영 확인이면 Facade가 커밋 뒤 BILLING-030·BILLING-031(409)을 반환하며 완료 후 사용자가 탈퇴를 재요청
    - 준비 결과가 READY일 때만 별도 최종 탈퇴 트랜잭션에서 비밀번호·주문·이용권·4 Scope 정산과 확인 포인트 잔액을 모두 재검사. 이미 완료된 원격 카드 삭제는 최종 탈퇴 거절로 되돌리지 않으므로 화면에서 사전 안내
    - BILLING_KEY_DELETION_ENABLED와 BILLING_KEY_DELETION_WITHDRAWAL_ENABLED는 기본 OFF 유지. 두 값이 모두 켜져야 준비와 AUTO_BILLING 실제 검사가 활성화되며 미연결·비활성 상태에서는 기존 MEMBER-008 차단 유지. 이미 시작된 거래의 후속 처리에는 탈퇴 검사를 추가하지 않음
    - 취소·환불이 완료되어 종료된 주문과 배송 완료 주문은 탈퇴를 제한하지 않음. 다만 관련 미해결 결제·환불이 남아 있으면 탈퇴 불가
    - 탈퇴와 탈퇴 제한 상태를 새로 만드는 작업은 같은 회원 행을 잠가 경합을 제어하며, 탈퇴는 잠금 후 탈퇴 여부·진행 중 주문·미해결 결제·환불·활성 멤버십을 확인
    - 탈퇴하면 로그인·토큰 재발급을 차단하고 모든 기기의 리프레시 토큰을 폐기하며, 기존 액세스 토큰으로 요청해도 회원 인증 시 탈퇴 여부를 확인해 접근을 거절
    - 회원 정보의 이메일·이름·휴대전화는 고유한 대체값으로 바꾸고, 현재 배송지 선택과 이용 마트를 해제한 뒤 배송지를 삭제
    - 주문에 기록된 수령인·연락처·배송 주소와 결제·멤버십 기록은 회원 정보 정리와 별개로 보관하며, 항목별 보존 근거·기간과 만료 후 파기 방식은 별도로 확정
    - 장바구니·찜·포인트·결제수단 등 다른 도메인 데이터의 정리 범위는 해당 담당과 정하며, 탈퇴로 소멸되는 포인트 잔액은 탈퇴 전에 안내
    - 장바구니는 탈퇴 차단 조건이 아니며, 정산 확인을 모두 통과한 뒤 같은 탈퇴 트랜잭션에서 회원의 장바구니 항목을 모두 삭제하고 담기 이력은 유지. 탈퇴가 거절되면 삭제도 함께 롤백
    - 탈퇴 전 실제 사용 가능 포인트를 안내하고, `POST /api/members/me/withdraw`에 `password`와 사용자가 확인한 `acknowledgedPointBalance`(필수, 0 이상의 Long, 잔액이 없으면 0)를 전달
    - 회원 쪽은 확인 잔액을 기본값으로 대체하지 않고 `WithdrawalSettlementChecker.requireSettled(memberId, acknowledgedPointBalance)`에 그대로 전달. POINTS 구현이 회원 잠금 이후 포인트를 잠그고 지연 만료·미정산 확인·실제 잔액 비교·소멸을 수행하며 다른 Scope는 확인 잔액을 사용하지 않아도 됨
    - 잔액만 있으면 탈퇴를 막지 않고 안내한 잔액과 실제 잔액이 같을 때 소멸 처리. 다르면 POINT-002(409)로 거절해 최신 잔액을 재확인하며 예외 시 지연 만료를 포함한 해당 트랜잭션 변경을 모두 롤백. 재안내용 잔액 조회도 유효기간을 반영
    - 포인트의 PENDING 적립·RESERVED 사용은 POINT-003(409)으로 탈퇴 차단. 포인트 잔액과 적립 원장의 합계가 맞지 않는 상태는 회원이 해결할 수 없는 문제라 409가 아닌 내부 오류(COMMON-500)로 차단하고 운영이 확인. CONFIRMED 사용 자체와 완료 이력만으로 차단하지 않으며 잔액이 0이어도 미정산 검사를 수행
    - 포인트 탈퇴 소멸은 자연 만료와 구분해 FORFEITED·WITHDRAWAL_FORFEITED로 기록하고 소멸 금액이 없으면 소멸 이력을 생성하지 않음(포인트 구현: 정윤)
    - 실제로 활성화된 멤버십 이용 이력(관리자 지급 포함, activated_at이 있는 이력)이 있는 회원이 탈퇴하면 휴대전화의 키 해시(HMAC-SHA-256)를 TRIAL_BLOCK에 탈퇴 시각부터 1년간 보관
    - 같은 번호로 재가입하면 가입·유료 구독은 가능하지만 차단 기간 중에는 무료체험을 받을 수 없으며, 만료된 차단 기록은 체험 자격을 제한하지 않음
    - 차단 기간 중 이용 이력 없이 재가입·재탈퇴하면 기존 만료일을 유지하고, 새 계정에 멤버십 이용 이력이 있으면 새 탈퇴 시각부터 1년으로 연장
    - 해시 보관 항목·사유·기간은 탈퇴 화면과 개인정보처리방침에 표시하고, 만료된 기록은 내부 배치가 삭제
    - 회원 쪽 탈퇴 기반을 먼저 준비하되 주문·결제·포인트 등 필요한 연동과 경합 검증이 끝나기 전에는 탈퇴 기능을 제공하지 않음
- **상품 결제** (담당: 정윤)
    - PortOne 카드 결제
    - 주문 생성 트랜잭션에서 `ORDER`와 `PAYMENT(IN_PROGRESS)`를 함께 생성
    - 결제 유효시간은 주문·결제 생성 시점부터 **5분**
    - 서버가 PortOne 결제 상태·주문 식별자·통화(KRW)·결제 금액·결제 완료 시각을 다시 조회해 검증한 뒤에만 결제 확정. 통화·금액 누락은 실패 확정이 아니라 재조회 대상이고, KRW가 아닌 거래는 자동 승인·주문 종료·`SYSTEM` 환불 없이 운영 확인(`PAYMENT-013`, 409)으로 남김. 이미 `PAID`·`CANCELED`인 결제와 PG 실패 확정의 기존 판정은 유지
    - PG 실제 결제 완료시각(`paidAt`)이 결제 만료시각(`expiresAt`) 이내인지 검증
    - 결제 성공 시 `PAYMENT = PAID` , `ORDER = PAID` , 마트 처리 상태를 `RECEIVED(접수중)` 로 같은 트랜잭션에서 반영
    - 웹훅도 동일한 검증·상태 전이 로직으로 처리
    - 결제 확정 API·웹훅·만료 큐가 동시에 들어와도 결제 성공은 한 번만 반영
- **결제 실패·만료** (담당: 정윤)
    - PG가 결제 실패를 명확히 확정하면 `PAYMENT = FAILED(PG_FAILED)` 처리
    - 5분 내 결제가 완료되지 않으면 지연 큐에서 `PAYMENT = FAILED(EXPIRED)` 처리
    - 실패·만료 시 주문을 `CANCELED`로 종료하고 주문 생성 시 차감한 재고 복구
    - 기존 실패 주문·결제를 다시 사용하지 않으며, 다시 결제하려면 **새 주문·새 결제 생성**
    - 기존 결제대기 주문이 있으면 새 주문 생성 불가
    - PG 응답이 불명확하면 실패로 단정하지 않고 기존 결제 상태를 조회해 결과 확인
    - 내부적으로 이미 종료된 결제에서 뒤늦은 PG 성공이 확인되면 주문을 되살리지 않고 시스템 자동 취소
- **결제 전 취소** (담당: 정윤)
    - `PAYMENT = IN_PROGRESS` 상태에서 회원이 결제를 취소할 수 있음
    - 결제 전·후 취소는 동일한 취소 API를 사용하며 `Idempotency-Key` 를 필수로 전달
    - 결제 전 취소는 PG 취소 호출과 `REFUND` 생성을 하지 않음
    - `PAYMENT = FAILED(CANCELED_BEFORE_PAY)` 처리
    - 주문 `CANCELED`, `pending_member_id` 해제
    - 주문 생성 시 차감한 재고 복구
    - 같은 종료 처리가 중복 실행되지 않도록 결제·주문 상태를 기준으로 멱등 처리
- **결제 후 취소** (담당: 정윤)
    - 결제 완료 후 마트 상태가 `RECEIVED(접수중)` 일 때만 회원 직접 전체 취소 가능
    - `PREPARING(배송준비중)` 부터는 회원 직접 취소·환불 불가
    - 부분 취소·부분 환불 없음
    - 취소 시작 시 `PAYMENT/ORDER = CANCEL_REQUESTED`, `REFUND = REQUESTED`를 먼저 저장
    - PortOne 취소 호출은 DB 트랜잭션 밖에서 수행
    - PG 취소 성공 시 `PAYMENT = CANCELED`, `ORDER = REFUNDED`, `REFUND = COMPLETED` 처리 및 재고 복구
    - PG 취소 결과가 불명확하면 `CANCEL_REQUESTED / REQUESTED` 상태를 유지하고 웹훅·재조회로 결과 확인
    - 회원 취소가 명확히 실패하면 결제·주문을 `PAID`, 마트 상태를 `RECEIVED`로 복구
- **환불 처리** (담당: 정윤)
    - PortOne 취소 성공을 확인한 뒤에만 환불 완료 처리
    - 환불 요청 주체 `MEMBER / ADMIN / SYSTEM / EXTERNAL` 기록
    - `Idempotency-Key`로 같은 PG 취소가 중복 실행되지 않도록 처리
    - 동일 환불이 진행 중이면 새 환불 요청을 중복 생성하지 않음
    - 만료·금액 불일치 후 PG 결제 성공이 확인되면 `SYSTEM` 환불 실행. `FAILED` 결제의 늦은 `PAID`도 주문 식별자·KRW·실제 수납액을 확인한 뒤에만 이 경로를 따르며, 환불을 실행할 때도 PortOne 재조회 결과의 통화와 원수납액을 환불 금액과 대조(누락은 재실행, 명확한 불일치는 운영 확인)
    - 만료 시 이미 주문 종료·재고 복구가 완료됐으므로 늦은 승인 자동환불에서는 주문·재고를 다시 변경하지 않음
- **결제 내역 조회** (담당: 정윤)
    - 본인 주문별 결제 금액·결제 방식·결제 일시·결제 상태·실패 사유·취소 여부 조회
    - 결제 도메인은 주문 엔티티를 직접 조회하지 않고 주문 서비스의 소유 확인·조회 계약을 사용
    - 실패·취소된 결제도 이력으로 유지
    - 취소가 발생한 결제는 완료 환불 금액과 최근 환불 상태 표시

### 관리자

- **관리자 감사 로그** (담당: 정윤 — 결제·포인트 조회 및 환불 재처리 기록 연동, 공통 감사 기능: 채빈)
    - 관리자가 수행한 등록·수정·삭제·상태 변경과 개인정보가 보이는 조회를 ADMIN_AUDIT_LOG에 기록
    - 기록 항목은 관리자·작업 종류·대상 종류와 ID·관련 마트·변경 전후 값(details)·접속 IP·기록 시각이며, 목록 조회의 대상 ID와 details는 비워 둘 수 있음
    - 내부 DB 변경은 작업과 감사 기록을 같은 쓰기 가능한 트랜잭션으로 처리하고 기록 실패 시 작업도 롤백
    - 개인정보가 보이는 조회도 조회와 감사 기록을 같은 쓰기 가능한 트랜잭션으로 처리하며, 기록에 실패하면 조회 결과를 반환하지 않음
    - 외부 결제사 호출이 필요한 관리자 작업은 요청 접수 상태와 감사 로그를 먼저 함께 저장·커밋한 뒤 외부 호출을 수행하고 최종 결과는 별도 트랜잭션으로 반영
    - 각 도메인은 global의 공통 기록 인터페이스 AdminAuditRecorder를 호출하고 구현은 회원 도메인이 제공하며, 원래 작업을 조립하는 위치에서 중복 없이 기록
    - details에는 필요한 변경 전후 값만 기록하고 기존 이력 표와 연결하지 않으며, 개인정보·비밀번호·비밀번호 해시·토큰·빌링키·비밀키는 넣지 않음
    - 조회 응답 본문·이메일·이름 검색어와 거절 사유 등 자유 입력 원문은 감사 로그에 복사하지 않음
    - 실제 변경이나 새 실행이 없는 쓰기 재요청은 기록하지 않고 개인정보 조회는 요청마다 기록

## 2차

### 일반 회원

- **포인트 사용** (담당: 정윤)
    - 1포인트 = 1원
    - 1포인트부터 상품금액 전액까지 사용, 배송비에는 사용 불가
    - 만료일이 빠른 적립부터 사용
    - 한 주문에서 여러 적립 건의 포인트를 나누어 사용 가능
    - 주문 생성 시 `POINT_USAGE = RESERVED`
    - 예약 시 `MEMBER_POINT.balance`와 해당 `POINT_EARNING.remaining_amount` 차감
    - 결제 성공 시 `CONFIRMED`
    - 결제 실패·만료·취소 시 `RESTORED`
    - 주문 생성 당시 유효했던 예약 포인트는 5분 결제 대기 중 만료일이 지나도 해당 주문에서는 인정
    - 외부 결제금액이 0원이면 `PAYMENT`는 `payment_method = POINTS_ONLY`, `amount = 0`으로 생성하고 PG는 호출하지 않는다.
- **포인트 적립** (담당: 정윤)
    - 일반·체험 회원 적립률 0.5%
    - 적립액 = `(상품금액 − 사용 포인트) × 0.5%`
    - 배송비 제외, 소수점 이하 버림
    - 주문 생성 시 `POINT_EARNING = PENDING` 으로 적립 예정 건을 생성
    - **배송완료 시** `PENDING -> COMPLETED`로 적립 확정
    - 적립 확정 시 `MEMBER_POINT.balance` 증가
    - 주문당 적립 건 1개
    - 유효기간은 적립 확정일로부터 1년
    - `expires_on` 당일까지 사용 가능
- **취소 시 포인트 복원** (담당: 정윤)
    - 주문에서 사용한 포인트는 사용 당시 차감했던 원래 `POINT_EARNING` 적립 건으로 복원
    - 원래 `expires_on`은 연장하지 않음
    - 복원 시 이미 만료일이 지났다면 `RESTORED` 이력을 남긴 뒤 즉시 `EXPIRED` 처리
    - 이미 만료된 포인트는 `MEMBER_POINT.balance` 에 다시 추가하지 않음
    - 배송완료 전 주문이 종료되면 적립 예정 `POINT_EARNING` 은 `CANCELED`
    - 배송완료가 포인트 적립 확정이자 최종 거래 완료 시점이므로 **적립 완료 후 환불에 따른 포인트 회수(clawback)는 없음**
    - 포인트 전액결제 주문 취소 시 PG 호출 없이 내부적으로 사용 포인트 복원
- **포인트 조회** (담당: 정윤)
    - 회원별 현재 사용 가능 총 포인트 조회
    - 가장 가까운 만료 포인트와 만료일 조회
    - 주문별 적립 예정·적립 완료·사용 예약·사용 확정·복원·만료 이력 조회
    - 적립 건별 최초 적립량·남은 포인트·만료일 조회
    - 포인트 보유 이력이 없는 회원은 404가 아니라 잔액 0·빈 목록 반환

### 관리자

- **마트 주문 거절·자동 환불** (담당: 준희·정윤)
    - 마트 관리자는 본인 마트의 주문이 `PAID` 이고 마트 처리 상태가 `RECEIVED` 일 때만 주문을 거절할 수 있습니다.
    - 거절 요청 시 결제 Facade에서 `PAYMENT = CANCEL_REQUESTED`, `ORDER = CANCEL_REQUESTED`, 마트 처리 상태를 `REJECTED`, `REFUND = REQUESTED`로 먼저 저장합니다.
    - 거절 접수 시점에는 재고와 사용 포인트를 복구하지 않습니다.
    - PortOne 취소는 DB 트랜잭션 밖에서 전액 취소로 실행합니다.
    - PG 취소 성공 시 `PAYMENT = CANCELED`, `ORDER = REFUNDED`, `REFUND = COMPLETED`로 처리하고 최초 차감 재고를 한 번 복구합니다.
    - 사용 포인트가 있는 경우 원래 사용했던 적립 건으로 복원합니다.
    - PG 취소 결과가 불명확하면 `CANCEL_REQUESTED / REQUESTED / REJECTED` 상태를 유지하고 웹훅·재조회로 결과를 확인합니다.
    - PG 취소가 명확히 실패하면 `PAYMENT = PAID`로 복귀하지만 `ORDER = CANCEL_REQUESTED`, 마트 처리 상태 `REJECTED`는 유지하고 관리자 재처리 대상으로 관리합니다.
    - 관리자 재처리 시 새 `Idempotency-Key`와 새 환불 시도를 사용하며, 최종 성공 시 재고·포인트 복원은 한 번만 반영합니다.
- **포인트 조회** (담당: 정윤)
    - `SUPER_ADMIN` 전용
    - 회원별 현재 포인트 잔액 조회
    - 가장 가까운 만료 예정 포인트 확인
    - 회원별 적립·사용·복원·만료 감사 이력 조회
    - 적립 건 ID와 주문 ID를 함께 제공해 적립 lot 단위로 추적

## 3차

### 유료 회원

- **즉시 해지** (담당: 채빈, 환불 처리: 정윤)
    - 유료 멤버십 회원은 이용기간 중 즉시 해지 및 환불을 요청할 수 있습니다.
    - `POST /api/memberships/{membershipId}/terminate`는 회원 도메인이 소유하며 요청 본문 없이 `Idempotency-Key`를 필수로 받습니다.
    - 회원 Facade는 바깥 트랜잭션 없이 결제 `MembershipRefundFacade.requestMemberRefund(memberId, membershipId, idempotencyKey)`를 호출하고 `MembershipRefundResult`를 HTTP 200의 data로 반환합니다. 환불 완료와 이용권 종료는 결제 결과 반영 트랜잭션에서 함께 처리하며 회원 쪽에서 별도로 종료하지 않습니다.
    - 응답은 `refundStatus`(COMPLETED·REQUESTED·FAILED), `membershipTerminated`, `reviewRequired`를 함께 확인합니다. 같은 키 재요청은 새 계산·PG 호출 없이 기존 환불의 현재 결과를 반환합니다.
    - 요청 시 `Idempotency-Key`를 필수로 받고 결제 도메인의 이용료 환불 서비스를 호출합니다.
    - 환불 처리 중에는 멤버십을 `ACTIVE`로 유지합니다.
    - 환불이 `COMPLETED`된 경우에만 멤버십을 즉시 종료합니다.
    - 환불이 명확히 실패하면 멤버십을 `ACTIVE`로 유지합니다.
    - 환불 결과가 불명확하면 `REQUESTED` 상태와 멤버십 `ACTIVE`를 유지하고 웹훅·재조회로 결과를 확인합니다.
    - 결과 불명 건이 나중에 환불 성공으로 확인되면 `즉시 해지 환불 완료 반영`을 통해 멤버십을 종료합니다.
    - 같은 `Idempotency-Key`로 다시 요청하면 새 환불을 만들지 않고 기존 결과를 반환합니다.
    - 같은 이용권에 결과 확인 중인 `REQUESTED` 환불이 있으면 다른 키의 새 요청은 거절합니다.
    - 명확한 실패가 `FAILED`로 확정된 뒤에는 새 `Idempotency-Key`로 다시 요청할 수 있습니다.
- **자동 결제 동의** (담당: 정윤 안내, 채빈 저장)
    - 체험·유료 구독 시작 전 결제 금액·첫 결제일·월 갱신 주기·자동갱신 해지·즉시 해지 방법 안내
    - 동의 금액·동의 문구 버전·동의 일시를 멤버십에 저장
    - 자동 청구 시 멤버십 도메인에 자동청구 대상·동의 여부 확인
- **카드 등록** (담당: 정윤)
    - 카드번호·CVC는 저장하지 않고 PortOne 빌링키만 관리
    - 빌링키 원문은 AES-256-GCM 암호문(`portone_billing_key_ciphertext`, `v1:<IV>:<암호문+태그>`)과 HMAC-SHA256 지문(`portone_billing_key_hash`, UNIQUE·같은 키 조회)으로만 저장. 암호화 키·지문 키는 환경변수(`BILLING_KEY_ENCRYPTION_SECRET`·`BILLING_KEY_HMAC_SECRET`)로 분리하고 로컬은 자동 생성. 기존 평문 행은 기동 백필(재실행·동시 실행 안전, 미완료 시 기동 실패)로 채우고 평문 컬럼 제거는 별도 승인. 암호문·지문은 로그·`toString`·응답에 넣지 않음
    - 회원당 `ACTIVE` BillingKey 최대 1개
    - 새 카드 등록 시 기존 ACTIVE 키는 `REPLACED`, 새 키는 `ACTIVE`
    - 동일 ACTIVE BillingKey 재등록은 새 행을 만들지 않고 기존 결과 반환
    - 자동결제 customer 개인정보(name/email/phone)는 BillingKey에 중복 저장하지 않음
    - 실제 자동결제 시 MemberService의 결제용 회원정보 조회를 통해 원문을 받아 Customer DTO 구성
- **결제수단 정리·탈퇴 정산** (담당: 정윤, 탈퇴 API 연결: 채빈)
    - `REPLACED`·`REVOKED` 빌링키는 그 키를 쓰는 미해결 시도(READY·DISPATCHING·UNKNOWN·MANUAL_REVIEW)와 회차 강한 차단이 없을 때만 PortOne에서 원격 삭제. `REVOKED`는 청구 불가 표시일 뿐 원격 삭제 확인과 같지 않음. 일반 카드 삭제 API는 추가하지 않음
    - 삭제 접수는 회원 정산 잠금 → 빌링키 PK 잠금 뒤 상태를 재검사하고, 키를 `DELETE_REQUESTED`로 바꾸며 삭제 요청(`BILLING_KEY_DELETION`, 키당 1건 UNIQUE)을 같은 트랜잭션에 저장. 요청 시각·상점·사유는 재접수로 바뀌지 않음. 잠금 순서 MEMBER → BILLING_KEY(PK 오름차순) → BILLING_KEY_DELETION
    - 실행은 실행권(토큰 증가 + 임대 5분) 획득 커밋 → PortOne 조회(같은 키·같은 상점 확인) → 삭제 직전 재검증 커밋 → DELETE → 재조회 → 결과 반영. DELETE 응답만으로 완료하지 않고 조회로 `DELETED`를 확인해야 로컬 키 `DELETED`(행은 지우지 않고 결제 시도 FK·이력 보존)
    - 첫 조회가 404뿐이면 상점 근거 없이 완료로 추정하지 않고 운영 확인(`SCOPE_UNPROVEN`). 키·상점 식별 불일치, 실연동 채널, 401·403, 400은 자동 DELETE 중단·운영 확인이며 접수 후 24시간이 지나면 DELETE를 멈춤. 운영 확인 상태도 1시간 간격 조회는 계속해 콘솔 삭제를 정합화. 강제 완료·표시 해제 API 없음
    - 복구는 DB 기준(Redis 큐 사용 안 함): 5분마다 교체·폐기 키 후보를 ID 상한 고정 keyset으로 접수, 1분마다 기한이 된 요청을 최대 20건 실행. 다음 확인 간격은 1·2·4·8분 뒤 10분
    - 회원 탈퇴 정산 `AUTO_BILLING` 영역: 회원의 모든 빌링키가 삭제 확인(`DELETED` + 확인 시각)이고 운영 확인 중인 삭제 요청·멤버십 미정산(C-17)이 없어야 통과. 탈퇴 준비 단계(회원 잠금 TX)는 활성 키를 포함한 회원의 키 전부를 정리 접수만 하고 커밋하며, 처리 중이면 `BILLING-030`, 운영 확인이면 `BILLING-031`로 응답(접수는 유지). 회원은 정리 뒤 탈퇴를 다시 요청하며 자동 탈퇴·원격 키 복구는 없음
    - 기능 스위치 `payment.billing-key-deletion.enabled`(정리 접수·실행)·`withdrawal-enabled`(AUTO_BILLING 영역 제공·탈퇴 준비)는 운영 기본 false. 둘 다 true일 때만 AUTO_BILLING을 지원한다고 선언하며 꺼져 있으면 탈퇴는 기존대로 `MEMBER-008`. 신규 자동청구 플래그와 별개
    - 로그·저장은 내부 ID와 고정 코드만 사용하고 빌링키·API Secret·PG 응답 원문은 남기지 않음
- **멤버십 결제** (담당: 정윤)
    - 월 이용료 3,900원
    - 체험 종료 또는 일반회원의 유료 구독 시작 시 첫 자동 결제
    - 이후 첫 유료 결제일을 기준으로 매월 같은 날짜에 자동청구
    - 해당 날짜가 없는 달은 말일 청구
    - 청구 대상은 멤버십 서비스에서 조회
    - 동일 이용권의 같은 이용기간 회차 결제는 한 번만 생성
    - `UNIQUE(membership_id, period_start_date)`로 회차 중복 생성 방지
    - PortOne 자동결제 성공 후 멤버십 도메인에 결과 반영
- **첫 유료 결제 실패** (담당: 정윤)
    - 체험 종료 후 첫 결제가 명확히 실패하면 `FAILED` 결과 전달
    - 멤버십 도메인은 유료 전환하지 않고 일반 회원으로 전환
    - PG 결과가 불명확하면 즉시 실패로 단정하지 않고 `UNKNOWN` 상태로 조회해 결과 확정
- **갱신 결제 실패** (담당: 정윤)
    - 기존 유료 멤버십 갱신 실패 시 3일 유예
    - 갱신일에 1회, 이후 하루 1회씩 2회 추가해 총 3회 시도
    - 재시도 대기 상태는 `RETRY_WAITING`
    - 결과 불명(`UNKNOWN`)은 새 결제 시도보다 기존 PG 결과 조회를 우선
    - 최종 실패 시 멤버십 도메인에 최종 실패 결과 전달
    - 갱신 회차의 결제 마감은 직전 이용 종료 시각 + 3일이며 생성 때 저장해 바꾸지 않음. 다음 청구는 명확한 실패 확정 시각 + 24시간이고, 3회는 PG에 실제로 발송된 시도 수 기준(미발송 취소·되돌림은 제외). 같은 실패를 다시 받아도 재시도 시각을 다시 세지 않음
    - 마감이 지나거나 발송 3회를 쓰거나 해지 예약·종료된 회차는 회차 FAILED와 함께 자동갱신만 중단하고 유예 종료 시각·이용 종료 시각은 줄이지 않음. 결과 불명·운영 확인 시도가 남아 있으면 마감이 지나도 회차를 실패로 확정하지 않음
    - 마감 뒤에 확인된 결제 성공, 결제기간이 이미 끝난 성공, 금액 불일치는 이용기간을 연장하지 않고 SYSTEM 환불 요청으로 기록. PG 결제 시각이 회차 시작 전이거나 서버 시각보다 미래면 자동 연장·환불 없이 운영 확인
    - 신규 청구 기능 플래그가 꺼져 있어도 이미 생긴 갱신 회차의 마감·해지 정리와 시도 재조회는 계속 수행하고, 새 접수·재시도·카드 대기 재개·PG 호출만 멈춤
    - 결과 불명은 발송 시각 + 24시간까지 같은 결제 ID로 재조회하고, 지나면 운영 확인으로 넘기되 그 뒤 도착한 웹훅·운영자 재조회 결과는 저장된 결제 마감 기준으로 반영
    - 결제 마감까지 갱신 접수가 한 번도 없던 이용권은 실패 회차 1건으로 닫고 자동갱신만 중단(소급 청구 없음)
    - 실패로 확정한 발송 시도에 늦게 수납이 확인되면 이용기간을 연장하지 않고 수납을 정정해 실제 수납액을 SYSTEM 환불 요청. PG에 보낸 적 없는 시도의 결제 ID로 PG 거래가 확인되거나 저장된 수납 근거와 PG가 다르면 자동 청구·반영·정산 해제를 멈추고 운영 확인
    - 탈퇴한 회원의 이미 시작된 결제도 결과 확인·환불 요청은 진행하되 연장·새 청구는 하지 않음. 다른 이용권과 겹치는 갱신 수납은 연장하지 않고 환불 요청
    - PortOne이 카드 키 삭제·없음을 명확히 답할 때만 그 키를 사용 불가로 바꾸고, 조회 장애·권한 오류는 키 상태를 바꾸지 않음
- **갱신 시 카드 없음** (담당: 정윤)
    - 갱신일에 활성 BillingKey가 없으면 `PAYMENT_METHOD_REQUIRED` 3일간 카드 등록 대기
    - 유예기간 내 카드 등록 시 한 번 청구
    - 기간 종료까지 카드가 없으면 최종 실패 결과 전달
    - 카드 등록 API는 등록 트랜잭션이 커밋된 뒤 그 회원의 카드 대기 회차만 같은 회차에서 재개하며, 재개가 실패해도 등록 응답은 성공. 신호가 유실되면 갱신 스케줄러의 주기 조회가 같은 회차를 재개
    - 실패 뒤 카드를 바꿔도 24시간 재시도 간격은 앞당기지 않고, 이미 접수된 시도는 접수 때 카드로 실행하며 새 시도부터 새 카드 사용
- **이용료 환불** (담당: 정윤)
    - 유료 멤버십 즉시 해지 요청의 내부 처리로 실행
    - 회원이 멤버십 결제 환불 API를 직접 호출하지 않음
    - 멤버십은 환불 결과가 확정될 때까지 `ACTIVE` 유지
    - 환불액 = `max(0, 결제금액 - 이용일수 요금 - 위약금)`
    - 이용일수 요금 = `floor(결제금액 x 이용일수 / 해당 결제기간 실제 일수)`
    - 위약금 = 결제금액의 20%
    - 이용일수는 이용 시작일과 환불 요청일을 모두 포함
    - 이용일수·이용일수 요금·위약금·환불금액을 `MEMBERSHIP_REFUND`에 저장
    - 환불 요청 시 `MEMBERSHIP_REFUND = REQUESTED`를 먼저 저장·커밋한 뒤 PortOne 환불 호출
    - 환불 성공 시 `COMPLETED` 처리 후 멤버십 종료
    - 명확한 실패 시 `FAILED`, 멤버십 `ACTIVE` 유지, 새 요청 가능
    - 결과 불명 시 `REQUESTED` 유지, 멤버십 `ACTIVE` 유지 후 웹훅·재조회로 확인
    - 결과 불명 건이 나중에 성공으로 확인되면 `COMPLETED` 처리 후 멤버십의 즉시 해지 환불 완료 반영 호출
    - 환불액이 0원이면 PG 호출 없이 `COMPLETED` 처리 후 멤버십 종료
    - 동일 요청은 `Idempotency-Key`로 중복 환불 방지
    - 결제기간은 시작 시각부터 다음 결제기간 시작 시각 전까지이며 일수에 종료일을 더하지 않음(1/31 10:03 → 2/28 10:03은 28일). 이용일수는 결제기간 일수를 넘지 않음
    - 접수 판정 시각은 회원·이용권·회차·시도 잠금을 모두 잡은 뒤 읽음. 환불 대상은 정상 반영된 PAID 회차 중 기간이 가장 늦고 종료 시각이 이용권 현재 종료와 같은 회차의, 정상 반영 PAID 시도 정확히 하나. 아니면 `BILLING-022`로 거절하고 시도에 `REFUND_TARGET_PERIOD_MISMATCH` 차단 표시
    - 환불 행마다 PG 멱등 키를 생성 때 정하고, 상점 ID·요청 사유는 최초 실행권 확보 때 한 번 고정(설정이 바뀌어도 덮어쓰지 않음). PG 취소는 금액 지정 취소이며 같은 행의 키·본문은 바뀌지 않음
    - 같은 키 재POST는 최초 발송 + 2시간 55분 미만에서만, 자동 결과 확인은 24시간(기준: 최초 발송 시각, 없으면 접수 시각)까지. 그 뒤에는 `REQUESTED` 유지 + 운영 확인(`UNKNOWN_WINDOW_EXPIRED`)
    - 실행권은 예약된 다음 확인 시각 전에는 잡지 않고(접수 직후 큐와 동기 실행이 겹쳐도 조회·재요청 1회), PG 취소 요청 직전에 회차 차단·재요청 창을 다시 확인. 예약·자동 중단·임대 해제는 실행 토큰이 같고 임대가 유효할 때만 반영
    - PG 취소 내역은 저장된 취소 ID 정확 일치 → 없을 때만 서버 생성 사유 정확 일치(API 취소) 순서로만 연결하며 금액·시각으로 연결하지 않음. 결제 식별(결제 ID·상점·KRW·원수납액)과 누적 취소액(SUCCEEDED 합)을 함께 검증하고, 일시적 불일치는 재조회·명백한 모순은 환불·시도에 강한 차단(`EVIDENCE_CONFLICT`·`REFUND_EVIDENCE_CONFLICT`)
    - 결과 확정은 PortOne 조회 결과로만 하며 취소 요청 응답은 취소 ID 기록 근거로만 사용. 확정 반영은 실행 토큰이 아니라 잠금 순서·현재 상태·증거로 보호해 웹훅·관리자 재조회도 검증된 성공을 반영할 수 있음
    - 수납 PAID 시도에 PortOne 취소 계열 상태가 관측되면 결제 상태를 바꾸지 않고 환불 정합화로 처리(수납 불신뢰로 보내지 않음). 환불 요청이 없는 시도의 취소 웹훅은 외부 취소로 운영 확인
    - 결제 웹훅은 환불 정합화 결과대로 기록: 완료·실패 확정은 처리 완료, 미확정은 재시도 대기, 환불 요청이 없는 취소 관측·환불 운영 확인은 운영 확인(환불이 확인되지 않은 웹훅을 처리 완료로 기록하지 않음). 여러 환불은 운영 확인 > 미확정 > 완료 > 실패 순으로 집계
    - 반영하지 않은 수납의 SYSTEM 환불은 같은 실행기로 실제 수납액을 ADMIN 요청 주체로 취소하며 이용권을 바꾸지 않음. 명확히 실패한 SYSTEM 환불은 관리자가 후속 환불 1건으로 재실행(같은 실패 행에 반복 요청 시 기존 후속 행)
    - 복구 스캔(1분)이 다음 확인 시각이 지난 `REQUESTED` 환불을 실행하고, 환불 실행 기능 전에 운영 확인으로 보존된 취소 웹훅은 재처리 대기로 되돌림
- **적립률 차등** (담당: 정윤)
    - 유료 멤버십 1%, 체험 0.5%(일반 회원 0.5%)
    - 적립률은 **주문 생성 시점의 회원 상태**로 결정해 주문에 스냅샷
    - 주문 조립 단계에서 동일 기준시각을 정해 MembershipService.getTypeAt(memberId, 기준시각)으로 혜택 유형을 조회하고 포인트 정책에 전달. 결제 전 이용권은 제외하고 갱신 유예 중에는 혜택을 유지하는 기준을 3차 이용권 생명주기에 반영
    - getTypeAt은 activated_at이 없는 결제 대기를 제외하고 활성화 시각부터 유예 종료 시각까지 혜택 유형을 반환. 결제 결과 반영은 MembershipBillingService 계약으로 제공. 주문 생성 시 동일 기준시각의 getTypeAt 조회 결과로 포인트 적립률과 멤버십 배송비 혜택을 함께 판정하며, 결정된 적립률은 주문에 저장
    - 실제 포인트 지급은 배송완료 시점
    - 이후 회원 멤버십 상태가 바뀌어도 해당 주문의 적립률은 변경하지 않음

### 관리자

- **멤버십 환불 운영** (담당: 정윤)
    - `POST /api/admin/membership-refunds/{refundId}/recheck`: 감사 기록 커밋 → PortOne 조회 1회 → 검증된 결과 반영(강한 차단 행은 관측만) → 저장 상태와 이번 관측값을 분리해 응답
    - `POST /api/admin/membership-refunds/{refundId}/retry`: FAILED SYSTEM 환불의 후속 환불 접수(같은 시도에 진행·완료 환불 없음, 금액 동일)와 재실행 감사 기록을 같은 트랜잭션으로 커밋 → 실행. 새 후속 환불이 생길 때만 감사하며 기존 후속 환불 반환·거절은 감사하지 않음. 조건 불충족은 `BILLING-021`
    - 운영자는 금액·결제 ID·취소 ID를 입력하지 않으며 표시 해제·강제 완료는 없음. 결제 시도 상세는 기존 `systemRefunds`와 함께 MEMBER·SYSTEM 전체 환불 이력(`refunds`)을 제공
    - 감사 저장 실패 시 PortOne 호출 없음(재실행은 후속 환불 생성까지 롤백). SUPER_ADMIN 전용
- **멤버십 결제 조회** (담당: 정윤)
    - `SUPER_ADMIN` 전용
    - 첫 결제·월 정기결제·실패·재시도·결제수단 필요·결과 불명 상태 조회
    - 청구일·이용기간·시도 횟수·다음 재시도 시각·실패 사유 확인
    - 결제별 전체 `MEMBERSHIP_REFUND` 실행 이력 확인
    - 환불 금액·이용일수·이용요금·위약금·처리상태·실패사유 확인
    - 결제 시도별 운영 확인·정합성 차단 여부 확인, 같은 결제 ID로 PortOne 상태 재조회(조회·재조회 모두 감사 기록, 결제 ID·금액·상태 입력 없음, 차단 해제·강제 확정 없음)
