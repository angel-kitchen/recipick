## 최종 Before/After 요약 (상품 검색, 100명 구간)

같은 시나리오(`scripts/perf/k6/product-search.js`)를 단계마다 3회 재고 전체 p95의 **중앙값**을 적었습니다. 모든 단계에서 실패율은 0%입니다. 10월 측정과 11/05 재측정은 코드·실행 방식·PC 상태가 달라 서로 직접 비교하지 않고, 각각 같은 측정 안의 단계 변화로 읽습니다.

| 단계 | p95 (10월 측정) | p95 (11/05 재측정, 최신 dev) | 풀 대기 최대 (10월 / 11/05) |
| --- | --- | --- | --- |
| Before (인덱스 X·캐시 X) | 2.66s | 1.87s | 69 / 62 |
| 인덱스 후 | 264ms | 492ms | 23 / 23 |
| 캐시 후 | 19.8ms | 45.7ms | 0 / 0 |

- 11/05 재측정은 인덱스를 제거한 Before부터 같은 날 이어서 쟀고, 10월 Before는 [부하 테스트](product/load-test.md)의 2회차입니다. 이번에 After가 10월보다 느리게 나온 원인은 확정하지 않았습니다(그 사이 백엔드 변경, 실행 방식, 같은 PC에서 켜 둔 프로그램 등). 필터 검색은 판매가 식(#494)이 가격 인덱스를 못 쓰는 것이 원인 후보이며, 단독 `EXPLAIN` 결과는 [병목 개선 5-1절](product/bottleneck.md)에 있고 `scripts/perf/explain-product-search.sql`로 재현합니다.
- 처리량은 10월 26.9 → 42.5 → 46.3요청/초, 11/05 27.1 → 39.6 → 45.7요청/초입니다. 요청 사이 1초 대기(think time) 때문에 응답이 빨라져도 요청 수가 크게 늘지 않아, 효과는 응답 시간과 풀 대기에서 잘 보입니다.
- 요청 수 제한은 악성 IP 1개를 섞은 별도 시나리오라 위 표와 합치지 않습니다. 일반 회원 p95 1,343ms → 791ms, DB 풀 평균 대기 27.4 → 2.0건입니다([요청 수 제한](product/rate-limit.md)).
- 모두 로컬 단일 PC 측정입니다. 서버(AWS) 환경에서는 다시 측정해야 합니다.

## 기술 선택 근거 요약

| 주제 | 선택 | 선택하지 않은 것 | 핵심 이유 | 상세 |
| --- | --- | --- | --- | --- |
| 부하 도구 | k6 | JMeter, Gatling | 시나리오가 JS 한 파일이라 리뷰하기 쉽고, 단계별 부하·API별 결과·합격선 지정이 쉽다. Docker 이미지로 설치 없이 같은 명령으로 재현한다 | [부하 테스트](product/load-test.md) |
| 검색 병목 | 복합 인덱스 3개(필터 2개, 최신순 1개) | 풀 크기 증가, 풀텍스트(ngram) | 병목이 연결 부족이 아니라 쿼리 하나가 연결을 오래 쥐는 것이었다. 풀텍스트는 JPA가 `MATCH ... AGAINST`를 지원하지 않아 쿼리 코드 변경이 크다 | [병목 개선](product/bottleneck.md) |
| 조회 캐시 | Redis(Spring Cache) | Caffeine(앱 메모리), 캐시 없음 | 이미 쓰는 인프라이고 서버가 여러 대여도 캐시와 무효화를 공유한다. 왕복 약 1ms는 쿼리 70~100ms에 비해 작다 | [조회 캐시](product/caching.md) |
| 요청 수 제한 | 직접 구현(필터 + Redis 카운터) | Bucket4j 등 라이브러리 | 새 의존성이 없고 로그인 잠금의 카운터 구조를 그대로 쓴다. IP별 분당 N회 규모에는 라이브러리가 과하다 | [요청 수 제한](product/rate-limit.md) |
| 모니터링 | Prometheus + Grafana(대시보드를 파일로 관리) | Actuator JSON 직접 확인, 클라우드 모니터링 | 로컬에서 같은 구성으로 재현할 수 있고 p95·p99 비교가 된다 | [모니터링](../monitoring.md) |

읽는 순서는 위 표(보고서 목록) 순서를 권장합니다. 앞 보고서의 수치가 뒤 보고서의 Before 기준이 됩니다.

관련 문서: [모니터링](../monitoring.md)(측정 지표·관리 포트), [동시성](../concurrency.md), [문서 목차](../README.md).

## 로컬 혼합 흐름 검증 (담당: 채빈)

[최대 100명 혼합 부하 결과](local-100-users.md)는 상품·레시피·회원·장바구니·주문 흐름과 종료 정합성을 검증한 별도 측정입니다. 상품 검색 Before/After와 직접 비교하지 않습니다. Grafana 캡처와 측정 요약도 해당 문서에 연결합니다.
