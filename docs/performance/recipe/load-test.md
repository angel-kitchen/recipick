## 2. 시나리오와 재현 방법

- 대상 API: `GET /api/recipes?keyword=…&size=20`(50%, 검색어 김치·된장·닭·두부·파스타), `GET /api/recipes/{id}?servings=2`(30%, 이 중 30%는 인기 레시피 10개에 집중), `GET /api/recipes/suggestions?keyword=…`(20%, 김·ㄱㅊ·된장·닭·파스). 인증은 setup에서 CSRF 토큰을 받아 100명 로그인 후 Bearer 토큰을 재사용한다.
- 동시 사용자: 10 → 30 → 60 → 100명(단계마다 증가 30초·유지 1분, 감소 20초), 약 6분 20초. 요청마다 1초 대기라 100명은 초당 100요청이 아니다.
- 반복: 단계마다 3회, 회차 사이 20초. 표의 대표값은 **3회 p95의 중앙값**이다.
- 워밍업: Before는 1명 점검 후, ① After는 앱 재시작 약 15초 뒤 바로(워밍업 없음), ② After는 재시작 후 1명 점검·20초 대기 뒤 측정했다.
- 동일 조건: 같은 PC·DB·데이터·스크립트, 모니터링 켠 상태. 단, 상세 조회가 `view_count`를 올리므로 회차가 지날수록 조회수 값은 달라진다(정렬 결과에만 영향).
- 실행 명령(레포 루트):
  ```bash
  k6 run -e BASE_URL=http://localhost:28080 scripts/perf/k6/recipe-search.js
  ```
  1명 점검은 `-e SMOKE=1`. 스크립트: [`recipe-search.js`](../../../scripts/perf/k6/recipe-search.js)
- 원본 결과: 로컬 `scripts/perf/results/recipe-{before,after-suggest,after-index}-{1..3}/`(gitignore). 서버 지표는 Prometheus·Grafana(Recipick 개요)에서 회차 시간대로 조회했다.

## 3. 병목과 변경

### 관찰 (Before)

사용자가 적을 때는 빠르지만(응답 중앙값 106ms) 100명에 가까워지면 p95가 1.5초를 넘었다. DB 연결 10개가 모두 사용 중이었고 연결 대기가 최대 55~73건이었다. 앱 CPU는 30% 아래였다.

| 확인 | 결과 |
| --- | --- |
| 부하 없이 1건 | 상세 10~13ms, 목록 69~90ms, 자동완성 캐시 적중 7ms, **자동완성 캐시 없음 620~900ms** |
| 3회차 7분 서버 지표 | **GC 정지 합계 약 16.5초**(대형 객체 할당 GC 2.9초 포함), DB 연결 1회 점유 최대 **4.7초**(평균 0.07초), 힙 최대 762MB |

### 예상 병목별 판정

| 예상 병목 | 판정 | 근거 |
| --- | --- | --- |
| ① 목록 `LIKE '%검색어%'` 풀스캔·정렬·count | 확인 | 아래 EXPLAIN. 목록 73ms + count 27ms |
| ② 목록이 steps JSON까지 조회 | 부분 확인 | `SELECT r.*`가 맞지만 ①·④보다 영향이 작아 조치하지 않음 |
| ③ 상세 `view_count` UPDATE 행 락 경합 | **기각** | 인기 10개 집중에도 락 대기 23회·최대 33ms(MySQL 서버 누적값이라 상한), 조회수 실패 로그 0건. 조회수를 짧은 별도 트랜잭션으로 둔 기존 설계로 충분 |
| ④ 자동완성이 활성 레시피 전체 로드 | **주원인** | 활성 47,600건을 steps(평균 712바이트)까지 앱 메모리로 읽고 자바에서 걸렀다. 캐시가 빌 때마다 연결과 힙을 오래 잡고, GC 정지는 모든 API를 함께 멈춘다 |

목록 EXPLAIN ANALYZE(검색어 "김치", Before):

```text
-> Limit: 20 row(s)  (actual time=73.1..73.1 rows=20)
    -> Sort: r.name, r.id, limit input to 20 row(s) per chunk  (actual time=73.1..73.1 rows=20)
        -> Filter: (status = 'ACTIVE') and (replace(name,' ','') like '%김치%')  (actual time=2.53..64.2 rows=3948)
            -> Table scan on r  (actual time=0.0735..40.3 rows=50100)
```

### 변경

1. **자동완성을 DB에서 걸러 8건만 조회**: 상품 자동완성과 같은 방식으로, 띄어쓰기를 지운 이름(초성 검색이면 초성 컬럼)에 검색어가 들어간 활성 레시피를 `앞글자 일치 → 조회수 많은 순 → 이름 → ID` 순으로 8건만 가져온다. 정렬 규칙은 기존과 같다.
2. **목록 인덱스 `idx_recipe_status_name (status, name, id)`**: `'%검색어%'`는 인덱스로 거를 수 없지만, 이름순 인덱스를 따라 읽으면 정렬 없이 20건이 차는 즉시 멈춘다. count는 테이블 대신 크기가 작은 인덱스만 읽는다.

목록 EXPLAIN ANALYZE(인덱스 후):

```text
-> Limit: 20 row(s)  (actual time=0.923..2.05 rows=20)
    -> Index lookup on r using idx_recipe_status_name (status='ACTIVE'),
       with index condition: (replace(name,' ','') like '%김치%')  (actual time=0.92..2.05 rows=20)
```

| 쿼리 1건 | Before | 인덱스 후 |
| --- | --- | --- |
| 목록 "김치" 1페이지 | 73ms | 2ms |
| 목록 "파스타" 3페이지 | — | 17ms |
| 결과 없는 검색어 | — | 34ms(끝까지 읽지만 정렬 없음) |
| count(검색어 5개 × 3회 평균) | 41ms | 28ms |

자동완성 캐시 없음 1건은 620~900ms → 67~206ms가 됐다(부하 없음, 재시작 직후 포함).

## 4. Before / After

동시 사용자 100명까지의 전체 구간, 3회 중앙값.

| API p95 | Before | ① 자동완성 | ② + 목록 인덱스 | 변화(Before 대비) |
| --- | --- | --- | --- | --- |
| 목록 검색 | 1,512ms | 297ms | **95ms** | -94% |
| 상세 | 1,574ms | 199ms | **62ms** | -96% |
| 자동완성 | 1,739ms | 82ms | **46ms** | -97% |
| **전체** | **1,557ms** | **248ms** | **79ms** | **-95%** |

| 지표 | Before | ① 자동완성 | ② + 목록 인덱스 |
| --- | --- | --- | --- |
| 전체 p50 / p95 / p99(ms) | 106 / 1,557 / 3,413 | 72 / 248 / 913 | 26 / 79 / 406 |
| 회차별 전체 p95(ms) | 1,481 / 1,557 / 1,934 | 504 / 248 / 192 | 79 / 61 / 90 |
| 처리량(req/s, 중앙값) | 33.5 | 41.4 | 43.4 |
| 실패 / 시나리오 요청 | 0 / 38,400 | 0 / 47,732 | 0 / 50,471 |
| GC 정지 합계(7분) | 약 16.5초(3회차) | 0.25~0.51초 | 0.24~0.41초 |
| DB 연결 1회 점유 최대 | 4.7초(3회차) | 0.8~2.8초 | 0.5~1.1초 |
| DB 연결 대기 최대 | 61 / 55 / 73 | 47 / 44 / 12 | 27 / 8 / 83 |
| 앱 CPU 최대 | 26~29% | 11~12% | 11~13% |

변화율은 `(After − Before) / Before`, p95 중앙값 기준이다. 실패 요청 수는 setup(로그인)을 뺀 시나리오 요청만 센다.

- ①만으로 세 API가 모두 빨라졌다. 자동완성의 대량 로드가 만들던 GC 정지와 긴 연결 점유가 사라지자, 쿼리 자체는 10ms대인 상세도 p95가 1,574 → 199ms로 줄었다.
- ②는 남은 목록 정렬 비용을 없애 목록 응답 중앙값을 91 → 33ms로 줄였다.
- ①의 회차별 편차(504 → 192ms)는 재시작 직후 워밍업 영향이 섞였을 가능성이 있어, ②에서는 워밍업 후 측정했다.

## 5. 정합성·실패 처리 확인

- 목록: 검색어 5개 × 오프셋 0·40·2,000에서 인덱스 사용·미사용 쿼리의 결과 ID 20건과 전체 건수가 모두 같았다.
- 자동완성: 검색어 10개(글자 7·초성 3)에서 기존 자바 정렬 결과와 새 SQL의 8건 ID가 모두 같았다. 동률 정렬은 기존 자바 문자열 비교에서 DB 정렬 규칙(`name`, `id`)으로 바뀌어, 이름·조회수가 모두 같은 경우 순서가 다를 수 있다.
- 테스트: 정렬 순서·초성·8건 제한과 대소문자·비활성 제외를 실제 DB로 확인하는 `RecipeSuggestionRepositoryTest`를 추가했다. 서비스 단위 테스트는 검색어 정리(띄어쓰기 제거·소문자)만 확인하도록 바꿨다.
- 응답 검증: 모든 측정에서 k6 확인 항목(상태 200, 목록 20건, 상세 ID 일치) 실패는 0건이다.
- 추가 비용: 인덱스 1개만큼 레시피 쓰기와 저장 공간이 늘어난다. 레시피 쓰기는 관리자 등록·수정뿐이라 영향이 작다. 운영 DB에는 배포 시 `ddl-auto: update`가 인덱스를 만든다.
- 하지 않은 것: 자동완성 캐시 `sync = true`는 Spring Data Redis 3.5에서 동시 로드를 실제로 막는지 확인하지 못해 적용하지 않았다. 캐시가 빌 때의 비용 자체를 줄이는 쪽만 택했다.

## 6. 결론과 한계

- 목표 달성: 동시 사용자 100명에서 목록·상세·자동완성 p95가 모두 100ms 아래, 실패 0건, 결과 동일.
- 남은 병목: 목록 count는 `'%검색어%'` 특성상 여전히 전체(인덱스)를 훑는다. 풀텍스트(ngram) 인덱스는 JPA가 `MATCH ... AGAINST`를 지원하지 않아 쿼리 변경이 커서 이번에는 쓰지 않았다(상품과 같은 판단).
- 간헐적 꼬리 지연: ② 3회차에 DB 연결 대기가 순간 83건, p99가 1.14초였다. p95는 90ms로 안정적이며, 원인(같은 PC의 다른 작업, 자동완성 캐시 만료 겹침 등)은 확인하지 않았다.
- Before는 회차가 지날수록 느려졌다(1,481 → 1,934ms). 원인은 확인하지 않았고, 그래서 중앙값을 대표값으로 쓴다.
- 모두 로컬 단일 PC 측정이며 앱·DB·부하 도구가 자원을 공유한다. 수치보다 같은 조건의 Before/After 변화가 근거이며, 서버(AWS) 환경에서는 다시 측정해야 한다.
- 범위 밖: 레시피 쓰기·AI 추천·북마크·인기 순위 API, 로그인 부하.
