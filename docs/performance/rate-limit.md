# 요청 수 제한 (429 Too Many Requests)

한 클라이언트가 짧은 시간에 요청을 몰아 보내 서버 자원(DB 연결, BCrypt 연산)을 독점하지 못하게 요청 수 제한을 도입한 과정과 결과를 기록한다.

## 1. 상황

- 요청 수를 제한하는 장치가 없었다. 한 IP가 로그인·검색 API를 반복 호출하면 DB 커넥션 풀(HikariCP)과 BCrypt 연산을 독점할 수 있다.
- 부하 테스트에서 풀(최대 10)이 가득 차고 대기가 최대 69까지 쌓이는 것을 확인했다(`load-test.md`). 한 사용자가 몰아치면 다른 사용자도 같은 줄에서 기다리게 된다.
- 로그인 실패 횟수로 계정을 잠그는 장치는 있었지만(`RedisLoginAttemptStore`) 요청 자체를 막는 장치는 없었다.

## 2. 후보와 선택

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| **직접 구현: 필터 + Redis 카운터 (선택)** | 새 의존성이 없다. 이미 쓰는 Redis와 로그인 잠금의 카운터 구조를 그대로 쓴다. 서버가 여러 대여도 카운터를 공유한다 | 알고리즘과 예외 처리를 직접 관리해야 한다 |
| Bucket4j 등 라이브러리 | 토큰 버킷, 분산 저장소 연동이 준비돼 있다 | 의존성과 설정이 늘어난다. 이번 규모(IP별 분당 N회)에는 과하다 |
| 앱 메모리(Caffeine 등)로 카운트 | 가장 빠르다 | 서버마다 카운터가 따로라서 서버가 늘면 한도가 서버 수만큼 커진다 |
| 프록시·게이트웨이에서 제한 | 앱 코드가 필요 없다 | 프록시 설정은 배포 담당 영역이고 앱 안에서 정책(로그인은 더 엄격하게)을 나누기 어렵다 |

선택 이유: Redis 카운터는 새 인프라가 필요 없고, 로그인 잠금과 같은 구조라 이해하기 쉬우며, 서버가 늘어도 한도가 유지된다.

알고리즘은 **고정 윈도우**(키마다 첫 요청 시점부터 `window`(기본 1분) 동안 세고, 그 시간이 지나면 카운터가 만료되어 다시 센다)를 골랐다. 시계의 정각이 아니라 IP별 첫 요청이 기준이다. 구현이 가장 단순하고 Redis 명령 두 개(`INCR`, `PEXPIRE`)로 끝난다. 윈도우 경계에서 순간적으로 최대 2배가 통과할 수 있는 한계는 7절에 적었다.

## 3. 정책

| 정책 | 대상 | 한도 (분당, IP별) |
| --- | --- | --- |
| `auth` | `/api/auth/` 하위 경로, `/api/admin/auth/` 하위 경로 | 10회 |
| `api` | 그 외 `/api/**` | 120회 |

- 제외: `/api/webhooks/**`(외부 서비스가 보내는 요청이라 막으면 안 된다), 관리 포트 8081(필터가 앱 포트의 `/api/**`에만 적용된다).
- 카운터 키: `recipick:rate:{정책}:{IP}`. 정책 이름이 들어가서 로그인류와 일반 API를 따로 센다.
- 한도 초과 시 `429`와 에러 코드 `COMMON-012`(`요청이 너무 많습니다. 잠시 후 다시 시도해주세요.`)를 돌려준다.
- 로그인류를 더 엄격하게 둔 이유: 무차별 대입 공격의 대상이고 BCrypt 연산이 무겁기 때문이다.
- 값은 `recipick.rate-limit.{window, auth-limit, api-limit}`으로 설정에서 바꾼다.

## 4. 구현

- `global/filter/RateLimitFilter`: 요청이 컨트롤러에 닿기 전에 IP별 카운터를 올리고 한도를 넘으면 429로 응답한다. 요청 로그 필터 바로 뒤에 두어 429도 요청 로그(`status=429`)에 남는다.
- `infra/redis/RedisRateLimitStore`: Lua 스크립트로 `INCR`과 첫 요청에서만 `PEXPIRE`를 한 번에 실행한다. 둘을 따로 실행하면 그 사이에 장애가 났을 때 만료 없는 카운터가 남아 그 IP가 계속 막힐 수 있어서 원자적으로 묶었다.
- `global/config/RateLimitProperties`: 설정 바인딩.
- Redis 오류 시: 예외를 잡아 경고 로그만 남기고 **제한 없이 통과(fail-open)**시킨다. 제한 장치 때문에 서비스가 멈추면 안 된다는 판단이며, 조회 캐시의 `CacheErrorHandler`와 같은 원칙이다.
- Redis 타임아웃을 명시했다. `spring.data.redis.timeout`(500ms)은 명령을 보낸 뒤 응답을 기다리는 시간이고, `connect-timeout`(1s)은 연결을 맺는 시간이다. 기본값(약 60초)이면 Redis가 응답만 멈췄을 때 요청 스레드가 그 시간 동안 묶여, 위의 fail-open이 즉시 동작하지 않는다.
- 스위치 `recipick.rate-limit.enabled`(환경변수 `RATE_LIMIT_ENABLED`). 테스트 프로필은 끄고, 필터 테스트만 켠다. **k6 부하 테스트는 한 IP에서 많은 요청을 보내므로 반드시 끄고 실행한다.**

## 5. 결과

### 동작 확인 (로컬, 같은 IP에서 `curl` 연속 호출)

| 시나리오 | 제한 전 | 제한 후 |
| --- | --- | --- |
| `GET /api/categories` 130회 | 200 × 130 | 200 × 120, **429 × 10** |
| `POST /api/auth/login` 15회(빈 본문) | 400 × 15 | 400 × 10, **429 × 5** |
| 로그인 한도 초과 직후 `GET /api/categories` 30회 | - | 200 × 30 (정책별로 따로 센다) |

한도(120, 10)까지는 모두 통과하고 그 이후만 거부되며, 그 IP의 첫 요청에서 `window`(1분)가 지나 카운터가 만료되면 다시 통과한다. 로그인 줄이 막혀도 일반 API는 영향을 받지 않는다.

### 자동 테스트

`RateLimitFilterTest`(한도를 일반 3회, 로그인 2회로 낮춰 실행) 5개가 통과한다.

| 테스트 | 확인 내용 |
| --- | --- |
| 한도 안의 요청은 통과한다 | 3회 모두 200 |
| 한도를 넘으면 429와 `COMMON-012`를 돌려준다 | 4번째 요청이 429, 본문 코드 확인 |
| 로그인류는 일반 API와 따로 센다 | 로그인 3번째 429, 같은 때 `GET /api/categories`는 200 |
| 웹훅은 한도를 넘겨도 막지 않는다 | 5회 모두 429가 아님 |
| Redis 카운터가 실패하면 제한 없이 통과한다 | 카운터 예외 상황에서도 200 |

### 측정하지 않은 것

- 여러 IP나 실제 부하(k6)에서의 Before/After 수치는 측정하지 않았다. 이 문서의 수치는 "한도를 넘으면 거부된다"는 동작 확인이다. 한 IP가 몰아칠 때 DB 풀 점유가 얼마나 줄어드는지는 이후 측정 항목이다.
- 거부 건수를 보는 Prometheus 지표(`rate_limit_rejected_total`)와 Grafana 패널은 아직 없다. 거부는 요청 로그의 `status=429`로 확인한다.

## 6. 해석

- 한도를 넘은 요청은 컨트롤러, 서비스, DB를 거치지 않고 필터에서 바로 끝난다. BCrypt 연산이나 DB 연결을 쓰지 않으므로 한 클라이언트의 폭주가 풀 대기를 늘리는 경로를 막는다(효과 크기는 5절 "측정하지 않은 것" 참고).
- 로그인 잠금(실패 3회)은 "맞는 아이디에 대한 추측"을 막고, 요청 수 제한은 "아이디와 무관한 폭주"를 막는다. 서로 보완한다.

## 7. 한계와 주의

- **IP 기준이다.** 같은 공유기나 회사망의 사용자는 한 묶음으로 센다. 회원별 제한은 하지 않았다. 필터가 Spring Security 앞에 있어 요청 시점에 회원을 알 수 없기 때문이다.
- **프록시 설정에 의존한다.** 운영은 `server.forward-headers-strategy: native`로 프록시 뒤에서도 실제 클라이언트 IP를 쓴다. 다만 프록시가 클라이언트가 보낸 `X-Forwarded-For`를 덮어쓰는지는 확인하지 못했다. 덮어쓰지 않으면 헤더 위조로 제한을 우회할 수 있다.
- **고정 윈도우의 경계 문제.** 윈도우가 바뀌는 순간 직전과 직후에 각각 한도만큼 보내면 짧은 시간에 최대 2배가 통과할 수 있다.
- **429 응답에 CORS 헤더가 없다.** 필터가 Spring Security(CORS 처리) 앞에 있어서, 프런트가 다른 도메인이면 브라우저가 429 본문을 읽지 못하고 CORS 오류로 볼 수 있다. 프런트 도메인이 다르면 필터를 보안 체인 안으로 옮기는 후속 작업이 필요하다.
- `/api/auth/logout`, `/api/auth/reissue`도 `auth` 정책(분당 10회)에 묶인다. 정상 사용에서는 충분하지만 한도 조정이 필요할 수 있다.
- Redis 장애 중에는 제한이 풀린다(fail-open). 이 상태에서는 요청 수 제한이 없는 것과 같다.
- Redis 타임아웃 500ms는 Redis를 쓰는 모든 곳(로그인 잠금, 리프레시 토큰, 조회 캐시, 요청 수 제한)에 적용된다. 서버에서 부하를 걸었을 때 정상 요청이 타임아웃으로 실패하지 않는지 다시 확인해야 한다.
- `Retry-After` 헤더는 넣지 않았다. 클라이언트는 429 응답만 보고 재시도 시점을 알 수 없다.
- 로컬 단일 PC 확인이라 서버(AWS) 환경에서 다시 확인한다.
