# 회원·관리자 인증과 브라우저 세션 보완

## 바뀐 정책

2026-11-11 보완입니다. 기존 문서의 “비밀번호 변경·로그아웃 후 액세스는 만료까지 허용” 정책을 변경합니다.

- 액세스 JWT에 회원 tokenVersion을 포함하고 DB의 refresh_token_version과 비교합니다.
- 회원은 탈퇴 여부·버전, 관리자는 활성 여부·역할·소속 마트를 공통 인증에서 확인합니다.
- 업무 API는 Redis의 sid 세션도 존재해야 접근할 수 있습니다.
- 비밀번호 변경은 모든 이전 회원 버전, 로그아웃은 해당 sid만 폐기합니다.
- 로그아웃은 같은 sid 삭제를 반복해도 성공할 수 있습니다. 일반 업무 API는 삭제된 sid로 접근할 수 없습니다.
- 최초 로그인 시점부터 최대 14일입니다. 회전은 sessionExpiresAt을 유지하고 액세스·리프레시 모두 그 시각을 넘지 않습니다.
- 기존 보안 스키마 토큰은 허용하지 않고 재로그인을 요구합니다.

이는 JWT만으로 요청을 인증하는 무상태 구조가 아닙니다. DB·Redis를 확인해 세션 회수를 우선합니다. 인증 저장소 장애를 정상 인증으로 통과시키지 않으며, 기존 상품 캐시·요청 제한의 fail-open과 구분합니다.

## API·Cookie

| 주체 | 재발급 | 로그아웃 | Cookie |
| --- | --- | --- | --- |
| 회원 | POST /api/auth/reissue | POST /api/auth/logout | memberRefreshToken, Path=/api/auth |
| 관리자 | POST /api/admin/auth/reissue | POST /api/admin/auth/logout | adminRefreshToken, Path=/api/admin/auth |

리프레시 Cookie는 HttpOnly·SameSite=Strict이며 Secure는 기존 설정을 따릅니다. 로그인 때 기존 refreshToken Cookie를 만료시킵니다. 로그아웃 요청의 액세스와 Cookie가 다른 정상 세션이면 그 Cookie를 지우지 않습니다.

GET /api/auth/csrf는 data.headerName·data.token을 반환하고 authCsrfToken Cookie를 설정합니다. 인증 Cookie를 발급·교체·폐기하는 POST 경로와 회원가입은 Cookie와 X-CSRF-TOKEN 헤더가 일치해야 합니다. 잘못되면 AUTH-013(403)입니다.

CSRF Cookie는 리프레시 인증 Cookie와 다른 용도이며, Swagger의 헤더 전달을 위해 JavaScript에서 읽을 수 있습니다. 로그인 자격·리프레시 원문을 보관하지 않습니다. 업무 Bearer API와 서명 검증 웹훅은 이 인증 전용 CSRF matcher의 적용 대상이 아닙니다.

## 민감 작업 재인증

비밀번호 변경·탈퇴는 MEMBER_REAUTH 이름공간으로 회원별 실패 제한을 공유합니다. 10분 안 연속 실패 5회면 민감 작업을 10분 제한하고 MEMBER-009(403)을 반환합니다. 이 숫자는 현재 정한 정책이며 최적값 비교 결과는 아닙니다. 일반 로그인 잠금과 분리해 다른 정상 이용까지 계정 전체를 잠그지 않습니다.

회원 행 잠금 후 비밀번호 검증은 유지합니다. Redis 재인증 카운터는 DB 롤백과 별개로 실패를 남깁니다. 성공 시 잠금이 없을 때만 실패 이력을 지워 동시 실패가 만든 잠금을 무조건 해제하지 않습니다.

## 프론트

- 회원·관리자 토큰·초기 복구·재발급 Promise를 분리합니다.
- 같은 탭의 동시 재발급은 주체별 한 번으로 합칩니다.
- Web Locks 지원 브라우저는 같은 주체의 탭 간 회전·로그아웃을 순서화합니다.
- BroadcastChannel로 해당 sid의 로그아웃을 다른 탭에 전달하며 토큰을 localStorage에 저장하지 않습니다.
- Web Locks 미지원 환경은 탭 내부 단일화만 적용되므로 탭 간 경합을 같은 수준으로 보장하지 않습니다.
- 명확한 CSRF 거절만 새 보호 정보를 받아 한 번 재시도합니다. 업무 요청의 결과 불명 재시도와 다릅니다.
- 서버·네트워크 장애를 로그인 만료로 처리하지 않습니다. 회원 로그아웃 실패는 화면에 안내하고 성공처럼 인증 상태를 지우지 않습니다.

## 멤버십 화면

기존 endAt은 정상 이용기간 종료로 유지합니다. 현재 이용권에 graceEndAt·effectiveEndAt·inGrace를 추가하고 내 정보 요약에도 effectiveEndAt·inGrace를 추가합니다. 프론트는 실제 혜택 종료 시각과 “결제 유예 중”을 표시합니다. 유예 중 예약 확인 문구는 즉시 혜택 종료를 명확히 안내합니다. 결제·환불 계산과 PG 코드는 변경하지 않습니다.

## 보안 이벤트와 업무 감사

업무 감사의 동일 트랜잭션 계약은 유지합니다. TOKEN_REJECTED·SESSION_REVOKED·ADMIN_STATE_REJECTED·PASSWORD_CHECK_FAILED·PASSWORD_CHECK_LOCKED·AUTH_STORE_UNAVAILABLE 같은 보안 실패는 애플리케이션 로그로 별도 기록합니다.

비밀번호·Cookie·토큰 원문·이메일·전화번호·검색어·예외 메시지는 보안 이벤트에 넣지 않습니다. 이 로그가 내구성 있는 감사 저장소나 실패 행위의 완전한 장기 보관을 보장하는 것은 아닙니다.

## 운영 반영 순서

1. 변경된 백엔드 테스트와 프론트 인증 테스트·빌드를 모두 통과시킵니다.
2. 같은 PR의 백엔드를 먼저 정상 배포하고 해당 프론트를 이어서 배포합니다.
3. 기존 이용자는 화면을 새로고침하고 한 번 재로그인합니다. 기존 토큰을 허용하는 임시 우회는 두지 않습니다.
4. 회원·관리자 동시 로그인, 각자 새로고침·재발급·로그아웃, 비밀번호 변경 후 구 토큰 거절, 유예 상태 표시를 확인합니다.
5. 새 필수 환경변수·DB 컬럼·인프라 추가는 없습니다. Redis 전체 삭제와 키 교체도 하지 않습니다.
6. 롤백은 백엔드·프론트를 함께 되돌립니다. 구 코드로 돌아가면 강화된 액세스 회수 보장도 되돌아간다는 점을 인지해야 합니다.

현재 CI는 프론트 빌드 전에 npm run test:auth를 실행합니다. 배포 브랜치 레포 변수의 실제 값은 이 문서에서 가정하지 않습니다. 실제 운영 반영과 TEST PG 검증은 로컬 코드·테스트 완료와 구분해 기록해야 합니다.
