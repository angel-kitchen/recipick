# 멤버십 결제 미정산 판정 (C-17)

회원 탈퇴가 "이 회원의 멤버십 결제 중 아직 끝나지 않은 것이 있나"를 묻는 결제 도메인 계약입니다. 3차 2단계(PR-2b) 기준.

- `MembershipPaymentQueryService.existsUnresolved(Collection<Long> membershipIds)` → `boolean`
- 호출자: 회원 탈퇴 Facade. 종료·만료 이용권까지 **모든** 이용권 ID(C-8)를 넘깁니다. 빈 목록은 조회 없이 `false`입니다.
- `@Transactional(propagation = MANDATORY)` — 바깥 트랜잭션 없이 부르면 `IllegalTransactionStateException`입니다. MANDATORY가
  강제하는 것은 **바깥 트랜잭션의 존재뿐**입니다. 회원 잠금이 먼저인지, 잠금 전에 일반 조회가 없는지는 검사하지 못하므로 그 둘은
  아래 전제(호출자 계약)와 동시성 테스트로 보장합니다.
- 조회 예외는 성공으로 바꾸지 않고 전파합니다(호출 트랜잭션 롤백).

## 미정산으로 보는 네 조건(하나라도 참이면 true)

| # | 조건 |
| --- | --- |
| ① | 회차 상태가 `PENDING`·`RETRY_WAITING`·`PAYMENT_METHOD_REQUIRED`·`UNKNOWN`·`MANUAL_REVIEW` |
| ② | 시도 상태가 `READY`·`DISPATCHING`·`UNKNOWN`·`MANUAL_REVIEW` |
| ③ | 환불 상태가 `REQUESTED` |
| ④ | 시도가 `PAID`이고 `refund_required_at`이 있는데 **그 시도의 SYSTEM 환불 `COMPLETED`가 없음** (MEMBER 환불 COMPLETED는 해제하지 않음) |

## 안전하게 호출하기 위한 전제

이 판정은 잠그지 않는 일반 조회입니다. InnoDB REPEATABLE READ에서 일반 조회의 스냅숏은 **그 트랜잭션의 첫 일반 읽기 시점**에
만들어지고 `FOR UPDATE` 같은 잠금 읽기는 스냅숏을 만들지 않습니다. 그래서 "회원 잠금 뒤의 판정은 최신을 본다"는 아래 세 전제가
모두 성립할 때만 참입니다.

| 전제 | 내용 | 지키는 쪽 | 증거 |
| --- | --- | --- | --- |
| P1 | 호출자 트랜잭션의 **첫 DB 작업이 `MemberService.lockActiveMember(memberId)`**이고, 잠금 전에 어떤 일반 조회도 하지 않습니다(`@LoginMember` 해석·인증 필터의 조회는 트랜잭션 밖이라 무관) | 회원 탈퇴 Facade(1단계가 이미 이 순서) | `MembershipPaymentQueryConcurrencyTest` — 지키면 직렬화, 어기면 오래된 스냅숏 재현 |
| P2 | 이 회원의 회차·시도·환불을 **만들거나 상태를 바꾸는 모든 트랜잭션이 회원 행 잠금을 먼저 잡습니다.** 탈퇴 회원 거절(`lockActiveMember` → MEMBER-001)은 **신규 거래 접수**에만 적용하고, 이미 시작된 거래의 결과 반영·복구·SYSTEM 환불은 탈퇴 뒤에도 진행합니다(잠금만 잡고 탈퇴 상태로 거절하지 않는 메서드 — 4단계 설계에서 정의) | 4·5단계 설계(아래 표를 다시 싣고 경로마다 잠금 위치를 적습니다) | 4·5단계 테스트 |
| P3 | 잠금 대상은 `member` 행 하나(`findByIdForUpdate`)이고 모든 경로가 같은 행을 씁니다 | `MemberService` | — |

| P2 쓰기 경로 | 단계 | 회원 행 잠금 | 탈퇴 회원 | 비고 |
| --- | --- | --- | --- | --- |
| 바로 구독 접수 TX1(회차·시도 생성) | 4 | 필수 | **거절**(신규 거래) | |
| 갱신 접수 TX1(스케줄러) | 4 | 필수(회원별) | **거절**(신규 거래) | |
| 시도 선점 READY → DISPATCHING | 4 | 시도 행만 | — | 둘 다 미해결이라 판정 불변 |
| 결과 반영 TX2(시도·회차 확정, `refund_required_at`) | 4 | 필수 | **진행**(이미 시작된 거래의 후속 정합화) | 웹훅 경로 포함 |
| 복구 Sweep(UNKNOWN 재조회·MANUAL_REVIEW) | 4 | 필수 | **진행** | |
| SYSTEM 환불 생성·완료 | 5 | 필수 | **진행**(돌려줄 돈은 탈퇴와 무관) | ④ 판정에 영향 |
| MEMBER 환불 신규 접수(즉시 해지 요청) | 5 | 필수 | **거절**(신규 거래) | ③ 판정에 영향 |
| 이미 접수된 MEMBER 환불의 PG 결과 확인·완료 반영 | 5 | 필수 | **진행**(이미 시작된 거래의 후속 정합화) | ③ 판정에 영향 |
| 운영 수동 처리 | 4·5 | 필수 | 진행 | |

돈을 돌려주는 후속 처리는 처음 누가 요청했느냐(MEMBER·SYSTEM)가 아니라 이미 접수된 거래의 후속 처리냐로 구분합니다.
탈퇴 뒤에도 진행하는 경로가 회원 행을 잠그는 이유는 탈퇴 판정과의 직렬화(P1·P2)이지 탈퇴 차단이 아닙니다. 탈퇴가 먼저 커밋됐다면
C-17이 그 거래를 미정산으로 보고 탈퇴를 막았을 것이고, 거래의 후속 정합화가 먼저 커밋됐다면 탈퇴가 그 결과를 봅니다.

P1·P2가 성립하면 판정이 틀릴 수 있는 방향은 "SYSTEM 환불 COMPLETED가 늦게 보여 더 막는 쪽"뿐입니다(안전). 상품 결제 판정(1단계)이
`FOR SHARE` 잠금 읽기를 택한 것과 다른 이유는 상품 결제는 웹훅 수신기가 회원을 잠그지 않는 기존 경로라 P2를 만들 수 없었기 때문입니다.
멤버십 결제는 모든 쓰기 경로를 새로 설계하므로 P2를 규칙으로 둡니다. P2가 깨지는 경로가 4·5단계 설계에서 나오면 그때 잠금 읽기로 바꿉니다.
