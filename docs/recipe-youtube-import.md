# 유튜브 레시피 100개 수집·적재 계획

레시픽(Recipick) · 레시피 도메인 · 작성일: 2026-10-25

> 핵심: 유튜브 영상에서 레시피를 "가져오는" 일의 본질은 수집이 아니라 구조화와 검수다. 사람은 메뉴 목록과 재료 마스터만 결정하고, 영상 찾기·수집·구조화·규칙 검증은 스크립트와 LLM이 한다.

## 1. 목적과 범위

- 요구사항 `레시피 관리`의 레시피 100개(한식 70·양식 30)를 유튜브 영상 기반으로 등록한다.
- 레시피는 관리자 API(`POST /api/admin/recipes`, `PUT /api/admin/recipes/{id}/ingredients`)가 받는 형태로 만든다.
  - 레시피: 이름(50자), 한식/양식, 요리 유형 8종(SOUP·STEW·STIR_FRY·RICE·NOODLE·SIDE·PASTA·ETC), 기본 인분(1~10), 조리 시간, 난이도(EASY·NORMAL·HARD), 맵기(0~3), 조리 순서, 유튜브 URL
  - 레시피 재료: 재료 마스터 ID, 1인분 필요량(소수 둘째 자리), 필수 여부. 단위는 재료 마스터(G·ML·EA)를 따른다.
- 유튜브 어디에도 이 형태로 적힌 데이터는 없다. 설명란·자막 원문을 위 스키마로 바꾸는 단계가 반드시 필요하다.
- 이 작업은 서버 기능이 아니라 일회성 데이터 작업이다. `infra/ai`는 런타임 AI 장보기용이므로 여기서 쓰지 않는다.

## 2. 기본 원칙

1. 사람이 결정하는 것은 두 가지다. 어떤 요리 100개를 넣을지(메뉴 목록)와 재료 마스터의 이름·단위 기준.
2. 영상 찾기, 설명란·자막 수집, 구조화, 규칙 검증은 스크립트와 LLM이 한다.
3. LLM에게 영상 링크를 직접 묻지 않는다. 존재하지 않는 영상 ID를 만들어 낸다. 링크는 항상 YouTube Data API 결과에서만 가져온다.
4. 설명란·자막 원문은 DB와 레포에 저장하지 않는다. DB에는 요약한 조리 순서와 영상 ID만 들어간다.
5. 검수된 JSON 파일이 원본이고 DB는 결과물이다. 적재 스크립트는 어느 DB에든 다시 돌릴 수 있어야 한다.
6. 배포와 독립적으로 진행한다. 배포는 나중에 하고, 그때 같은 적재 스크립트를 배포 서버에 한 번 더 돌린다.

## 3. 작업 순서

1. 메뉴 목록 100개를 확정한다. Claude 초안을 팀이 시트에서 다듬는다.
2. 재료 마스터의 이름·단위 기준을 상품 등록 담당과 맞춘다.
3. 스크립트로 요리별 영상을 자동 선정하고, 사람이 제목·썸네일만 훑어 바꾼다.
4. 설명란과 자막을 수집해 영상별 원문 JSON으로 저장한다.
5. Claude Batch로 관리자 API 입력 형태의 JSON으로 구조화한다.
6. 규칙 검증·LLM 재확인·플래그 분류로 걸러낸 뒤 사람이 걸린 항목만 검수하고, 검수된 JSON을 레포에 커밋한다.
7. 적재 스크립트로 로컬 DB에 넣고 자동 장보기 지정까지 확인한다.

## 4. 단계별 상세

### 4.1 메뉴 목록

- 조건: 한식 70·양식 30, 요리 유형 8종이 고르게 분포, 마트에서 파는 재료로 만들 수 있는 요리.
- Claude에게 조건을 주고 후보 목록을 받은 뒤 팀이 시트에서 빼고 넣는다. 10~20분.
- 시트 열: 요리명, 한식/양식, 요리 유형. 이 값이 레시피 이름·cuisineType·dishType의 원본이 된다.

### 4.2 재료 마스터 기준

- 자동 장보기 지정은 모든 필수 재료가 마트 상품에 연결돼야 가능하다. 재료 이름·단위를 상품 등록 담당과 먼저 맞추지 않으면 100개를 넣고 다시 손봐야 한다.
- 결정할 것: 재료 세분화 수준(예: "대파·파·쪽파"를 합칠지), 단위(G·ML·EA 중 하나), 신규 재료 승인 담당.

### 4.3 영상 자동 선정

- 신뢰 채널 3~5개를 정한다. 설명란에 재료·분량을 적는 채널(예: 백종원, 만개의레시피, 쿠킹하루). 채널별 설명란 형식이 일정해 뒤의 LLM 추출 정확도가 올라간다.
- `playlistItems.list`로 채널 업로드 목록을 전부 받는다. 50개당 1유닛이라 비용이 거의 없다. 제목을 메뉴 목록과 매칭해 후보를 뽑는다.
- 매칭 안 된 요리만 `search.list`로 "요리명 레시피"를 검색한다. 검색은 1회 100유닛, 하루 무료 할당량 10,000유닛이므로 하루 100회가 한도다. 전체를 검색으로 하면 꼭 하루 분량이라 채널 목록을 먼저 쓴다.
- 후보별 자동 점수로 1순위와 예비 1개를 고른다.

| 기준 | 처리 |
| --- | --- |
| 임베드 허용 | 미허용은 탈락. 레시피 상세에서 영상을 표시한다. `videoEmbeddable=true` |
| 자막 실제 수신 | 받아 보고 판정. API의 자막 필터는 자동 자막까지 보장하지 않는다 |
| 설명란에 "재료"와 분량 숫자 | 있으면 가점 |
| 길이 4~20분 | 쇼츠·라이브 제외. `videoDuration=medium` |
| 조회수·업로드 시점 | 가점 |

- 남는 사람 일: 자동 선정 100개의 제목·썸네일을 훑어 엉뚱한 영상(먹방 등)을 예비로 바꾼다. 30분~1시간.

### 4.4 수집

- 설명란: Data API v3 `videos.list`. 공식·무료, 50개씩 조회. 재료·분량의 1순위 소스다.
- 자막: Data API의 자막 다운로드는 본인 영상에만 되므로 `youtube-transcript-api` 또는 `yt-dlp`의 자막만 받기를 쓴다. 자동 생성 자막은 재료명·수량 오인식이 잦아 조리 순서와 설명란에 빠진 분량을 채우는 용도로만 쓴다.
- 자막 없는 영상은 버리고 예비로 바꾼다. 후보를 130개쯤 모아 두면 된다. 오디오 다운로드 후 Whisper 받아쓰기는 약관 부담이 커서 마지막 수단이다.
- 자막 요청은 클라우드 IP에서 자주 차단되므로 로컬 PC에서 1~2초 간격으로 실행한다.
- 영상별 원문(제목·설명란·자막·길이·채널)을 `videoId.json`으로 저장해 재실행 시 다시 받지 않는다. 이 원문은 커밋하지 않는다.

```bash
pip install youtube-transcript-api yt-dlp
```

### 4.5 구조화

- 입력: 제목·설명란·자막, 재료 마스터 목록(이름·단위), 시트에서 정한 요리명·한식/양식·요리 유형.
- 출력: 아래 형태. 구조화 출력으로 스키마를 강제한다.

```json
{
  "name": "김치찌개",
  "cuisineType": "KOREAN",
  "dishType": "STEW",
  "baseServings": 2,
  "cookingTimeMinutes": 30,
  "difficulty": "EASY",
  "spicyLevel": 2,
  "youtubeUrl": "https://www.youtube.com/watch?v=...",
  "steps": [
    { "order": 1, "description": "돼지고기를 한입 크기로 썰어 기름에 볶는다." }
  ],
  "ingredients": [
    {
      "name": "돼지고기 앞다리살",
      "unit": "G",
      "amountPerServing": "100.00",
      "required": true,
      "matchedIngredientId": 12,
      "estimated": false
    }
  ],
  "metaEstimated": ["difficulty", "spicyLevel"]
}
```

- 프롬프트에 넣는 환산 규칙
  - 큰술 15ml, 작은술 5ml, 종이컵 180ml
  - 영상이 N인분이면 N으로 나눠 1인분 필요량을 소수 둘째 자리까지
  - "약간", "적당히"는 선택 재료로 두고 수량은 추정 표시(`estimated: true`)
  - 재료 마스터에 없는 재료는 `matchedIngredientId: null`로 신규 제안 분리
  - 조리 순서는 자막을 베끼지 않고 단계별 요약 문장으로
  - 난이도·맵기·조리 시간은 원문에 없으면 추정하고 `metaEstimated`에 표시
- 모델 `claude-opus-5-5`, 100건은 Message Batches로 한 번에 돌린다(50% 할인).

| 항목 | 100건 기준 |
| --- | --- |
| 입력 약 800K 토큰 | 약 $3.2 |
| 출력 약 150K 토큰 | 약 $3.0 |
| 배치 할인 적용 | 약 $3 |

### 4.6 검수

사람이 100개를 전부 보지 않는다. 네 겹으로 걸러 걸린 항목만 본다. 목표는 100개 중 20~30개, 그중에서도 플래그가 붙은 항목만.

1. 규칙 검증(스크립트)
   - 재료명이 마스터에 없음, 단위가 G·ML·EA가 아님
   - 1인분 분량 비정상(예: 소금 500g, 돼지고기 5g)
   - 조리 순서 2개 이하 또는 20개 이상, 조리 시간 0 또는 300분 초과
2. LLM 재확인
   - 추출 결과와 원문을 함께 주고 "원문에 근거 없는 수치가 있는가"를 항목별로 판정시킨다.
   - 또는 같은 영상을 두 번 추출해 분량이 어긋나는 재료만 표시한다.
3. 플래그 항목만 사람이 본다
   - 필수 재료의 `estimated: true`는 반드시 본다.
   - 선택 재료의 플래그는 시연 품질 영향이 적어 넘겨도 된다.
4. 통과분 무작위 10개 확인
   - 오류가 거의 없으면 나머지 통과분은 믿는다.
   - 오류가 많으면 프롬프트를 고쳐 다시 돌린다. 100개를 손으로 고치는 것보다 빠르다.

- 사람이 꼭 봐야 하는 것은 레시피가 아니라 재료 마스터다. 신규 재료 제안 목록(30~50개)을 한 번 승인하거나 기존 재료에 합치면 100개의 매칭이 한꺼번에 정리된다.
- 조리 순서 문장은 보지 않는다. 서비스 동작에 영향이 없고 형식 오류는 적재 시 관리자 API 검증이 막는다.
- 예상 소요: 재료 마스터 정리 30분, 플래그 확인 1시간, 무작위 확인 30분. 한 명 두 시간 안쪽.

### 4.7 적재

- 검수 완료 JSON을 레포에 커밋한다(예: `src/main/resources/seed/recipes.json`).
- SQL 직접 INSERT 대신 관리자 API를 호출하는 스크립트로 넣는다. 엔티티의 인분 범위·조리 순서·재료 중복 검증을 그대로 타고, 누구 DB에서든 같은 스크립트로 재현된다.
- 호출 순서
  1. `POST /api/admin/ingredients` 신규 재료
  2. `POST /api/admin/recipes` 레시피
  3. `PUT /api/admin/recipes/{id}/ingredients` 레시피 재료
  4. `PATCH /api/admin/recipes/{id}/auto-cart` 자동 장보기 지정
- 자동 장보기 지정이 실패하는 레시피는 연결 상품 없는 필수 재료가 있다는 뜻이다. 상품 등록 쪽과 맞춘다.
- 배포 후 같은 스크립트를 배포 서버에 한 번 더 돌린다.

## 5. 주의 사항

- 유튜브 약관: 설명란은 공식 API로 받는다. 자막·영상 다운로드는 비공식 경로이므로 원문을 저장·공개하지 않고 요약만 DB에 넣는다. 영상은 `youtube_video_id`로 공식 플레이어 임베드만 한다.
- 임베드 금지 영상은 레시피 상세에서 재생되지 않으므로 선정 단계에서 걸러야 한다.
- 쇼츠는 정보가 부족하고, 1시간짜리 라이브는 자막이 너무 길다. 4~20분 영상만 쓴다.
- 자막 요청은 로컬에서, 간격을 두고 실행한다.
