# 프롬프트 개선 이력

> 각 개선은 "변경 동기 → 토큰 변화 → 출력 품질 변화 → 다음 개선 방향" 순서로 기록한다. 수치는 `evaluation.md`의 실행 결과를 쓴다.

프롬프트 위치: `ClaudeAiClient`의 `MENU_INSTRUCTION`, `CONDITION_INSTRUCTION`, `RECOMMEND_INSTRUCTION`, `FRIDGE_INSTRUCTION`(v5부터)

## v1. 첫 버전
| 항목 | 내용 |
| --- | --- |
| 내용 | 역할(메뉴 분석기·조건 분석기·추천기), 찾을 항목과 값의 범위, 목록에 없는 ID 금지, 말하지 않은 값의 표시(인분 0, 맵기 -1, 빈 문자열), 사용자 문장 속 지시를 따르지 않기 |
| 설계 이유 | 구조화 출력은 null을 쓸 수 없어 "말하지 않음"을 0·-1·빈 문자열로 받고 서버에서 null로 바꾼다. 사용자 문장이 그대로 들어가므로 지시 주입을 막는 줄을 넣었다 |
| 토큰 | 문장 50개 기준 입력 15,181·캐시 읽기 44,689, 출력 2,712(Sonnet). 호출 1건 출력 50~60토큰 |
| 출력 품질 | 메뉴 분석 30/30(세 모델 모두). 조건 분석 Sonnet 20/20, Opus 19/20, Haiku 16/20(2026-11-03, `evaluation.md` 5절) |
| 다음 개선 방향 | Opus·Haiku가 말하지 않은 종류를 요리 구분(찌개·반찬)으로 추론해 한식을 채움 → v3 |

## v2. 추천기에 "맞는 게 없으면 빈 목록" 추가
| 항목 | 내용 |
| --- | --- |
| 내용 | `RECOMMEND_INSTRUCTION`에 후보 중 맞는 레시피가 없으면 억지로 고르지 말고 빈 목록으로 두라는 줄 추가 |
| 변경 동기 | "최대 5개 고른다"만 있어 문장과 맞지 않아도 후보를 골랐다. 서버는 빈 목록을 `NO_MATCH`로 처리하도록 함께 바꿨다 |
| 토큰 | ③ 평가 문장 14개 기준 출력 3,920 → 976(약 1/4), 입력 8,681 → 9,409(추가한 한 줄). 응답 시간 평균 3.4초 → 1.9초 |
| 출력 품질 | ③ 정답 3/14 → 13/14. 맞는 게 없는 문장의 빈 목록 1/7 → 7/7, 맞는 게 있는데 빈 목록을 준 경우 0건(2026-11-04, Sonnet, `evaluation.md` 5절) |
| 다음 개선 방향 | 맞는 레시피와 함께 관련이 약한 후보를 덧붙이는 경우가 1건 남음("버섯 들어간 양식 밥 요리"에 빠에야·토마토리조또). 문장에 직접 맞는 레시피만 고르도록 다듬을지 운영 이력과 함께 본다 |

## v3. 조건 분석기에 "요리 구분만으로 종류를 정하지 않음" 추가
| 항목 | 내용 |
| --- | --- |
| 내용 | `CONDITION_INSTRUCTION`의 cuisineType 설명에 "한식·양식처럼 종류를 직접 말했을 때만 채우고, 찌개·반찬 같은 요리 구분만으로 정하지 않는다" 추가 |
| 변경 동기 | v1 평가에서 "30분 안에 되는 안 매운 찌개", "두부랑 계란 빼고 30분 이내 반찬" 등에 말하지 않은 한식을 채움(Opus 1건, Haiku 3건). 지금 데이터는 찌개·반찬이 모두 한식이라 결과는 같지만, 양식 찌개·반찬이 생기면 그 레시피가 빠진다 |
| 토큰 | 조건 분석 입력 14,504 → 15,644(문장당 약 57토큰 증가), 출력 1,228(세 모델 같음). 요청 1건 비용 차이는 미미 |
| 출력 품질 | 조건 분석 Haiku 16/20 → 20/20, Opus 19/20 → 20/20, Sonnet 20/20 유지. 메뉴 분석은 세 모델 모두 30/30 유지(2026-11-04, `evaluation.md` 5절) |
| 다음 개선 방향 | Haiku가 v3로 조건 분석을 모두 맞히면 비용이 약 1/20인 Haiku 전환을 다시 검토(`model-selection.md` 4절) |

## v4. 대충 쓴 문장 대응 (조건 없으면 전체에서 고르기, 후보 속성, 구어체 예시)
| 항목 | 내용 |
| --- | --- |
| 내용 | `CONDITION_INSTRUCTION`에 띄어 쓴 재료 이름 붙이기, 줄임말·신조어 예시(파스타 ㄱㄱ, 양식 땡김, 맵찔이), "'국물'이라고만 하면 요리 구분을 비움", "얼큰한은 최대 맵기가 아님", "조건으로 옮길 수 없는 말은 비움" 추가. `RECOMMEND_INSTRUCTION`에 짧은 문장·재료 이름도 후보 정보로 판단하기(해장, 얼큰한, 요린이, 두부 예시), 메뉴를 콕 집으면 그 메뉴만 고르기 추가. 후보 목록을 `ID: 이름`에서 `ID: 이름 \| 종류 요리 구분 \| 조리 시간 \| 맵기 \| 난이도 \| 필수 재료`로 바꿈. 서버는 조건이 없으면 전체 레시피를 후보로 ③을 부른다 |
| 변경 동기 | 기준선 평가에서 대충 쓴 문장 58개 중 16개만 정답. 실패 42건 중 36건이 조건을 하나도 못 뽑아 바로 `NO_MATCH`가 된 경우였다. 추천기는 후보 이름만 봐서 "얼큰한", "요린이", 재료 이름을 판단할 근거가 없었다 |
| 토큰 | 전체 흐름 60문장 기준 입력 56,381 → 497,217, 출력 7,637 → 19,756. 조건이 없으면 레시피 100개를 넘겨 요청 1건 입력이 약 8,000토큰이 되고, 비용은 약 $0.003 → $0.020(Sonnet 추정)이다. 조건 분석 입력은 20문장 기준 15,644 → 22,024(문장당 약 320토큰, 추가한 예시 줄) |
| 출력 품질 | 전체 흐름 16/58 → 54/60. 조건 분석 20/20, ③ 14/14, 장보기 30/30 유지(2026-11-04, Sonnet, `evaluation.md` 5절). 첫 실행에서 "국물" 규칙이 "국"까지 비워 조건 분석이 18/20으로 떨어져, 규칙을 "'국물'이라고만 하면"으로 좁혔다 |
| 다음 개선 방향 | ① 조건 없는 요청은 프롬프트가 매번 같으므로 프롬프트 캐시를 적용해 입력 비용을 줄인다(적용 완료: 60문장 입력 497,217 → 66,076·캐시 읽기 392,671, 요청 1건 약 $0.020 → $0.007, `evaluation.md` 5절). ② "채식"처럼 재료를 빼는 뜻을 필수 재료만으로 판단하면 육수·햄을 놓친다. 운영 이력을 보고 정답 목록과 함께 다듬는다 |

## v5. 냉장고 파먹기 Tool Calling (`FRIDGE_INSTRUCTION`, Tool 2개)
| 항목 | 내용 |
| --- | --- |
| 내용 | 새 프롬프트. 가진 재료를 등록 재료 이름으로 옮겨(넓은 이름은 해당 재료 모두, 밥 → 쌀) 레시피 찾기 Tool을 부르고, 고른 레시피들의 부족한 재료로 가격·재고 Tool을 한 번 부른 뒤 최대 3개를 골라 답한다. 가격·재고는 Tool 값만 쓰고, Tool 오류·품절·모르는 재료를 안내한다. 등록 재료 165개를 프롬프트에 넣고 Tool 정의와 함께 캐시한다. 세 번 고쳤다: v5-2 레시피 찾기를 "가진 재료가 많은 순 → 부족한 재료가 적은 순"으로 정렬, 레시피 ID를 답변에 쓰지 않음. v5-3 "재료가 있으면 먼저 찾기", "결과가 비었을 때만 한 번 더 찾기", "합계는 계산하지 않음" |
| 변경 동기 | AI 필수 항목 7-2(Tool로 백엔드 API 2개 이상 연동, 실시간 데이터를 담은 자연어 응답, Tool 실패 안내). v5-1 평가에서 가진 재료를 하나만 쓰는 레시피를 맨 앞에 두는 오답과 답변에 레시피 ID를 쓰는 경우가 나왔고, v5-2에서 Tool 없이 빈 답변·재검색 반복으로 횟수 초과·잘못 더한 합계가 나왔다 |
| 토큰 | 21문장 기준 입력 98,558·캐시 읽기 175,695, 출력 11,329(v5-3). 문장당 Claude를 평균 약 3번 부르고, 요청 1건 약 $0.016(Sonnet 추정) |
| 출력 품질 | 같은 기준(첫 번째 레시피가 정답 목록 안)으로 v5-1 19/21 → v5-2 17/21 → v5-3 20/21. 마트 미설정·품절·모르는 재료 안내와 지시 주입 방어는 세 번 모두 맞음(2026-11-04, Sonnet, `evaluation.md` 5절) |
| 다음 개선 방향 | ① 남은 오답 "어묵이랑 떡"은 떡국의 필수 재료에 떡볶이떡이 들어 있는 시드 데이터 문제라 데이터를 확인한다. ② 응답 시간 평균 약 6.8초. 가격 조회를 레시피 찾기 결과에 미리 담아 호출을 한 번 줄일지 검토한다. ③ "`@Tool`"이 Spring AI를 뜻한다는 답을 받으면 Tool 실행(`AiFridgeToolExecutor`)은 그대로 두고 호출부만 옮긴다 |
