# 스케줄 작업 정합성 보장 방안

작성일 2026-10-26. 블루그린 겹침 창과 2대 구성에서 스케줄 작업이 두 번 실행돼도 데이터가 틀어지지 않도록, 작업별로 필요한 방법을 정리한다. 팀 합의 전 제안이다.

## 1. 결론

- 분산락(ShedLock, Redis SET NX)은 도입하지 않는다. 락은 TTL이 지나면 풀리므로 정합성을 보장하지 못하고, 결국 작업 자체의 방어가 따로 필요하다.
- 규칙은 방법이 아니라 성질로 정한다. **"스케줄 작업은 여러 인스턴스에서 동시에, 또는 반복해서 실행돼도 결과가 같아야 한다."**
- 방어 수단은 이미 컨벤션에 있는 것만 쓴다. 조건부 상태 전이, 비관적 락 후 상태 재검사, UNIQUE 제약, 외부 호출 전 COMMIT이다.
- 외부 결제가 나가는 멤버십 정기결제만 PortOne 결제 ID를 결정적으로 만들어 외부에도 방어선을 하나 더 둔다.

## 3. 공통 규칙

1. **판정은 사용 시점에, 배치는 정리만.** 만료 여부는 체험 자격 검사, 포인트 사용, 멤버십 조회가 각자 `expires_at`, `expires_on`, `end_at`으로 판정한다. 배치가 늦거나 두 번 돌아도 판정 결과가 같다.
2. **대상 조회와 처리를 나눈다.** 대상 ID 목록은 락 없이 조회하고, 한 건마다 별도 트랜잭션에서 잠근 뒤 상태를 다시 검사한다. 이미 처리된 건은 건너뛴다. 한 트랜잭션에 여러 건을 묶지 않아 락 보유 시간을 짧게 하고, 한 건의 실패가 다른 건을 롤백하지 않게 한다.
3. **건별 실패는 ERROR 로그를 남기고 다음 건으로 넘어간다.** 다음 실행에서 다시 대상이 되므로 따로 재시도 큐를 두지 않는다.
4. **업무 경로와 같은 메서드로 상태를 바꾼다.** 만료·재조회 배치는 결제 확정 API·웹훅이 쓰는 전이 메서드를 그대로 호출한다. 이미 "동시에 들어와도 한 번만 반영"을 지키는 메서드이므로 배치 전용 분기를 만들지 않는다.
5. **외부 호출은 선점을 COMMIT한 뒤 락 밖에서 한다.** 흐름은 `시도 선점 → COMMIT → PortOne 호출 → 결과 반영 트랜잭션`이다.
6. **벌크 DELETE·UPDATE는 행별 업무 처리나 이력이 필요 없는 정리에만 쓴다.** UPDATE면 `updated_at`을 함께 갱신한다(`docs/convention.md` 264행).
7. **시각은 주입한 `Clock`과 `zone = "Asia/Seoul"`로 계산한다.** `AutoCartCleanupScheduler`와 같은 방식이다.

## 4. 작업별 방안

### 4-1. 미확정 자동 장바구니 정리 (구현됨)

- `AutoCartRequestRepository.deleteByStatusAndCreatedAtBefore`가 `status = PREVIEWED AND created_at < :before`를 한 문장으로 지운다.
- 두 번째 실행은 0건을 지운다. 확정과 겹쳐도 확정된 행은 `CONFIRMED`라 조건에서 빠진다.
- **변경 없음.**

### 4-2. TRIAL_BLOCK 만료 기록 삭제

- 배치는 `DELETE FROM trial_block WHERE expires_at < :now` 한 문장이다. 중복 실행은 무해하다.
- 위험은 중복 실행이 아니라 **재탈퇴 연장과의 경합**이다. 만료된 기록을 탈퇴 경로가 읽고 연장하려는 사이에 배치가 지우면, 연장 UPDATE가 0건이 되어 차단 기록이 사라진다.
- 탈퇴 경로의 기록은 `phone_hash` UNIQUE 기준 upsert(`INSERT ... ON DUPLICATE KEY UPDATE expires_at = ...`)로 한다. 행이 지워졌으면 새로 만들어지고, 남아 있으면 연장된다.
- 만료일 유지·연장 판단(요구사항 29행)은 upsert의 UPDATE 절 조건으로 표현한다. 이 부분은 member 담당과 확정한다.
- 체험 자격 검사는 행의 존재가 아니라 `expires_at > now`로 판정한다(공통 규칙 1).

### 4-3. 감사 로그 1년 경과분 삭제

- `created_at < now - 1년` 조건으로 삭제한다. 감사 로그는 추가만 하므로 다른 경로와 경합하지 않고, 중복 실행도 무해하다.
- 한 번에 많이 지우면 긴 트랜잭션과 큰 undo가 생기므로 네이티브 `DELETE ... LIMIT 1000`을 0건이 될 때까지 반복한다. JPQL은 LIMIT을 지원하지 않는다.

### 4-4. 결제 5분 만료

- 지연 큐로 구현하든 1분 주기 폴링으로 구현하든 방어는 같다.
- 대상은 `status = IN_PROGRESS AND expires_at < now`인 PAYMENT ID 목록이다.
- 건마다 기존 잠금 순서 `PAYMENT → ORDERS → MEMBER_POINT → POINT_EARNING → 재고`로 잠그고, `IN_PROGRESS`일 때만 `FAILED(EXPIRED)`로 바꾼다. 주문 `CANCELED(PAYMENT_TIMEOUT)`, 포인트 `RESTORED`, 재고 복구도 같은 트랜잭션에서 한다.
- 이미 `PAID`이거나 `FAILED`면 건너뛴다. 두 번째 실행이나 웹훅과 겹친 실행이 여기서 걸러진다.
- 만료 처리 뒤 늦게 도착한 승인은 웹훅이 `SYSTEM` 환불로 처리한다(요구사항 156행). 만료 배치는 PortOne을 호출하지 않는다.
- 테스트: 같은 결제에 만료 처리와 결제 확정을 동시에 실행해 둘 중 하나만 반영되고 재고가 한 번만 복구되는지 확인한다(동시성 테스트).

### 4-5. 포인트 만료

- 잔액·상태·이력을 함께 바꾸므로 벌크 UPDATE를 쓰지 않는다(`docs/convention.md` 265행).
- 대상은 `status = COMPLETED AND remaining_amount > 0 AND expires_on < 오늘`인 POINT_EARNING ID 목록이다. `expires_on` 당일까지 쓸 수 있으므로 `<`다.
- 건마다 `MEMBER_POINT → POINT_EARNING` 순서로 잠그고 상태와 남은 양을 다시 검사한다. 그다음 `balance -= remaining_amount`, `remaining_amount = 0`, 상태 `EXPIRED`, POINT_HISTORY `EXPIRED`를 한 트랜잭션에서 처리한다.
- 두 번째 실행은 `EXPIRED`라 건너뛰므로 잔액이 두 번 차감되지 않는다.
- 주문 생성의 사용 예약과 취소 시 복원도 같은 행을 잠그므로 경합이 직렬화된다. 복원 시점에 이미 만료된 건은 복원 경로가 `RESTORED` 후 `EXPIRED`로 처리하고, 배치 대상이 되지 않는다(요구사항 424~425행).
- 포인트 사용은 배치 실행 여부와 상관없이 `expires_on >= 오늘`인 적립 건만 쓴다(공통 규칙 1).

### 4-6. 멤버십 정기결제·첫 유료 결제·갱신 재시도·카드 대기 만료

실제 돈이 나가는 유일한 배치라 세 겹으로 막는다.

**① 회차 생성: UNIQUE**
- 청구일이 된 이용권마다 MEMBERSHIP_PAYMENT를 INSERT한다. `UNIQUE(membership_id, period_start_date)`가 같은 회차의 두 번째 행을 막는다.
- 중복 키 오류는 이미 생성된 것으로 보고 건너뛴다.

**② 시도 선점: 조건부 UPDATE**
- 결제를 시도하기 전에 아래 UPDATE를 실행하고, 1건이 바뀐 쪽만 COMMIT한 뒤 PortOne을 호출한다.
  ```sql
  UPDATE membership_payment
     SET status = 'IN_PROGRESS', attempt_count = attempt_count + 1,
         last_attempt_at = :now, updated_at = :now
   WHERE id = :id AND status IN ('READY', 'RETRY_WAITING') AND next_retry_at <= :now
  ```
- 0건이면 다른 인스턴스가 이미 선점한 것이므로 건너뛴다.
- 상태 이름은 결제 도메인의 enum에 맞춘다.

**③ PortOne 결제 ID: 결정적으로 생성**
- `portone_payment_id`를 무작위가 아니라 회차 행에서 계산한다. 예: `mp-{membershipPaymentId}`.
- ①②가 모두 뚫려도 PortOne이 같은 ID의 두 번째 승인을 거절한다.
- ID를 계산할 수 있으므로 선점 후 앱이 죽어 `IN_PROGRESS`로 멈춘 행도 PortOne에서 결과를 조회할 수 있다. 일정 시간이 지난 `IN_PROGRESS`는 `UNKNOWN`으로 보고 4-7의 재조회 대상에 넣는다.
- PortOne V2가 실패한 결제 ID로 재시도를 허용하는지 확인해야 한다. 허용하면 회차당 ID 하나(`mp-{id}`)로 시도 간 이중 승인까지 막는다. 허용하지 않으면 시도마다 `mp-{id}-{attemptCount}`로 바꾸고, 시도 간 방어는 ②가 맡는다.

**결과 반영**
- PortOne 응답 뒤 새 트랜잭션에서 행을 잠그고 `IN_PROGRESS`일 때만 결과를 반영한다. 반영 결과는 `PAID`, 다음 재시도 시각을 정한 `RETRY_WAITING`, 최종 실패, `UNKNOWN` 중 하나다.
- 멤버십 도메인으로 결과를 전달하는 메서드(유료 전환, 일반 전환)는 같은 결과를 두 번 받아도 한 번만 바꾸도록 현재 상태를 검사한다. 결제와 멤버십을 함께 바꾸는 조립은 Facade가 한다.
- 3회 시도 규칙은 `attempt_count`를 선점 UPDATE에서 올리므로 중복 실행으로 시도 횟수가 어긋나지 않는다.
- `PAYMENT_METHOD_REQUIRED` 3일 만료는 시도 없이 상태만 바꾸는 조건부 전이다.

### 4-7. 결과 불명 재조회

- 대상: 결제 `CANCEL_REQUESTED`, 환불 `REQUESTED`, MEMBERSHIP_REFUND `REQUESTED`, MEMBERSHIP_PAYMENT `UNKNOWN`, 4-6의 오래된 `IN_PROGRESS`.
- PortOne 조회는 트랜잭션 밖에서 한다. 반영은 웹훅이 쓰는 전이 메서드로 하고, 그 메서드가 잠금과 상태 재검사를 한다(공통 규칙 4).
- 중복 실행이나 웹훅과 겹친 실행은 PortOne 조회가 한 번 더 일어날 뿐이고, 두 번째 반영은 상태 검사에서 걸러진다.

### 4-8. 해지 예약·체험 만료 후 일반 전환

- 멤버십 조회와 적립률 결정 시점에 `end_at`과 `terminated_at`으로 판정하면 배치가 필요 없다. 이 방식을 권장한다.
- 배치로 상태를 바꿔야 한다면 `UPDATE ... WHERE id = :id AND 현재 상태 = 이용 중 AND end_at <= :now` 조건부 전이로 하고, 중복 실행은 0건이 된다.
- 체험 종료 시 첫 결제는 4-6의 회차 생성으로 처리한다.

## 5. 분산락을 쓰지 않는 이유와 재검토 조건

- 정합성을 지키는 수단은 4절의 행 단위 방어다. 분산락은 이를 대체하지 못한다. 락을 잡은 인스턴스가 TTL보다 오래 걸리거나 GC로 멈추면 다른 인스턴스가 같이 실행된다.
- 4절만으로 중복 실행의 비용은 "대상 조회 한 번 더, 건너뛰기"뿐이다.
- 재검토 조건: 대상 조회 자체가 무거워 두 번 실행되는 부하가 문제로 측정되면 ShedLock(JDBC)을 **부하 절감용으로** 추가한다. 그때도 4절의 방어는 유지한다.

## 6. 테스트

- 각 작업은 같은 대상에 대해 배치를 두 스레드로 동시에 실행하고, 결과가 한 번 실행한 것과 같은지 검증한다.
- 4-4, 4-5, 4-6은 업무 경로(결제 확정·웹훅, 포인트 사용·복원, 멤버십 결과 반영)와 배치를 동시에 실행하는 동시성 테스트를 추가한다.
- 4-6은 PortOne 목이 같은 결제 ID의 두 번째 승인을 거절하는 경우와, 선점 후 PortOne 호출 전에 중단되어 `IN_PROGRESS`가 남는 경우를 검증한다.
