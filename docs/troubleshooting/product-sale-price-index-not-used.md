# 판매가 `CASE` 식 때문에 필터 검색이 가격 인덱스를 쓰지 못한다

| 항목 | 내용 |
| --- | --- |
| 제목·담당자·발생일 | 판매가 식과 가격 인덱스 · 태헌 · 2026-11-05 |
| 영향 범위 | 카테고리·가격 범위·가격순 정렬을 쓰는 상품 검색(`searchMemberProducts`). 인덱스의 범위·정렬 대신 그 카테고리의 행(약 2,400~2,500건)을 모두 읽은 뒤 거르고 정렬한다. 로컬 시연 데이터(상품 약 660건)와 같은 규모에서는 체감 영향이 없다. 운영 DB의 상품 수는 확인하지 못했다 |
| 관련 이슈·PR·커밋 | #494(할인·판매가), #522·PR #523(재측정), #252·PR #527(원인 후보 기록) |
| 처리 상태 | 후속 작업(보류): 단독 실행 계획으로 원인 후보를 확인했고 코드는 바꾸지 않았다. 부하 상태의 영향은 확인하지 않았다 |

## 1. 증상

- 기대한 동작과 실제 동작: 인덱스 개선(`idx_product_mart_category_price_asc` 등) 뒤 필터 검색은 단독 약 1ms대여야 하는데, 2026-11-05 최신 `dev`로 다시 잰 부하 결과에서 After가 10월보다 느렸다.
- 발생 환경·재현 조건: 로컬 `recipick_perf`(상품 100,661건), k6 100명, 같은 시나리오(`scripts/perf/k6/product-search.js`) 3단계 각 3회 중앙값.
- 재현 명령·요청·순서: `scripts/perf/explain-product-search.sql`의 3번(현재 코드 모양)과 4번(`price` 컬럼을 직접 쓰는 이전 모양)을 `EXPLAIN ANALYZE`로 비교한다.
- 핵심 관찰 결과

| 항목 | 10월 | 11/05 재측정 |
| --- | --- | --- |
| 필터 검색 p95(인덱스 후) | 135ms | 369ms |
| 전체 p95(인덱스 후) | 264ms | 492ms |
| 전체 p95(캐시 후) | 19.8ms | 45.7ms |
| 키워드 검색 p95(인덱스 후) | 306ms | 548ms |

## 2. 원인

| 가설 | 확인 방법 | 관찰 결과·판정 |
| --- | --- | --- |
| #494의 판매가 `CASE` 식이 `price` 인덱스의 범위·정렬을 막는다 | 같은 필터 쿼리를 `CASE` 식 모양(3번)과 `price` 직접 모양(4번)으로 단독 `EXPLAIN ANALYZE`(두 번째 실행 값) | 목록 5.5ms 대 0.46ms, 개수 5.4ms. `CASE` 모양은 `(mart_id, category_id, deleted)`까지만 인덱스를 타고 카테고리 행 2,397건을 모두 읽는다. 단독 실행에서는 확인됨 |
| 코드 변경·실행 방식·PC 상태가 다르다(이번은 JAR로 실행했고 같은 PC에서 다른 프로그램이 켜져 있었다. 10월과 같다는 보장이 없다) | 같은 날 Before부터 3단계를 이어서 측정 | 같은 날 단계 사이 비교는 유효하지만 10월 값과는 직접 비교할 수 없다. 영향 정도는 못 갈랐다 |
| 키워드 검색도 느려졌다 | 키워드 검색은 판매가 식과 무관한 경로 | 위 원인으로 설명되지 않는다. 원인 미확정 |

확인된 원인: 판매가 식은 실행 계획에서 인덱스를 못 쓰게 한다는 점까지 확인했다. 그것이 부하 상태의 지연을 얼마나 키웠는지는 확인하지 않았다. 지금 데이터에는 `discount_rate > 0`인 행이 0건이라 이 식은 결과를 바꾸지 않고 실행 계획만 바꾼다.

## 3. 해결

- 바꾼 내용과 이유: 이번에는 코드를 바꾸지 않았다. 시연 데이터 규모에서는 영향이 작고 발표(11/12)·시연(11/13)을 앞두고 있어 쿼리 변경 위험이 이득보다 크다고 판단했다.
- 다른 대안을 선택하지 않은 이유: 후보 두 가지는 효과를 단독 실행 계획으로 먼저 확인해야 한다.
  - 가격 조건을 "할인 중인 상품 / 아닌 상품"으로 나눠 아닌 쪽이 `price` 인덱스를 타게 한다. 코드 변경이 작지만 정렬은 여전히 계산이 필요할 수 있다.
  - 판매가를 컬럼으로 저장한다. 가장 빠르지만 할인 종료 시각이 지나면 값이 달라져 갱신 장치가 필요하고 변경 범위가 크다.
- 변경 코드·설정·문서: [`ProductRepositoryImpl.salePrice`](../../src/main/java/com/recipick/domain/product/repository/ProductRepositoryImpl.java), [재현 스크립트](../../scripts/perf/explain-product-search.sql), [병목 개선 5-1절](../performance/product/bottleneck.md), [선택 근거 3-10절](../adr/product-domain.md)
- 기존 데이터·운영에 필요한 조치: 없음

## 5. 재발 방지와 남은 작업

- 추가한 테스트·알림·문서·규칙: 재현 스크립트와 선택 근거 문서(재검토 조건)에 남겼다. 조건·정렬에 계산 식을 넣는 변경은 `EXPLAIN`으로 인덱스 사용 여부를 먼저 확인한다.
- 남은 제한과 담당 이슈: 할인 상품이 늘거나 가격 검색이 느려지면 위 두 후보를 단독 실행 계획으로 비교한 뒤 정한다. 이슈는 만들지 않았다.
- 다른 팀원에게 공유할 적용 방법: 인덱스가 있는 컬럼에 함수·`CASE`를 씌워 조건이나 정렬에 쓰면 인덱스를 못 쓰는 경우가 있으므로, 단독 `EXPLAIN ANALYZE`로 먼저 확인한다.
