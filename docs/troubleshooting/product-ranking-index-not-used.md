# 순위 인덱스를 만들었는데 옵티마이저가 쓰지 않았다

| 항목 | 내용 |
| --- | --- |
| 제목·담당자·발생일 | 베스트 상품 순위 인덱스 미사용 · 태헌 · 2026-11-04 |
| 영향 범위 | 베스트 상품 조회(`findBestSellingProductIds`)의 30일·전체 구간 성능. 동작과 결과는 정상 |
| 관련 이슈·PR·커밋 | #453, PR (생성 후 번호 기입) |
| 처리 상태 | 후속 작업(인덱스는 유지, 30일·전체 구간은 개선하지 않음) |

## 1. 증상

- 기대한 동작과 실제 동작: 인덱스 `idx_orders_mart_id_status_paid_at(mart_id, status, paid_at)`를 만들면 쿼리가 빨라지고 `EXPLAIN`에 새 인덱스가 보여야 하는데, 30일 구간에서는 계획이 인덱스 생성 전과 같았다.
- 발생 환경·재현 조건: 로컬 `recipick_perf`(MySQL 8.4), 결제 완료 주문 90,000건(전체 100,010건), 주문 상품 300,047건, 마트 1, 최근 30일.
- 재현 명령: `EXPLAIN ANALYZE`로 `orders`와 `order_item`을 조인해 상품별 판매량을 합산하는 쿼리를 실행한다(저장소 쿼리와 같은 조건).
- 관찰 결과: 인덱스 생성 후에도 `idx_orders_mart_id_mart_status (mart_id=1)`로 주문 90,004행을 읽은 뒤 상태·기간으로 40,060행만 남겼다. 시간 차이(773ms → 596ms)는 인덱스 효과가 아니라 캐시가 데워진 영향이었다.

## 2. 원인

| 가설 | 확인 방법 | 관찰 결과·판정 |
| --- | --- | --- |
| 쿼리에 쓴 사용자 변수(`@from`) 때문에 범위 검색을 못 한다 | 날짜를 `DATE_SUB(NOW(), INTERVAL 30 DAY)`로 직접 넣어 실행 | 같은 계획이라 아님 |
| 새 인덱스에 문제가 있다 | `FORCE INDEX`로 강제 | `Covering index range scan`으로 40,059행만 읽었고 주문 필터 단계가 303ms → 62ms, 전체 1,040ms → 549ms로 줄었다. 인덱스는 정상 |
| 옵티마이저가 구간에 따라 다르게 고른다 | 기간별로 `IGNORE INDEX`, 힌트 없음, `FORCE INDEX` 비교 | 24시간·7일은 새 인덱스를 골랐고 30일·전체는 고르지 않았다 |

확인된 원인: 옵티마이저는 새 인덱스를 쓸 때 약 49,622행을 읽는다고 추정했다(강제 시 계획의 `rows=49622`, `cost=10578`). 기존 인덱스 경로의 추정 비용(`cost=816`)보다 커서 고르지 않았다. 30일 구간은 주문의 약 44%, 전체는 거의 전부를 읽어야 해서 범위가 넓다. 전체는 강제로 쓰면 1,624ms로 오히려 느려져서 옵티마이저가 안 쓰는 쪽이 더 빨랐다. 추정 행 수가 왜 이렇게 나오는지(통계, 히스토그램)는 확인하지 못했다.

## 3. 해결

- 바꾼 내용과 이유: 코드는 바꾸지 않았다. 인덱스는 유지한다. 24시간 구간이 455ms → 17.6ms로 약 26배 빨라지고, 다른 구간에서 느려지지는 않았다.
- 다른 대안을 선택하지 않은 이유
  - `FORCE INDEX` 힌트: JPQL로 쓴 쿼리에는 넣을 수 없고, 전체 구간은 강제하면 더 느리다.
  - 히스토그램·캐시·집계 테이블: 시도하지 않았다. 순위 화면이 실제로 느려질 때 검토한다고 ADR에 적었다.
- 변경 코드·설정·문서: [상품 ADR](../adr/product-domain.md) 5절 "순위 인덱스 측정 상세"
- 필요한 조치: 없음

## 4. 검증 결과

| 확인 항목 | 실행 방법 | 수정 전(인덱스 막음) | 수정 후(힌트 없음) | 근거 |
| --- | --- | --- | --- | --- |
| 24시간 | `EXPLAIN ANALYZE`, 1회 | 455ms | 17.6ms | 새 인덱스 사용 |
| 7일 | 같음 | 274ms | 208ms | 새 인덱스 사용(강제 119ms) |
| 30일 | 같음 | 608ms | 552ms | 사용 안 함 |
| 전체 | 같음 | 1,185ms | 936ms | 사용 안 함(강제 1,624ms) |

기간별 값은 1회 측정이다. 30일 구간을 3회 재면 Before 657~995ms, After 543~680ms로 겹쳐서, 24시간 구간만 차이가 뚜렷하다고 판단한다.

## 5. 재발 방지와 남은 작업

- 추가한 문서: ADR 5절의 기간별 표와 4절 "감수하는 비용"에 30일·전체가 0.5~0.9초라는 점을 적었다.
- 남은 제한: 주문 10만 건에서 30일·전체 순위는 0.5~0.9초다. 순위 화면이 느려지면 순위 캐시나 집계 테이블을 검토한다(ADR 4절 "다시 검토할 조건"). 찜 순위 인덱스는 레시피가 100개뿐인 시드라 효과를 입증하지 못했다(17.8ms → 18.8ms).
- 공유할 적용 방법: 새 인덱스를 추가하면 `EXPLAIN ANALYZE`에서 실제로 쓰이는지 기간(데이터 범위)별로 확인한다. `IGNORE INDEX`와 `FORCE INDEX`로 비교하면 인덱스 문제인지 옵티마이저 선택 문제인지 가를 수 있다.
