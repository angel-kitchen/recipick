# 요청 수 제한 부하 테스트: 로컬에서 서로 다른 IP를 만들 수 없었다

| 항목 | 내용 |
| --- | --- |
| 제목·담당자·발생일 | 요청 수 제한 테스트의 클라이언트 IP 구분 · 태헌 · 2026-11-04 |
| 영향 범위 | 로컬 부하 측정 방법. 앱 코드는 바뀌지 않았다 |
| 관련 이슈·PR·커밋 | #453, PR #456 |
| 처리 상태 | 해결(측정 방법 변경) |

## 1. 증상

- 기대한 동작과 실제 동작: 일반 회원 20명이 서로 다른 IP로 접속한 것처럼 보여야 하는데, 앱에는 모두 한 IP로 찍혀 한도에 걸렸다.
- 발생 환경·재현 조건: Windows 11 단일 PC, 요청 수 제한 켬(`api` 120/분, `auth` 10/분), 호스트에 설치한 k6(v2.2.0).
- 재현 순서: 일반 회원이 `127.0.0.11`~`127.0.0.30`으로 접속하도록 시나리오를 짜고 실행한다.
- 관찰 결과
  - 측정 요청을 하나도 보내지 못하고 끝났다(일반 회원 요청 0건).
  - Redis 키가 `recipick:rate:auth:127.0.0.1` 하나뿐이었고 값이 **11**이었다. 로그인 한도(10)를 넘은 값이다.

## 2. 원인

| 가설 | 확인 방법 | 관찰 결과·판정 |
| --- | --- | --- |
| 접속 주소를 `127.0.0.x`로 바꾸면 앱에도 그 주소로 보인다 | 요청 수 제한을 켠 채 실행하고 Redis 키 조회 | 틀렸다. 20명의 로그인이 모두 `127.0.0.1` 키로 합쳐졌다 |
| Docker의 k6도 모든 요청이 같은 IP로 보인다 | 직접 실행해 보지는 않았다 | 추정이다. 컨테이너 요청이 Docker Desktop을 거쳐 한 주소로 보일 것이라고 보고 쓰지 않았다 |
| 앱이 `X-Forwarded-For`를 읽게 하면 구분된다 | `SERVER_FORWARD_HEADERS_STRATEGY=native`로 앱을 띄우고 k6가 회원마다 다른 헤더를 보냄 | 맞다. 키가 `10.0.0.12`, `10.0.0.13`… 으로 나뉘었다 |

확인된 원인: `RateLimitFilter`는 `request.getRemoteAddr()`만 쓴다(`global/filter/RateLimitFilter.java`). Windows는 루프백 접속의 출발 주소를 `127.0.0.1`로 고정해서 접속 주소를 바꿔도 앱이 보는 IP가 같다. 로컬 `application-local.yml`에는 `forward-headers-strategy`가 없고, 운영(`application-prod.yml`)에만 `native`가 있다.

## 3. 해결

- 바꾼 내용과 이유: 앱을 운영과 같은 `forward-headers-strategy: native`로 띄우고(환경변수 `SERVER_FORWARD_HEADERS_STRATEGY=native`), k6의 일반 회원은 회원마다 다른 `X-Forwarded-For`(`10.0.0.11`~)를 보내고 악성 IP는 헤더 없이 `127.0.0.1`로 보내게 했다. 프록시가 보낸 헤더를 실제 클라이언트 IP로 읽는 운영 방식과 같다.
- 다른 대안을 선택하지 않은 이유: PC에 IP를 여러 개 붙이는 방법은 환경 설정이 커져 팀원이 재현하기 어렵다고 보고 택하지 않았다(시도하지 않았다).
- 변경 코드·설정·문서: `scripts/perf/k6/rate-limit-abuse.js`(머리 주석에 이유 기록), [요청 수 제한 보고서](../performance/product/rate-limit.md) 5절 "측정 조건과 한계"
- 필요한 조치: 없음. 앱 코드와 설정 파일은 바뀌지 않았다.

## 4. 검증 결과

| 확인 항목 | 실행 방법 | 수정 전 | 수정 후 | 근거 |
| --- | --- | --- | --- | --- |
| IP 구분 | 실행 후 Redis `recipick:rate:*` 키 조회 | `auth:127.0.0.1` 하나(값 11) | `api:10.0.0.12`…`10.0.0.30`과 `api:127.0.0.1`로 분리 | 예열 회차의 Redis 키 목록 |
| 일반 회원 영향 | k6 결과 | 요청 0건 | 요청 1,400건 이상, 429 0건 | 측정 5회 |
| 악성 IP 차단 | k6 결과 | 해당 없음 | 약 8만 건 중 약 99.7%가 429, 통과 240건(분당 120건 × 2구간) | 같음 |

## 5. 재발 방지와 남은 작업

- 추가한 문서: 시나리오 머리 주석과 요청 수 제한 보고서에 방법과 이유를 적었다.
- 남은 제한: 이 방법은 앱이 `X-Forwarded-For`를 믿는 상태에서만 동작한다. 운영에서 프록시가 클라이언트가 보낸 이 헤더를 덮어쓰는지는 확인하지 못했다. 덮어쓰지 않으면 헤더 위조로 제한을 우회할 수 있고, 이 측정이 그 가능성을 보여 준다(보고서 7절, ADR 6절의 기존 확인 항목).
- 공유할 적용 방법: 요청 수 제한을 로컬 k6로 재려면 앱을 `SERVER_FORWARD_HEADERS_STRATEGY=native`로 띄우고 `rate-limit-abuse.js`를 호스트에서 실행한다.
