# 커밋 후 캐시 삭제가 Redis 장애를 API 실패로 만들 수 있었다(`transactionAware`)

| 항목 | 내용 |
| --- | --- |
| 제목·담당자·발생일 | 커밋 후 캐시 처리의 Redis 오류 전파 · 태헌 · 2026-10-28 |
| 영향 범위 | 카테고리·마트 변경 API. Redis가 멈추면 DB 변경은 성공했는데 응답이 실패할 수 있었다. 머지 전 리뷰에서 발견했다 |
| 관련 이슈·PR·커밋 | #229, PR #237, `ce91c19`(추가), `e52a9a4`(제거) |
| 처리 상태 | 해결(옵션을 쓰지 않기로 결정). 이론상의 경합은 감수 |

## 1. 증상

- 기대한 동작과 실제 동작: Redis 장애 시에도 캐시 오류는 무시하고 DB로 처리해야 한다(`CacheErrorHandler`). 그런데 커밋 후 캐시 삭제에서 난 오류는 이 처리기를 거치지 않는다.
- 발견 경로: 캐시 삭제가 DB 커밋보다 먼저 실행되는 경합을 막으려고 `transactionAware()`를 추가했고(`ce91c19`), PR #237 리뷰(CodeRabbit, Major)가 이 옵션의 부작용을 지적했다.
- 리뷰 지적 요지: `transactionAware()`는 캐시 저장·삭제를 `afterCommit`으로 미루고, 이때 난 Redis 예외는 `CacheErrorHandler`를 거치지 않고 호출자에게 전파된다.
- 재현: 실제로 Redis를 끄고 호출해 보지는 않았다.

## 2. 원인

| 가설 | 확인 방법 | 관찰 결과·판정 |
| --- | --- | --- |
| 커밋 후 처리가 오류 처리기를 우회한다 | 리뷰가 가리킨 `TransactionAwareCacheDecorator`의 동작 확인 | 리뷰 지적과 같은 동작이라 판단했다 |

확인된 원인: 캐시 삭제를 트랜잭션 커밋 뒤로 미루는 `transactionAware()`는 그 시점의 예외를 `CacheErrorHandler`가 잡지 못해, DB는 이미 커밋됐는데 API가 실패로 끝날 수 있다. "Redis 장애에도 서비스는 계속"이라는 설계(`fail-to-DB`)와 어긋난다.

## 3. 해결

- 바꾼 내용과 이유: `transactionAware()`를 제거했다(`e52a9a4`, `CacheConfig.java` 1줄 삭제). 읽기 캐시에서는 약간 오래된 값을 허용하고 가용성을 우선했다.
- 다른 대안을 선택하지 않은 이유: `transactionAware()`는 삭제 뒤 옛 값이 다시 저장되는 경합을 막지만, 그 대가가 Redis 장애 시 API 실패라서 택하지 않았다.
- 감수한 위험: 캐시 삭제가 커밋보다 먼저 실행되므로, 그 사이 들어온 조회가 옛 값을 다시 저장하는 경합이 이론상 가능하다. 오래된 값이 남는 상한은 TTL이다(카테고리 10분, 마트 5분). Redis 장애로 삭제가 실패해도 같은 상한이다.
- 변경 코드·설정·문서: [`CacheConfig`](../../src/main/java/com/recipick/global/config/CacheConfig.java), [캐싱 보고서](../performance/product/caching.md) 한계 절, [상품 ADR](../adr/product-domain.md) 3-2
- 필요한 조치: 없음

## 4. 검증 결과

| 확인 항목 | 실행 방법 | 수정 전 | 수정 후 | 근거 |
| --- | --- | --- | --- | --- |
| Redis 오류 무시 | `CacheErrorHandlerTest`(단위) | - | 통과 | 오류 처리기 단위 테스트만 확인 |
| 실제 Redis 장애 | 실제로 Redis를 끄고 호출 | - | 확인하지 않았다 | PR #237 본문, ADR 6절 "확인이 필요한 차이" |

## 5. 재발 방지와 남은 작업

- 추가한 문서: 캐싱 보고서에 선택과 감수한 위험을 적었다.
- 남은 제한: 옛 값 경합은 TTL 안에서 허용하기로 했다. Redis를 실제로 끄고 호출하는 확인은 남아 있다(ADR 6절).
- 공유할 적용 방법: Spring Cache에 커밋 후 처리 옵션을 켤 때는 그 시점의 예외가 오류 처리기를 거치는지 먼저 확인한다.
