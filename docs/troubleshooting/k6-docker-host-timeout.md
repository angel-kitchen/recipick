## 1. 증상

첫 Docker k6 혼합 측정은 HTTP 58,961건 중 상품 상세 1건이 15초 뒤 `HTTP 0`으로 실패했다. p95 약 32ms·실패율 1% 미만 기준은 충족했지만 이 한 건의 원인을 확인할 자료가 부족했다. 서버 종료 정합성 검사는 통과했다.

상품 상세를 추가로 10 VU·30초 조회했을 때는 2,440건이 모두 성공했다. 단순 조회 재실행 성공을 원인 해결로 보지 않고 진단을 보강했다.

## 2. 가설과 확인

| 가설 | 관찰 | 판정 |
| --- | --- | --- |
| 상품 상세 코드가 15초 걸림 | 첫 실패 분의 전체 서버 완료 요청은 최대 73ms, 해당 상품 완료 기록은 8~15ms | 완료 기록에서 15초 처리 지연은 확인하지 못함. 네트워크·처리 전 대기를 배제하는 근거는 아님 |
| DB 연결 풀 타임아웃 | 전후 연결 획득 타임아웃 0, 재현 시점 샘플에서도 대기 0 | 이 실패를 DB 풀 타임아웃으로 단정할 증거 없음 |
| 긴 GC 정지 | 첫 측정의 일반 GC 정지 합계 증가 약 0.304초 | 15초 GC 정지를 뒷받침하지 않음. 전후 스냅샷만으로 모든 순간 지연을 설명할 수는 없음 |
| 연결 교체 경계 | 진단 재측정 실패 5건은 각 VU의 201·501·801번째 요청 | 새 연결 구간과의 연관성 가설. 순번만으로 원인 확정하지 않음 |
| 로컬 Docker→호스트 새 연결 경로 | 같은 상품·k6 버전의 새 연결 비교에서 Docker 53건 실패, 호스트 0건 실패 | 실행 경로와 재현 여부를 분리함. 특정 Docker 구성 요소의 결함까지 확정한 것은 아님 |

호스트의 직접 HTTP 연결을 관찰했을 때 서버는 100·200번째 요청에서 정상 `Connection: close`를 반환했다. [Tomcat HTTP Connector 문서](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)의 keep-alive 연결 제한과 부합하는 관찰이지만, 서버의 정상 연결 종료 자체가 결함이라는 뜻은 아니다.

## 3. 추가한 진단과 대응

- 실패한 요청에 고정 API 이름·VU·반복·시작/종료 UTC 시각·전체 대기 시간·오류 코드·단계별 timings를 남겼다. URL·검색어·본문·인증 정보는 남기지 않았다.
- `X-Perf-Request-Id`를 보내고 성능 앱에서만 Tomcat 접근 로그에 기록했다. 응답이 있으면 서버 `X-Request-Id`도 대조한다.
- CPU·GC·DB 풀·Tomcat 스레드·HTTP 지표를 5초마다 수집했다. 수집 실패도 샘플로 보존한다.
- 전체 대기 `request_wall_time`을 추가해 HTTP 단계별 timings가 0이어도 실제로 기다린 15초를 숨기지 않게 했다.

진단 재측정에서는 5건 모두 약 15초 뒤 `HTTP 0 / error_code 1050`, 단계별 timings 0, 응답 요청 ID 없음으로 끝났다. 동일 클라이언트 ID의 완료 접근 로그도 없었다. 샘플 79개는 모두 수집됐고 실패 시점 DB 대기·타임아웃은 0이었다. 연결 전·중·서버 처리 전 대기 중 어디인지는 이 자료만으로 특정하지 않는다.

서버 코드·15초 제한·연결 재사용 기본값을 바꾸는 대신 같은 k6 1.3.0의 호스트 실행을 비교했다. 호스트 k6는 공식 릴리스의 macOS arm64 파일을 받고 공식 SHA-256 체크섬을 확인했다. 로컬 검증은 호스트 k6로 진행하되 운영은 별도로 검증한다.

## 4. 검증 결과

| 점검 | 요청·결과 | 해석 |
| --- | --- | --- |
| Docker 진단 혼합 100 VU | HTTP 57,706건 중 타임아웃 5, 정리 실패 1, 쓰기 건너뜀 23, 장바구니 잔여 1 | 정리 기준 초과로 실패. 평균·p95가 낮다는 이유로 통과 처리하지 않음 |
| Docker 연결 재사용, 상품 10 VU | 상세 3,500건 모두 성공 | 짧은 읽기 점검에서 미재현 |
| Docker 매번 새 연결, 상품 10 VU | 상세 3,500건 중 53건 타임아웃 | 연결 재사용 해제는 이 환경에서 해결책이 아님 |
| 호스트 k6 매번 새 연결, 상품 10 VU | 상세 3,500건 모두 성공 | 같은 앱을 호스트에서 직접 호출할 때 미재현 |
| 호스트 k6 혼합 100 VU | HTTP 58,199건 모두 성공, 차단·정리 실패·쓰기 건너뜀 0 | 시나리오 및 종료 정합성 통과 |

상품 비교의 HTTP 합계는 로그인 1건을 더한 각 3,501건이다. 요청 도구는 같은 버전이지만 OS·네트워크·자원 사용은 달라서 응답 속도의 개선율을 계산하지 않는다. 호스트 혼합 실행은 같은 생성 규칙의 새 DB·Redis에서 검증했고, 이전 실패 데이터는 덮어쓰지 않았다.

## 5. 재발 방지와 남은 작업

- 실행 도구 버전·Docker/호스트 위치·앱 커밋·DB·캐시 조건을 회차마다 기록한다. 타임아웃을 늘리거나 무조건 재시도해 실패를 숨기지 않는다.
- 기준은 실패율뿐 아니라 `blocked_writers`·`cleanup_failed`·`skipped_writes`도 함께 확인한다. 이번 정리 실패는 잔여 장바구니와 함께 별도 DB에 보존했다.
- 동일 시간대 요청 ID·클라이언트 timings·서버 지표를 먼저 대조한다. 접근 로그는 완료 요청만 보여주고 5초 샘플도 순간 지연을 놓칠 수 있다.
- Docker 내부 원인을 더 밝혀야 할 경우 네트워크 추적 등 별도 진단이 필요하다. 현재 결과만으로 앱 버그나 Docker 내부 구성 요소의 결함을 확정하지 않는다.
- 운영 HTTPS·프록시·외부 PG·AWS 부하는 이번 로컬 검증과 분리한다.

원본은 gitignore 대상 `scripts/perf/results/local-mixed-100-2026-11-03/`, `local-mixed-100-diagnostics-2026-11-03/`, `local-native-100-2026-11-03/`에 나눠 보관한다. 배포·제출 근거로 공유할 때는 비밀 값과 개인정보 포함 여부를 먼저 확인한다.


## 6. 2026-11-04 추가 조사

[추가 점검 요약](../performance/results/docker-network-isolation-2026-11-04.json)을 별도로 보관했다. 다음 점검은 모두 새 연결을 만드는 읽기 전용 비교이며 기존 100명 혼합 측정과 구분한다.

| 조건 | HTTP 요청 | 실패 |
| --- | ---: | ---: |
| Docker→Java, 기본 DNS | 3,501(로그인 1 포함) | 56 |
| Docker→Java, 호스트 IPv4 고정 | 3,501(로그인 1 포함) | 84 |
| Docker→단순 HTTP 서버, 호스트 IPv4 고정 | 3,500 | 36 |
| Docker→단순 HTTP 서버, PC 내부 IP 직접 지정 | 3,500 | 60 |

1,000회 단순 서버 및 1,000회 Java 조회에서는 각각 실패가 없었으나 3,500회 조건에서 재현돼 짧은 미재현만으로 해결로 판단하지 않았다. DNS 우회와 내부 IP 직접 연결에서도 실패했으므로 DNS 이름 해석만의 문제라는 가설은 지지되지 않는다. Java·DB가 없는 단순 HTTP 서버에서도 컨테이너 TCP 소켓의 SYN_SENT와 재전송을 확인했으므로 HTTP 업무 처리 전 TCP 연결 수립에서 지연이 재현된 것은 확인했다. 같은 소켓을 여러 시점에 관측한 것이므로 소켓 샘플 수를 실패 요청 수로 해석하지 않는다.

이는 SYN이 어느 지점에서 손실되거나 응답이 전달되지 않았는지를 특정한 결과는 아니다. Docker Desktop 4.86.0의 내부 네트워크 상태·VM 전달 경로·호스트 네트워크 영향 중 원인을 더 좁히려면 추가 분리가 필요하다. 현재까지 프로젝트의 상품 조회·SQL을 수정할 근거는 없다.

아래와 같이 Docker Desktop 정상 재시작까지 비교했으나 재현됐다. 추가 원인 조사는 실패 시점의 컨테이너·호스트 양쪽 패킷을 대조하는 작업으로 남긴다. 다른 PC와 운영 서버에서는 같은 조건을 측정하지 않았으므로 동일 증상이 발생한다고 일반화하지 않는다. 로컬 부하 결과는 정상 완료한 호스트 k6 실행을 기준으로 사용한다. 업데이트·초기화의 해결 효과는 확인하지 않았으며 컨테이너·볼륨 삭제는 수행하지 않았다.


### Docker Desktop 재시작 전후

사용자 동의를 받아 Docker Desktop을 정상 재시작했다. 실행 중이던 컨테이너 5개를 기록하고 복구했으며 볼륨 동일성을 확인했다. 개발 MySQL의 동적 게시 포트가 바뀌어 gitignore 대상 로컬 설정과 개발 백엔드 연결을 복구했다. 운영 설정·추적되는 애플리케이션 설정·데이터·볼륨은 초기화하지 않았다.

재시작 전과 같은 Java 서버·기본 DNS·새 연결 3,500건 조건에서 로그인 포함 3,501건 중 30건이 다시 타임아웃됐다. 따라서 정상 재시작만으로 해결됐다고 판단할 수 없다. 재시작 전 56건과 후 30건의 차이를 성능 개선으로 해석하지 않는다. 개발 백엔드 공개 API와 성능 서버 health는 모두 200을 확인했다.
