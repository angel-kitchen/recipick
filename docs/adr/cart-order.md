# 장바구니·주문 설계 결정과 검증 결과

장바구니는 회원 행 잠금 + 행 단위 조건부 UPDATE + UNIQUE 제약으로, 주문 생성은 회원 행 잠금 + 멱등 키 + 결제 대기 1건 제한으로 중복을 막습니다.
주문·결제·포인트·재고는 Facade가 한 DB 트랜잭션에서 동기 호출하고, 주문 종료와 재고 복구는 결제 도메인의 트랜잭션 안에서만 호출됩니다.
결제 완료 후 장바구니 정리처럼 잠깐 어긋나도 되는 후처리만 커밋 뒤 이벤트로 분리합니다.

## 사용 기술 한눈에 보기

각 기술이 하는 일과 고른 이유를 한 줄로 적었습니다. 후보 비교와 감수한 비용은 오른쪽 열의 절에 있습니다.

| 영역 | 기술 | 하는 일 | 고른 이유 | 자세히 |
| --- | --- | --- | --- | --- |
| 잠금 | 회원 행 `PESSIMISTIC_WRITE` | 담기·주문 생성의 첫 DB 작업으로 회원을 잠금 | 탈퇴와 직렬화해 탈퇴 뒤 장바구니·주문이 남지 않게 함. 같은 회원의 동시 요청도 한 줄로 세움 | D2, D5 |
| 잠금 | 주문 행 `PESSIMISTIC_WRITE`(`findByIdForUpdate`) | 결제 결과·수락·거절·배송 변경 전에 주문을 잠그고 상태 확인 | 겹치는 요청 중 한쪽만 성공. 낙관적 락은 컨벤션상 금지 | D10~D12 |
| 원자 연산 | 조건부 UPDATE | `quantity + n <= min(99, 재고)`일 때만 합산 | 읽고 더한 뒤 저장하는 갱신 유실 방지 | D2 |
| 제약 | UNIQUE `cart_item(member_id, product_id)` | 회원·상품당 장바구니 한 행 | 첫 담기 중복의 최종 방어 | D2 |
| 제약 | UNIQUE `orders(member_id, idempotency_key)` | 같은 키의 주문 1건 | 주문과 같은 행·같은 트랜잭션이라 Redis 캐시와 달리 원자적 | D6 |
| 제약 | nullable UNIQUE `orders.pending_member_id` | 회원당 결제 대기 주문 1건 | 조회만으로는 동시 요청이 함께 통과. NULL은 여러 개 허용돼 종료 주문은 쌓임 | D7 |
| 멱등성 | `Idempotency-Key` + SHA-256 요청 해시 | 같은 키·같은 본문이면 기존 주문 반환, 본문이 다르면 `COMMON-011` | 연타·재시도에도 주문·재고 차감·결제는 한 번 | D6 |
| 트랜잭션 | `Propagation.MANDATORY` | 주문 종료·재고 복구·배송 변경을 바깥 트랜잭션 안에서만 호출 | 따로 커밋되면 종료만 반영되고 재고 복구·적립 확정이 빠질 수 있음 | D11, D12 |
| 후처리 | `@TransactionalEventListener(AFTER_COMMIT)` + `NOT_SUPPORTED` | 결제 커밋 뒤 장바구니에서 결제 수량만 차감 | 장바구니 실패가 승인된 결제까지 롤백하지 않게 함. `@Async`는 쓰지 않음 | D13 |
| 금액 | `OrderAmount` 한 곳 | 배송비·포인트 한도·결제금액 계산 | 미리보기와 생성이 같은 계산. 포인트 한도는 재고를 잠근 뒤의 가격으로 판정 | D9 |
| 식별자 | `yyyyMMdd-` + SecureRandom 10자리 | 사용자 표시용 주문번호 | 순번이면 주문량이 드러나고 다른 주문번호를 추측할 수 있음 | D8 |
| 감사 | `AdminAuditRecorder`(같은 쓰기 트랜잭션) | 관리자 목록·상세 조회·수락·거절·배송 변경 기록 | 기록 실패 시 업무도 롤백(컨벤션) | D12 |

## 1. 상황

회원은 이용 마트의 상품을 장바구니에 담고, 그중 일부를 골라 주문합니다. 주문은 결제(PortOne 또는 포인트 전액 결제)가 끝나야 마트로 넘어가고,
마트는 결제 완료 주문을 수락하거나 거절한 뒤 배송중·배송완료로 바꿉니다. 결제·주문·재고·포인트·멤버십이 서로 다른 도메인이라 한 흐름이 여러 도메인을 함께 바꿉니다.

- 요청 흐름: 장바구니 담기 → 주문 미리보기 → 주문 생성(포인트 예약·재고 차감·결제 생성) → 결제 확정·웹훅·5분 만료 → 장바구니 정리 → 마트 수락·거절 → 배송중 → 배송완료(적립 확정) / 취소·환불
- 일관성 제약
  - 버튼 연타·네트워크 재시도로 같은 주문 요청이 여러 번 와도 주문·재고 차감·포인트 예약·결제는 한 번만 생겨야 합니다.
  - 결제 실패·만료·환불 결과가 결제 확정 API·웹훅·만료 큐로 반복·동시에 전달돼도 재고·포인트는 정확히 한 번만 복구돼야 합니다.
  - 마트 수락·거절과 회원 취소가 같은 주문에 겹쳐도 한쪽만 성공해야 합니다.
  - 배송완료가 반복돼도 포인트는 한 번만 적립돼야 합니다.
  - 회원 탈퇴와 주문 생성·장바구니 담기가 겹쳐도 탈퇴한 회원의 주문·장바구니가 남거나 재고가 빠지면 안 됩니다.
  - 장바구니 정리 같은 부가 처리가 실패해도 이미 PG에서 승인된 결제 확정이 롤백되면 안 됩니다.
- 운영 제약: 앱 서버 여러 대를 전제로 JVM 락은 쓰지 않습니다. 컨벤션상 낙관적 락·`NOWAIT`·`REQUIRES_NEW`는 쓰지 않습니다.
- 해결됐다고 판단할 기준: 위 경합을 동시성 테스트로 재현해 주문 1건·재고 1회 차감·1회 복구·적립 1회·이력 1건이 지켜지는 것

## 3. 결정별 상황·후보·선택

### 3-1. 장바구니 항목의 마트 판단 (D1)

| 후보 | 장점 | 비용·한계 |
| --- | --- | --- |
| `CART_ITEM.mart_id` 저장 | 조회 시 상품 조인 없이 판별 | 상품의 마트와 값이 어긋날 수 있고, 마트 변경 시 갱신 대상이 늘어남 |
| 이용 마트 변경 시 장바구니 자동 삭제 | 화면 단순 | 회원이 모르는 사이 담은 상품이 사라짐. 회원·주문 도메인이 배송지 변경 트랜잭션에서 묶임 |
| **상품 `mart_id`로 판단, 남기고 주문만 막음(선택)** | 원본 하나로 판정, 회원이 직접 확인·삭제 | 조회마다 상품 요약을 함께 읽어야 함 |

- [CartFacade](../../src/main/java/com/recipick/domain/order/facade/CartFacade.java)는 담기 전에 장바구니의 다른 마트 상품 여부를 확인해 `CART-006`으로 거절합니다.
  화면은 이전 마트 상품을 일괄 삭제할지 묻고, 확인하면 선택 항목 삭제 → 담기 순서로 요청합니다.
- 주문 생성도 [OrderFacade](../../src/main/java/com/recipick/domain/order/facade/OrderFacade.java)의 `validateSameMart`로 재고 차감 전에 같은 기준을 다시 검사합니다.
  이때 상품 엔티티 대신 마트 ID만 조회합니다. 엔티티를 미리 읽으면 이어지는 재고 잠금 조회가 영속성 컨텍스트의 이전 재고 값을 쓰기 때문입니다.
- 상품은 소프트 삭제만 하므로 담긴 뒤 삭제된 상품도 장바구니에서 조회되며, 이때는 `CART-004`(변경 불가)로 응답하고 삭제만 허용합니다.

### 3-2. 장바구니 담기 동시성 (D2)

같은 상품을 연타하거나 자동 구성과 직접 담기가 겹치면 수량 합산이 유실되거나 행이 중복될 수 있습니다.
여기에 탈퇴와 담기가 겹치면 탈퇴가 장바구니를 지운 뒤에 새 항목이 들어올 수 있습니다(#334).

| 후보 | 장점 | 비용·한계 |
| --- | --- | --- |
| 읽고 더한 뒤 저장 | 구현 단순 | 동시 요청에서 갱신 유실 |
| 없는 행도 `INSERT ... ON DUPLICATE KEY UPDATE` | 쿼리 한 번 | MySQL 갭 락으로 동시 INSERT끼리 데드락 가능 |
| 조건부 UPDATE + INSERT·UNIQUE만 | 기존 행 합산은 DB 원자 연산, 첫 담기 중복은 제약이 막음 | 탈퇴와의 순서를 보장하지 못함. 탈퇴가 지운 뒤 담기가 커밋되면 탈퇴 회원의 항목이 남음 |
| **회원 행 잠금 + 조건부 UPDATE + INSERT·UNIQUE(선택)** | 탈퇴와 직렬화되고, 같은 회원의 담기도 한 줄로 섬. DB 제약은 최종 방어로 남음 | 담기마다 회원 행을 잡아 같은 회원의 주문 생성·탈퇴·배송지 변경과 대기가 생김 |

- 처음(#73·#96)에는 회원 잠금이 경합을 키운다고 보고 DB 원자 연산만 썼습니다. 탈퇴 연동(#334)에서 "탈퇴는 회원을 잠그고, 탈퇴 제한 상태를 만드는 작업도 같은 회원 행을 잠근다"는 컨벤션을 장바구니에도 적용하면서 회원 잠금을 추가했습니다.
  담기가 먼저면 탈퇴가 기다렸다가 함께 지우고, 탈퇴가 먼저면 담기는 회원 조회(`MEMBER-001`)에서 거절됩니다. 직접 담기(`CartFacade`)와 자동 구성 확정(`AutoCartFacade`) 모두 `lockActiveMember`를 첫 DB 작업으로 부릅니다.
- 회원 잠금 뒤에도 조건부 UPDATE·UNIQUE를 남긴 것은 컨벤션의 "신규 행 중복 생성은 UNIQUE 제약으로 최종 방어"를 지키기 위해서입니다. 잠금 없이 `CartService`를 부르는 경로가 생겨도 합산 유실·중복 행은 생기지 않습니다.
- [CartService](../../src/main/java/com/recipick/domain/order/service/CartService.java)의 `increaseQuantity`는 `quantity + n <= min(99, 재고)` 조건으로 UPDATE하고, 0건이면 다시 판정해 `CART-003`·`CART-005`·`CART-007` 중 하나로 응답합니다.
  합산 뒤 최종 수량은 엔티티가 아니라 값 조회로 읽습니다. 처음에는 벌크 UPDATE 뒤 영속성 컨텍스트를 비워(`clearAutomatically`) 엔티티를 다시 읽었는데,
  자동 구성 확정이 같은 트랜잭션에서 잠가 둔 요청 엔티티까지 분리돼 확정 상태가 저장되지 않았습니다(#541).
- 첫 담기는 UNIQUE(`member_id`, `product_id`) 위반을 `CART-007`로 바꿉니다. 자동 재시도하면 앞 요청이 이미 담은 수량에 또 합산되므로, 회원이 장바구니를 확인하게 합니다.
- 수량 변경은 최종 수량으로 덮어써 반복·동시 요청에서 마지막 값이 남게 하고, 선택 삭제는 이미 없는 ID를 건너뛰어 재시도해도 같은 결과가 나오게 했습니다. 두 작업은 탈퇴 뒤 새 항목을 만들지 않아 회원을 잠그지 않습니다.
- 담기·수량 변경 시 재고는 차감하지 않고 비교만 합니다. 담기 이력(`CART_ADD_HISTORY`)은 담기에 성공했을 때만 남기고, 자동 구성 경로는 요청 ID를 함께 남깁니다.
- 탈퇴는 정산 확인을 모두 통과한 뒤 같은 트랜잭션에서 `CartService.deleteAllByMemberId`로 장바구니를 지우고 담기 이력은 남깁니다. 탈퇴가 거절되면 삭제도 롤백됩니다.

### 3-3. 장바구니 상태 표시 (D3)

컨벤션의 "조회의 판정 결과는 상태 필드로, 거절은 상태를 바꾸는 요청에서만" 원칙을 따릅니다.
[CartItemStatus](../../src/main/java/com/recipick/domain/order/dto/response/CartItemStatus.java)는
`PREVIOUS_MART → DELETED → STOPPED → SOLD_OUT → INSUFFICIENT_STOCK → AVAILABLE` 선언 순서대로 판정해 조건이 겹쳐도 한 값만 내려갑니다.
주문 미리보기도 같은 방식으로 구매 불가 상품을 제외하고 사유를 알려주지만, 주문 생성은 하나라도 구매 불가면 제외하지 않고 거절합니다.
회원이 확인하지 않은 금액으로 결제가 만들어지지 않게 하기 위해서입니다.

### 3-4. 한 번에 주문·일괄 삭제하는 항목 수 (D4)

장바구니 항목 수에는 상한이 없지만, 주문 미리보기·주문 생성·선택 항목 삭제는 한 요청에 1~100개만 받습니다(`@Size(max = 100)`).
이 차이 때문에 101개 이상 선택하면 400(`COMMON-001`)이 나는 문제가 있었고(#404), 상한을 없앨지 검토했습니다.

| API | 상한을 없앴을 때 | 판단 |
| --- | --- | --- |
| 주문 생성 | 한 트랜잭션에서 회원 잠금 + 상품 N개 `PESSIMISTIC_WRITE` + `ORDER_ITEM` N행. 잠금이 길어져 같은 상품을 주문하는 다른 회원이 `COMMON-010`으로 실패 | 상한은 재고 잠금 범위를 묶는 유일한 장치라 유지 |
| 미리보기 | 읽기 전용·잠금 없음. 큰 조회·큰 응답 정도 | 주문 생성과 같은 값을 받아야 해서 유지 |
| 일괄 삭제 | `member_id = 본인`으로 묶여 다른 회원·재고에 영향 없음. 다만 JSON 본문 크기 제한이 없고 MySQL 파라미터 상한(65,535)을 넘으면 500 | 요청 크기 방어로 유지. 없애도 얻는 것은 드문 경우의 요청 2회 → 1회뿐 |

100이라는 값은 성능 한계가 아니라 사용량으로 정했습니다. 자동 장보기 한 번은 메뉴 최대 5개 × 레시피 재료 최대 15개라 최대 75종류이고,
일반 장보기는 거의 닿지 않으며 목록 페이지 최대 크기(100)와도 같습니다. 50이면 자동 장보기 한 번만으로 걸리고, 200 이상은 잠금 범위만 두 배가 됩니다.

백엔드는 그대로 두고 화면을 맞췄습니다(#405). 일괄 삭제는 클릭 한 번 안에서 100개씩 나눠 요청하고, 100개를 넘게 선택하면 주문하기를 막고 안내합니다.
중간 묶음이 실패해도 일괄 삭제는 없는 ID를 건너뛰므로 다시 누르면 남은 것만 지웁니다.
장바구니 항목 수 자체에 상한을 두는 안은 새 에러 코드와 직접 담기·자동 구성 확정 양쪽 검사가 필요해 제출 뒤 논의로 남겼습니다(6절).

### 3-5. 주문 생성 순서 (D5)

[OrderFacade.createOrder](../../src/main/java/com/recipick/domain/order/facade/OrderFacade.java)는 하나의 `@Transactional`에서 아래 순서로 처리합니다.

```text
1. 회원 행 잠금(lockActiveMember)                ← 첫 DB 작업. 탈퇴와 겹쳐도 한쪽만 성공
2. 같은 Idempotency-Key 주문 조회                ← 있으면 기존 주문·결제 반환(해시 다르면 COMMON-011)
3. 결제 대기 주문 존재 확인                       ← 있으면 ORDER-003
4. 이용 마트 OPEN·배송 법정동·같은 마트 검증      ← 재고 차감 전에 거절
5. 기준 시각의 멤버십 유형 조회 → 적립률·배송비 기준
6. 주문 INSERT + flush (금액 미정)               ← UNIQUE 충돌을 상품 락 대기 전에 드러냄
7. 사용 포인트 예약(reserveUsage)                 ← 잔액 부족은 재고를 잠그기 전에 POINT-001
8. 재고 잠금·판매 상태 검증·차감, 그때의 가격     ← product 도메인 원자 차감
9. 주문 상품·금액 확정                           ← 포인트가 상품금액을 넘으면 ORDER-019
10. 적립 예정 건 생성(createPendingEarning)
11. 결제 생성(IN_PROGRESS) 또는 0원 결제 완료(POINTS_ONLY)
```

- 회원 잠금이 멱등 키 조회보다 앞서야 잠금 뒤에 만들어진 스냅샷이 앞 요청의 커밋 결과를 봅니다.
  순서를 바꾸면 같은 키의 두 번째 요청이 앞 요청의 주문을 보지 못하고 UNIQUE 위반으로 끝납니다.
- 멱등 키 확인을 결제 대기 제한보다 먼저 해야 재시도가 `ORDER-003`이 아니라 처음 결과로 성공합니다.
- 주문을 재고보다 먼저 저장하는 것은 잠금 순서 `MEMBER → ORDERS → MEMBER_POINT → POINT_EARNING → 재고`를 지키기 위해서입니다. 그래서 금액은 생성 뒤 `Order.confirmAmounts`로 채웁니다.
- 포인트 예약은 같은 순서에 따라 재고보다 앞입니다. 적립 예정 건은 재고 잠금 뒤의 가격으로 정한 상품금액이 있어야 만들 수 있어 예외적으로 재고 뒤에 INSERT합니다.
  기존 행의 잠금 순서는 바뀌지 않고, 드물게 생길 수 있는 갭 락 경합은 DB가 한 트랜잭션을 롤백해 `COMMON-010` 재시도로 처리됩니다.
- 한 단계라도 실패하면 주문·포인트 예약·결제·재고가 함께 롤백되고 키도 남지 않으므로, 같은 키 재시도는 처음부터 다시 검증합니다.

### 3-6. 멱등 키와 요청 해시 (D6)

| 후보 | 장점 | 비용·한계 |
| --- | --- | --- |
| Redis에 키·응답 캐시 | DB 부하 없음 | 주문 커밋과 원자적이지 않아 커밋 후 캐시 실패·만료 시 중복 생성 |
| 별도 멱등 테이블 | 여러 API에 재사용 | 주문 하나에만 쓰는데 테이블·정리 작업이 늘어남 |
| **`ORDERS`에 `idempotency_key`·`request_hash` 저장(선택)** | 주문과 같은 트랜잭션·같은 행이라 원자적 | 주문 생성 전용 |

- UNIQUE(`member_id`, `idempotency_key`)로 최종 방어하고, 키는 소문자로 정규화합니다(최대 64자). 키 충돌로 INSERT가 실패하면 `COMMON-006`, `pending_member_id` 충돌이면 `ORDER-003`으로 구분합니다.
- [OrderCreateRequest.requestHash](../../src/main/java/com/recipick/domain/order/dto/request/OrderCreateRequest.java)는 장바구니 항목 ID를 정렬하고
  수령인·연락처·주소·상세 주소·법정동과 함께 각 값 앞에 길이를 붙여 SHA-256을 계산합니다. 항목 순서만 다른 재시도는 같은 요청으로, 구분자가 섞인 서로 다른 값은 다른 요청으로 판정됩니다.
- 사용 포인트는 0보다 클 때만 해시에 붙입니다. 포인트를 쓰지 않는 요청이 포인트 도입 전과 같은 해시를 내야, 배포 직전에 만든 결제 대기 주문의 같은 키 재시도가 `COMMON-011`이 되지 않습니다.
  같은 키로 사용 포인트만 바꾸면 다른 결제 요청이라 `COMMON-011`로 거절합니다.
- 금액은 서버가 계산하므로 해시에 넣지 않습니다.

### 3-7. 결제 대기 주문 1건 제한 (D7)

`existsPendingOrder` 조회만으로는 서로 다른 키의 동시 요청이 함께 통과할 수 있습니다. 회원 잠금이 1차로 직렬화하고,
`ORDERS.pending_member_id`(UNIQUE, nullable)가 최종 방어합니다. 결제 대기 중에만 회원 ID를 넣고 `PAID`·`CANCELED`로 벗어날 때 `null`로 비웁니다.
MySQL UNIQUE는 `NULL`을 여러 개 허용하므로 종료된 주문은 몇 건이든 쌓일 수 있습니다.
새 주문 요청이 기존 대기 주문을 자동 종료하지 않으며, 회원은 기존 결제를 계속하거나 명시적으로 취소해야 합니다.

### 3-8. 재고 차감 시점과 가격 기준 (D8)

| 후보 | 장점 | 비용·한계 |
| --- | --- | --- |
| 예약 재고(가용·예약 분리) | 결제 전까지 실재고 유지 | 컬럼·전이·만료 정리가 늘고 결제 성공 시 한 번 더 변경 |
| 결제 성공 시 차감 | 미결제 주문이 재고를 잡지 않음 | 결제 후 재고 부족이 나면 환불이 필요 |
| **주문 생성 시 실재고 차감(선택)** | 결제 성공 시 재고 변경 없음, 실패·만료 시 한 번 복구 | 5분 동안 미결제 주문이 재고를 점유 |

결제 대기는 5분 만료와 회원당 1건 제한이 있어 점유 범위가 제한된다고 판단했습니다.
상품 가격은 재고를 잠근 뒤 `decreaseStocks`가 돌려준 값으로 `ORDER_ITEM`에 스냅샷을 남깁니다. 미리보기 이후 가격이 바뀌어도 잠근 시점의 가격이 결제 금액이 됩니다.
수령인·연락처·주소·법정동도 `ORDERS`에 저장하고, 이후 회원 배송지가 바뀌어도 고치지 않습니다.
주문번호는 `yyyyMMdd-` + SecureRandom 10자리로, 순번이면 주문량이 드러나고 다른 주문번호를 추측할 수 있어 난수를 씁니다.

### 3-9. 배송비·포인트·적립률 (D9)

[OrderAmount](../../src/main/java/com/recipick/domain/order/service/OrderAmount.java)가 미리보기와 생성의 금액 계산을 한 곳에서 합니다.

```text
배송비     = 포인트 사용 전 상품금액 ≥ 기준 ? 0 : 3,000   (기준: 일반 40,000 / 멤버십 활성 15,000)
결제금액   = 상품금액 + 배송비 − 사용 포인트              (사용 포인트 ≤ 상품금액, 넘으면 ORDER-019)
적립 예정  = (상품금액 − 사용 포인트) × 적립률            (유료 1%, 체험·일반 0.5%, 배송비는 적립 제외)
```

- **기준 시각 하나로 멤버십을 한 번만 조회합니다.** `membershipService.getTypeAt(memberId, now)` 결과 하나로 적립률(`PointPolicyService.resolveRate`)과 무료배송 기준을 함께 정합니다.
  따로 조회하면 유예 종료 같은 경계에서 "적립률은 유료, 배송비는 일반"처럼 엇갈릴 수 있습니다. 배송비 혜택은 체험 회원도 받으므로 유형이 아니라 활성 여부만 보고, 적립률은 유료 이용권만 1%입니다.
- **적립률·배송비는 주문에 저장합니다**(`point_rate`, `delivery_fee`). 주문 뒤 멤버십이 끝나도 이미 만든 주문의 금액과 배송완료 때 확정할 적립액은 바뀌지 않습니다.
  같은 키 재시도는 기존 주문을 그대로 돌려주므로 기준을 다시 계산하지 않습니다.
- **포인트 한도는 재고를 잠근 뒤에 판정합니다.** 상품금액은 잠근 시점의 가격으로만 알 수 있어 요청 DTO가 아니라 `OrderAmount`가 검사하고,
  넘으면 앞서 예약한 포인트·차감한 재고·저장한 주문이 함께 롤백됩니다. 포인트는 배송비에 쓸 수 없어 상품금액 전액을 포인트로 내도 배송비는 카드로 결제합니다.
- **0원 결제는 PG 없이 주문 생성 트랜잭션에서 끝냅니다.** 결제금액이 0원이면 `PointsOnlyPaymentProcessor`가 결제 `PAID` → 주문 `PAID` → 사용 포인트 확정을
  카드 결제 성공과 같은 순서로 반영합니다. 결제 확정 API·웹훅·만료 큐를 거칠 대상이 없어서입니다.

### 3-10. 주문 상태 모델 (D10)

결제 진행과 마트 처리는 진행 주체와 시점이 달라 한 enum으로 합치면 조합이 폭발합니다. 두 축으로 나누고 상태 이력은 `ORDER_STATUS_HISTORY`에 남깁니다.

```text
OrderStatus  PENDING_PAYMENT  → PAID | CANCELED
             PAID             → CANCEL_REQUESTED | REFUNDED(외부 취소 전용)
             CANCEL_REQUESTED → PAID(회원 취소 실패 복귀) | REFUNDED
MartStatus   NONE → RECEIVED(결제 성공) → PREPARING(수락) | REJECTED(거절)
             PREPARING → SHIPPING → DELIVERED
```

[OrderStatus](../../src/main/java/com/recipick/domain/order/entity/enums/OrderStatus.java)·[MartStatus](../../src/main/java/com/recipick/domain/order/entity/enums/MartStatus.java)의
`canTransitionTo`는 기능을 구현할 때 허용 전이를 추가하고, 목록에 없는 전이는 모두 막습니다(`ORDER-016`, `ORDER-017`).
배송은 단계 건너뛰기·역행을 허용하지 않고, 같은 상태로의 전이도 막습니다. 같은 요청의 반복은 Service가 먼저 판정해 성공으로 돌려줍니다.

- 회원 화면의 "배송완료 = 구매확정"은 별도 상태를 두지 않고 `PAID` + `DELIVERED`로 표현합니다.
- 탈퇴 판단용 `existsInProgressOrder`는 `CANCELED`·`REFUNDED`·배송 완료(`PAID` + `DELIVERED`)를 뺀 주문이 하나라도 있으면 진행 중으로 봅니다.
- 이력의 처리 주체는 회원 요청이면 `MEMBER`, 마트 처리 변경이면 `MART`와 `changed_by_admin_id`, PG·만료 판정이면 `SYSTEM`입니다.
  결제 전 회원 취소는 결제 실패·만료와 같은 `closeByPaymentFailure`를 타서 `SYSTEM`으로 남던 문제가 있어(#406), 사유가 `MEMBER_CANCELED`면 `MEMBER`로 남기게 고쳤습니다.
  결제 도메인이 주문 이력의 주체까지 알 필요가 없도록 주문 쪽에서 사유로 나눴고, 이미 저장된 과거 이력은 고치지 않았습니다.

### 3-11. 결제 결과 반영과 재고 복구 (D11)

결제 승인·웹훅·5분 만료가 모두 결제 도메인으로 들어오므로 결제 도메인이 상태 확정의 진입점입니다.
결제 → 주문 순서로 잠그고, 주문 서비스와 결제 서비스는 서로 주입하지 않고 Facade가 조립합니다.

- 잠금 순서 `PAYMENT → ORDERS → MEMBER_POINT → POINT_EARNING → 재고`에서 포인트 복구가 주문과 재고 사이에 들어가야 합니다.
  그래서 `closeByPaymentFailure`·`markRefunded`·`closeByExternalCancel`은 복구할 상품만 돌려주고, 재고 복구는 `restoreStock`으로 나눴습니다.
- 둘이 따로 커밋되면 종료만 반영되고 재고 복구가 빠질 수 있어 모두 `Propagation.MANDATORY`로 바깥 트랜잭션 없이는 호출되지 않게 했습니다.
- 반복 전달에 대한 멱등성은 주문 행 잠금 뒤 상태로 판정합니다. 이미 `PAID`면 아무것도 하지 않고, 이미 `CANCELED`면 빈 목록을 돌려줘 재고를 다시 더하지 않으며 최초 취소 사유도 덮어쓰지 않습니다.
- 만료 뒤 늦게 온 승인은 결제 도메인이 시스템 환불만 처리합니다. 주문은 `CANCELED`로 두고 재고는 다시 바꾸지 않습니다.
- 외부(PG 콘솔) 취소는 기다릴 PG 결과가 없어 `PAID → REFUNDED`로 바로 종료합니다. 마트 처리 상태가 `RECEIVED`·`PREPARING`일 때만 재고를 복구합니다.
  배송이 시작된 상품은 마트에 없으므로 재고를 더하면 실물보다 많아집니다. 이 경우 WARN 로그를 남기고 관리자가 재고 조정으로 맞춥니다.

### 3-12. 회원 취소·마트 수락·거절·배송 (D12)

- 회원 취소는 마트가 준비를 시작하기 전(`RECEIVED`)에만 받습니다. 주문은 같은 요청인지 알 수 없으므로 `PAID`가 아니면 상태를 바꾸지 않고
  `MemberCancelRequestResult`로 판정만 돌려줍니다. 같은 요청의 반복은 결제 쪽 `Idempotency-Key`가 먼저 거릅니다.
- 마트 거절은 PG 환불 결과를 기다려야 하므로 `CANCEL_REQUESTED` + `REJECTED`에 두고, 접수 시점에는 재고·사용 포인트를 복구하지 않습니다. 환불 성공 시 `markRefunded`가 재고를, 결제 Facade가 포인트를 복구합니다.
  거절 후 PG 취소가 실패해도 이미 처리할 수 없다고 판정한 주문이라 `PAID`로 되돌리지 않고 관리자 재처리 대상으로 둡니다.
- 수락은 주문 행만 잠급니다. 회원 취소는 결제 → 주문 순서로 잠그므로 교착이 없고, 잠근 뒤 상태를 보므로 둘 중 하나만 성공합니다.
- 배송 변경은 [OrderDeliveryFacade](../../src/main/java/com/recipick/domain/order/facade/OrderDeliveryFacade.java)가 조립합니다.
  - 배송완료는 구매확정이라 포인트 적립 확정(`confirmEarning`)까지 한 트랜잭션입니다. 따로 커밋되면 배송완료인데 적립이 확정되지 않은 주문이 남습니다.
  - 주문 → 포인트 순으로 불러 `ORDERS → MEMBER_POINT → POINT_EARNING`을 지키고, 결제는 바뀌지 않으므로 `PAYMENT`를 잠그지 않습니다. 잠그면 결제 흐름(`PAYMENT → ORDERS`)과 순서가 뒤집힙니다.
  - `changeDeliveryStatus`는 `MANDATORY`라 Facade 밖에서 배송완료만 커밋할 수 없습니다.
  - 주문이 `PAID`가 아니면 같은 상태 반복 판정보다 먼저 거절합니다. 환불로 끝난 배송완료 주문에 배송완료가 다시 와도 성공으로 숨기지 않기 위해서입니다.
- 결제 전(`NONE`) 주문은 마트 처리 대상이 아니므로 관리자 조회·수락·거절·배송 변경에서 없는 주문과 같이 `ORDER-012`로 답하고, 다른 마트 주문은 접근 범위 문제라 트랜잭션째 롤백합니다.
- 관리자 목록·상세 조회·수락·거절·배송 변경은 `AdminAuditRecorder`로 같은 쓰기 트랜잭션에서 감사 기록을 남기며, 기록 실패 시 업무도 롤백합니다. 같은 요청의 반복은 실제 변경이 없어 이력·감사를 남기지 않습니다.
- 마트 거절 환불이 실패한 주문은 `POST /api/admin/orders/{orderId}/refunds/{refundId}/retry`로 다시 환불합니다(#473, 결제 담당 구현). 처리는 결제 도메인이 하고,
  주문 쪽은 `validateMartRefundRetry`가 주문을 잠근 뒤 마트 범위와 거절 환불 진행 상태(`CANCEL_REQUESTED`·`REJECTED`·`MART_REJECTED`)만 확인합니다. 주문 상태는 바꾸지 않고, 환불이 성공하면 기존 `markRefunded` 경로로 끝납니다.
- 회원 탈퇴용으로 `existsInProgressOrder`를 제공합니다. 진행 중 상태로 들어오는 입구가 회원 행을 잠그는 주문 생성뿐이라, 탈퇴가 회원을 잠근 뒤라면 잠금 없이 조회해도 됩니다.

### 3-13. 결제 완료 후 장바구니 정리 (D13)

결제가 성공해도 결제한 상품이 장바구니에 남아 있었습니다(#352). 결제 실패·만료 때는 다시 결제할 수 있게 장바구니를 남기고, 성공했을 때만 정리합니다.

| 후보 | 장점 | 비용·한계 |
| --- | --- | --- |
| 결제 확정 트랜잭션 안에서 삭제(처음 시도) | 결제와 장바구니가 항상 함께 반영 | 장바구니 DELETE가 실패(잠금 대기 초과·교착)하면 이미 PG에서 승인된 결제 확정까지 롤백. 결제 잠금 순서 뒤에 `CART_ITEM`이 붙고, 결제 성공 경로(확정 API·웹훅·만료 재조회·0원 결제)마다 호출을 잊지 않아야 함 |
| 커밋 뒤 `@Async` 이벤트 | 결제 응답 지연 없음 | 결제 직후 장바구니에 상품이 남아 보일 수 있고, 서버 종료 시 큐의 작업이 사라짐. 스레드 풀·DB 커넥션·MDC 전파를 따로 관리 |
| **커밋 뒤 같은 스레드 이벤트(선택)** | 결제 커밋이 성공했을 때만 실행, 실패해도 결제는 그대로. 결제 코드는 장바구니를 모름 | 확정 API·웹훅 응답이 정리 시간만큼 늦어짐. 실패 시 자동 재처리 없음 |

- `OrderService.markPaid`가 주문을 `PAID`로 바꾸는 트랜잭션 안에서 `OrderPaidEvent`를 발행하고,
  [PaidCartCleanupListener](../../src/main/java/com/recipick/domain/order/event/PaidCartCleanupListener.java)가 `AFTER_COMMIT`에서 받습니다.
  모든 결제 성공 경로가 `markPaid`를 지나므로 경로마다 호출을 추가할 필요가 없습니다. 결제가 롤백되면 이벤트도 버려집니다.
- 커밋 뒤 콜백에는 끝난 트랜잭션 자원이 아직 묶여 있어 그대로 참여하면 삭제가 커밋되지 않습니다. 리스너를 `NOT_SUPPORTED`로 떼어 두고 `CartService.deductPaidItems`가 새 트랜잭션을 엽니다.
- 예외는 리스너 안에서 끊습니다. 호출자에게 올라가면 결제 확정 API가 실패로 응답하기 때문입니다. `DataAccessException`은 WARN, 그 밖은 ERROR + 스택으로 `orderId`·`memberId`와 함께 남깁니다.
- 컨벤션의 "`ApplicationEvent`는 일시적 불일치가 허용되는 후처리에만 쓴다"에 해당한다고 판단했습니다. 장바구니에 상품이 남아도 회원이 지울 수 있고 돈·재고는 맞습니다.
- **항목을 지우지 않고 결제한 수량만 뺍니다.** 결제 대기 중에 같은 상품을 더 담았을 수 있어서, 통째로 지우면 새로 담은 수량까지 사라집니다.
  결제 수량 이하인 항목을 먼저 지우고 남은 항목에서 결제 수량을 뺍니다. 순서를 바꾸면 뺀 결과가 다시 삭제 조건에 걸립니다. 장바구니에 없는 상품은 건너뛰고 담기 이력은 남깁니다.
- 같은 승인이 다시 오면 `markPaid`가 이미 `PAID`인 것을 보고 이벤트를 발행하지 않아, 그 사이 회원이 다시 담은 상품을 지우지 않습니다.
  회원 취소 실패 후 `PAID` 복구(`restorePaidAfterMemberCancelFailure`)도 `markPaid`를 거치지 않아 장바구니를 다시 정리하지 않습니다.
- `@Async`가 필요해지면 `@EnableAsync`, 이름 붙인 전용 `ThreadPoolTaskExecutor`(DB 커넥션 풀을 고려한 크기·거부 정책·종료 대기), MDC 복사용 `TaskDecorator`를 함께 준비해야 합니다.

## 4. 트레이드오프

- 얻는 점
  - 같은 요청 반복·동시 요청에서 주문 1건·재고 1회 차감·1회 복구·적립 1회가 DB 잠금과 UNIQUE 제약으로 보장되고, Redis 등 외부 저장소 장애와 무관합니다.
  - 결제 성공 경로에 재고 변경이 없어 결제 확정 트랜잭션이 짧고, 장바구니 정리 실패가 결제 확정에 영향을 주지 않습니다.
  - 적립률·배송비를 주문에 저장해 멤버십 변경이 이미 만든 주문의 금액을 바꾸지 않습니다.
- 감수하는 비용·해결하지 못한 부분
  - 주문 생성과 장바구니 담기가 회원 행을 잡으므로 같은 회원의 담기·주문 생성·탈퇴·배송지 변경은 직렬화됩니다. 한 회원이 동시에 여러 요청을 보내는 경우가 아니면 영향이 작다고 판단했습니다.
  - 미결제 주문이 최대 5분 재고를 점유합니다. 인기 상품의 재고가 적을 때 결제하지 않는 회원이 다른 회원의 주문을 막을 수 있습니다.
  - 적립 예정 건 INSERT가 재고 잠금 뒤라, 드물게 갭 락 경합으로 한쪽 주문이 `COMMON-010`으로 실패할 수 있습니다.
  - 결제 확정 API·웹훅 응답이 장바구니 정리 시간만큼 늦어지고, 정리에 실패하면 자동 재처리 없이 장바구니에 상품이 남습니다(로그로 확인).
  - 장바구니가 100개를 넘으면 화면이 나눠 요청하거나 선택을 줄이게 안내해야 합니다.
  - 주문 도메인 로그는 장바구니 정리 실패와 외부 취소의 재고 미복구 두 곳뿐이라, 그 밖의 실패 경로 추적은 상태 이력에 의존합니다. 요청 ID는 전역 `RequestLoggingFilter`가 MDC와 `X-Request-Id`로 남기지만, 주문 ID MDC·구조화 로그·주문 지표는 검토만 하고 도입하지 않았습니다.
- 다시 검토할 조건
  - 재고 점유로 인한 주문 실패가 실제로 관측되면 예약 재고나 만료 시간 단축을 검토합니다.
  - 장바구니 정리로 결제 응답이 눈에 띄게 늦어지거나 실패 로그가 반복되면 `@Async`·재처리를 검토합니다.
  - 장바구니 항목 수 상한이나 서버가 이전 마트 상품을 찾아 지우는 API가 필요해지면 D4를 다시 정합니다.
  - 배송 이후 부분 반품·부분 취소를 열 때 외부 취소의 재고 복구 기준을 함께 확인합니다.
