# 배포 방식 선택 근거 — 서버 1대 Compose와 단계별 고도화

초안 · 작성일 2026-10-26 · 대상 환경 AWS · 업무 전달 문서 대조 반영 2026-10-26 · 초안 검토 반영 2026-10-26

> 목적: 최종 제출(2026-11-12)까지의 배포 구성을 왜 이렇게 정했는지, 무엇을 버렸는지, 어떤 조건이 생기면 다음 단계로 넘어가는지 기록한다.
> 팀 결정(서버 구성, 도메인·HTTPS, 운영 관리자 생성 방법)이 확정되면 11절을 갱신한다.

## 1. 결론

- 서버 1대(EC2)에 Docker Compose로 올린다. 리버스 프록시(기본 nginx, 제품 선택은 11절)가 80·443을 받고, 앱·MySQL·Redis는 같은 호스트의 컨테이너로 둔다. Prometheus·Grafana는 앱 배포가 안정된 뒤 태헌의 구성을 같은 호스트에 추가한다.
- dev 병합 시 자동 배포한다. 2026-11-09에 병합을 동결하고 main으로 승격해 같은 서버에 시연 배포한다.
- 자동 파이프라인은 재시작 방식으로 먼저 완성한다. 첫 배포(10/28)는 수동이고, 10/30까지 "이미지 교체 → 헬스 체크 → 실패 시 이전 SHA 복구"를 dev 병합마다 자동 실행한다. CI/CD 증거와 서버 측정을 늦추지 않기 위해서다.
- nginx 업스트림 교체 블루그린은 고도화 사다리 1단계로 둔다. 필수 항목(부하 테스트·병목·캐싱·모니터링)에 착수한 뒤 여유가 있을 때 도입하고, 전환 후 이전 색은 짧은 관찰 뒤 중지한다. 스케줄 작업의 단일 실행 보장 규칙과, 앱 1개·모니터링의 실제 메모리 사용량을 잰 뒤 앱 두 개가 들어갈 여유가 확인되는 것이 선행 조건이다.
- 파이프라인은 GitHub OIDC로 AWS IAM 역할을 가정하고 ECR과 SSM Run Command를 쓴다. GitHub Secrets에 장기 액세스 키나 SSH 키를 두지 않고, 22번 포트를 열지 않는다.
- RDS 분리, ALB + EC2 2대는 지금 하지 않는다. 6절의 조건이 생길 때 올라가는 사다리로 둔다.

단일 구성은 한계가 아니라 조건부 판단이다. 평가는 가용성과 자동 확장이 아니라 부하 테스트·캐싱·모니터링과 그 근거 문서를 보고, 남은 시간은 그쪽에 써야 한다.

## 3. 대안 비교

금액은 서울 리전 온디맨드 대략치이며 확정 전에 요금표로 확인한다.

| 구분 | A. 단일 Compose (EC2 1대) | B. 부분 분리 (EC2 + RDS) | C. 전부 분리 (ECS + ALB + RDS + ElastiCache) |

| 부하 테스트 격리 | 앱·DB가 CPU를 공유. 같은 박스에서 전후 비교는 유효 | DB가 분리되어 깨끗함 | 깨끗함 |

| 병목 분석 도구 | slow query log를 직접 설정 | Performance Insights 제공 | 동일 |
| 호스트 장애 내성 | 없음 | DB만 있음 | 있음 |
| 11/12 안에 다른 미충족 5개 항목과 병행 | 가능 | 가능 | 어려움 |

B와 C를 지금 택하지 않는 이유는 둘이 주는 것(데이터 안전, 가용성, 자동 확장)이 평가 항목이 아니고, 그 대가로 쓰는 시간은 평가 항목(부하 테스트, 캐싱, 모니터링, 문서)에서 빠지기 때문이다. B는 비용과 시간이 작아 6절의 사다리 2단계로 둔다.

## 4. 선택한 구성

### 4-1. 컨테이너 배치

| 서비스 | 역할 | 호스트 노출 | 비고 |
| --- | --- | --- | --- |
| nginx | TLS 종단, 업스트림 교체 지점 | 80, 443 | 블루그린 도입 시 전환 장치 |
| app (블루그린 도입 후 app-blue / app-green) | Spring Boot | 없음 | 상시 1개. 블루그린에서도 교체와 짧은 관찰 시간에만 둘 다 실행하고 이전 색은 중지한다 |
| mysql | 데이터 | 없음 | named volume, 배포 때 재시작하지 않음 |
| redis | 리프레시 토큰, 로그인 실패 횟수 | 없음 | named volume |
| prometheus / grafana | 지표 수집·대시보드 | 없음 | 첫 배포에 포함하지 않는다. 태헌의 구성이 준비되면 `compose.monitoring.yml`로 추가. 접근 방식은 11절 미결 |

로컬용 `docker-compose.yml`은 3306·6379를 호스트에 노출하지만 운영 compose에서는 포트 매핑을 두지 않는다. 보안 그룹은 80·443만 연다. 서버 접속은 SSM Session Manager로 하고 22번은 열지 않는다.

프록시는 nginx를 기본으로 하되, 업무 전달이 조건으로 건 인증서 자동 발급·갱신을 만족해야 한다. nginx면 certbot 컨테이너와 갱신 후 reload 훅이 붙고, Caddy면 컨테이너 하나가 발급·갱신을 맡는다. 블루그린 절차(5-3)는 둘 다 업스트림 파일 수정과 reload로 같으므로 제품 선택이 배포 방식을 바꾸지 않는다. 선택은 11절에서 확정한다.

Actuator 관리 포트는 앱 포트와 분리해 호스트에 노출하지 않는다. 헬스 체크와 지표 수집은 도커 네트워크 안에서 그 포트를 쓰므로 프록시에 `/actuator/` 차단 규칙을 둘 필요가 없다. 포트 분리는 #190으로 병합됐다(10/26). Security 필터 체인은 관리 포트에도 적용되므로 `EndpointRequest` 허용 규칙이 함께 들어갔다(4-3).

### 4-2. Compose 파일 분리

호스트는 하나여도 파일은 역할별로 나눈다.

| 파일 | 서비스 | 이유 |
| --- | --- | --- |
| `compose.yml` | nginx, app (블루그린 도입 후 app-blue, app-green) | 배포 스크립트가 이 파일만 다룬다. DB를 건드리는 사고를 막는다 |
| `compose.infra.yml` | mysql, redis | RDS로 옮길 때 이 파일을 지우고 환경 변수만 바꾼다 |
| `compose.monitoring.yml` | prometheus, grafana (+ 태헌이 추가할 node·mysqld·redis exporter) | 첫 배포에는 없다. 태헌의 구성을 나중에 이 파일로 추가한다. 부하 테스트 중에도 켜 둔다. 병목 분석에 지표가 필요하고 Before·After 모두 켜 두면 조건이 같다 |

배포 때 `docker compose down`을 쓰지 않는다. 앱 서비스만 교체해야 MySQL·Redis 볼륨과 리프레시 토큰이 유지된다. 모든 서비스에 `restart: unless-stopped`와 json-file 로그 로테이션(`max-size` 10m, `max-file` 3)을 둔다. 로테이션이 없으면 루트 볼륨이 로그로 찬다.

### 4-3. 고도화를 막지 않기 위해 앱이 지키는 조건

| 조건 | 현재 코드 확인 결과 (2026-10-26) |
| --- | --- |
| 앱이 MySQL·Redis 위치를 모른다. 접속 정보는 환경 변수로만 받는다 | prod 프로필이 없다. 운영 프로필을 환경 변수 기반으로 추가한다 |
| 앱 컨테이너가 무상태다 | 세션은 JWT + Redis다. 로컬 파일 저장, 인메모리 캐시, `@Scheduled`가 없다. 로컬 JWT 키 파일은 local 프로필에서만 쓰고 그 외에는 `JWT_SECRET`이 없으면 기동을 거부한다. 지금 그대로 두 대로 늘려도 된다 |
| 이미지는 CI에서 빌드해 레지스트리에 둔다 | 서버에서 빌드하지 않는다. 같은 이미지가 나중에 ECS에서도 돈다 |
| 헬스 엔드포인트가 있다 | #190으로 Actuator가 병합됐다(10/26). 관리 포트 8081(`MANAGEMENT_PORT`)에서 `health`·`prometheus`만 열고, `SecurityConfig`가 `EndpointRequest.to("health", "prometheus")`로 허용한다. 이 매처는 관리 포트 요청에만 맞으므로 앱 포트의 `/actuator/**`는 그대로 `denyAll`(401)이다. 관리 포트는 호스트에 노출하지 않고 도커 네트워크 안에서만 쓴다. 컨테이너 헬스 체크는 관리 포트의 `/actuator/health`와 앱 포트의 `GET /api/categories`를 함께 본다. 관리 포트는 별도 서버라 UP이어도 앱 포트가 요청을 받는다는 보장이 없기 때문이다(`docs/monitoring.md`). ALB·ECS도 나중에 같은 것을 요구한다 |

### 4-4. 설정과 시크릿

- 운영 프로필은 `SPRING_PROFILES_ACTIVE=prod`로 켠다. `application.yml`의 시드 프로필 식 `(local | test) & !prod & !production`이 이미 prod를 제외하므로 `data-admin-local.sql`은 운영에서 실행되지 않는다. 운영 관리자 생성 방법은 별도로 정한다(11절).
- `data.sql`(시연 지역·마트 시드)은 기본 위치라 prod에서도 실행된다. 멱등 INSERT라 반복 실행에 안전하다. 실행이 의도인지 11절에서 확인한다.
- 환경 변수 이름은 업무 전달 4-1을 따른다: `SPRING_DATASOURCE_URL`·`_USERNAME`·`_PASSWORD`, `SPRING_DATA_REDIS_HOST`·`_PORT`, `SPRING_JPA_HIBERNATE_DDL_AUTO`, `JWT_SECRET`, `CORS_ALLOWED_ORIGINS`, `PORTONE_API_SECRET`·`PORTONE_STORE_ID`·`PORTONE_CHANNEL_KEY`·`PORTONE_WEBHOOK_SECRET`. `JWT_SECRET`은 `JwtConfig`가 Base64로 디코딩하므로 Base64 문자열이어야 하고, 디코딩 후 32바이트 이상이어야 HS256 키 검증을 통과한다. `openssl rand -base64 48`로 만든다. 값은 서버의 `/opt/recipick/.env`(권한 600)에만 둔다. 워크플로는 OIDC로 역할을 가정하므로 GitHub Secrets에 AWS 키나 SSH 키를 두지 않는다. 역할 ARN, 리전, 인스턴스 ID는 레포 변수로 둔다.
- `ddl-auto`는 기본값이 없고 DDL·마이그레이션 파일도 없다. 지정하지 않으면 테이블이 없어 `data.sql`이 실패하고 기동이 멈추므로 첫 배포부터 `update`를 지정한다.
- 락 대기 시간은 운영 프로필에 반드시 넣는다. Hikari `connection-init-sql: SET SESSION innodb_lock_wait_timeout = 5`가 로컬 예시에만 있어서, 빠지면 락 실패 시 `COMMON-010` 5초 규칙이 깨진다. 운영 compose의 MySQL 옵션 `--innodb-lock-wait-timeout=5`도 같이 둔다. DB URL의 `serverTimezone=Asia/Seoul&characterEncoding=UTF-8`과 PortOne 연결·읽기 타임아웃(3초·5초)도 로컬에만 있으므로 함께 옮긴다.
- 리버스 프록시 뒤에서는 앱이 보는 접속 IP가 도커 내부 주소가 된다. 운영 프로필에 `server.forward-headers-strategy=native`를 넣는다. Tomcat의 기본 내부 프록시 범위가 도커 네트워크 대역을 포함하므로, 프록시가 `X-Forwarded-For`를 자기 접속 주소로 덮어쓰면 채빈의 감사 IP와 나중의 429 요청 제한이 같은 방식으로 실제 클라이언트 IP를 받는다. 요구사항(감사 IP는 신뢰 프록시가 정리한 헤더만 사용)과 맞는다.
- 리프레시 쿠키의 Secure 기본값이 true라 HTTP에서는 브라우저 재발급이 되지 않고, PortOne 웹훅 등록에도 외부 고정 주소가 필요하다. 고정 DNS 주소는 요구사항이므로 도메인 구매와 DNS 연결은 첫날 시작하고 HTTPS는 10/30까지 올린다. 10/28의 고정 IP + HTTP 응답은 내부 점검점이다.

## 5. 배포 파이프라인

| 단계 | 내용 |
| --- | --- |
| 트리거 | 배포 대상 브랜치로 push. 대상 브랜치는 레포 변수로 두고 처음엔 dev, 11/9에 main으로 바꾼다. PR은 기존 `ci.yml`대로 테스트만 |
| 인증 | GitHub OIDC로 AWS IAM 역할을 가정한다. 장기 액세스 키를 GitHub Secrets에 두지 않는다 |
| 빌드 | `./gradlew test` → jar 빌드 → 이미지 빌드 → ECR에 push. 태그는 커밋 SHA |
| 전달 | 워크플로가 저장소의 `deploy/`(compose, nginx, 스크립트)를 S3에 올린다. SSM 명령이 서버 잠금을 먼저 잡고, 배포별 임시 디렉터리로 내려받아 `releases/<SHA>`에 푼다. 운영 설정은 배포 스크립트가 그 묶음과 정확히 같게 맞추므로 저장소에서 지운 파일도 서버에서 사라진다. 서버 설정 파일도 git이 원본이라 "코드 변경 자동 반영"에 설정 변경이 포함된다. `.env`·인증서·덤프·묶음은 보존한다 |
| 배포 | SSM Run Command로 묶음의 `scripts/deploy.sh <SHA>`를 실행한다. 재시작 방식: `.env` 필수 값 검사 → MySQL·Redis 준비 대기 → 배포 전 덤프 → 이미지 pull → 설정 교체·태그 갱신 → app·nginx 기동 → `nginx -t`·reload → 앱 healthy → nginx 경유 응답 확인. 기동·설정 검사·헬스·경유 응답 중 어디서 실패해도 이전 태그의 이미지와 설정으로 같은 절차를 밟아 복구한다. 블루그린 도입 후에는 5-3 절차. EC2는 인스턴스 프로파일로 ECR에서 pull한다 |
| 대안 | GHCR push + SSH 배포. 비교와 전환 조건은 5-1 |
| 소요 | 현재 CI가 약 2.5~3분이므로 빌드·테스트·배포 합쳐 5분 안팎 예상 |

배포 대상 브랜치를 변수로 두는 이유는 동결을 약속이 아니라 설정으로 만들기 위해서다. 같은 서버에 dev·main 두 트리거를 걸면 11/9 이후 dev 병합 한 번이 시연 서버를 덮어쓴다.

브랜치와 환경의 매핑은 다음과 같다. 서버는 한 대이고 배포 대상 브랜치 변수로 환경의 역할이 바뀐다.

| 브랜치 | 역할 | 워크플로 | 기간 |
| --- | --- | --- | --- |
| `feature/*`, `fix/*` 등 | 작업 | PR에서 `./gradlew test`만 | 상시 |
| `dev` | 통합. 11/9 전까지는 시연 서버이기도 하다 | push 시 빌드 → 테스트 → 배포 | 11/9까지 |
| `main` | 시연. 11/9에 dev를 승격한다 | push 시 빌드 → 테스트 → 배포. 이후 dev push는 배포하지 않는다 | 11/9부터 |

origin에 main이 이미 있다. 10/16 PR #5로 dev를 병합한 상태에서 멈춰 있고 dev가 444 커밋 앞서 있다. 다음 dev → main 병합은 가상 병합으로 충돌 없음을 확인했고, main에만 있는 커밋은 그 병합 커밋 하나뿐이다. 현재 룰셋 `protect-main-dev`는 main·dev 공통으로 PR 필수, merge commit만 허용, 삭제·force push 금지, CI `test` 통과, 리뷰 스레드 해결을 요구하며 필수 승인 수는 0이다.

main 운영 규칙은 다음과 같다. main은 11/9 전까지 "그 시점에 검증된 스냅샷"이고 서버와 무관하며, 11/9부터 실제 배포 소스가 된다.

| 규칙 | 내용 |
| --- | --- |
| 들어오는 경로 | dev → main PR만. 직접 push와 squash·rebase는 룰셋이 막는다. 이 규칙을 지키면 승격 PR은 항상 충돌 없이 끝난다 |
| 보호 규칙 | main 전용 룰셋을 추가해 사람 승인 1~2개를 요구한다. 기존 룰셋은 그대로 두고 겹쳐 적용한다. dev에는 승인 수를 올리지 않는다 |
| 승격 횟수 | 정상 경로에서 두 번. (1) 10/30 이후 파이프라인이 돌 때 따라잡기 승격, (2) 11/9 최종 승격. 컨벤션(차수 종료 승격)대로면 2차 종료 승격이 빠져 있다 |
| 리허설 | 따라잡기 승격 직후 배포 대상 변수를 main으로 바꿔 배포 한 번을 돌리고 dev로 되돌린다. 승격 직후여야 main과 dev가 같아 서버 내용이 바뀌지 않는다. 며칠 뒤에 하면 서버를 옛 코드로 되돌리게 된다. 변수 되돌리기를 체크리스트에 둔다 |
| 배포 소스 | 11/9 전까지 dev, 11/9부터 main. 변수가 dev인 동안 main 승격은 서버를 건드리지 않고 CI 테스트만 돈다 |
| 태그 | 11/9 승격 직후 main에 태그를 단다. 시연 영상의 서버, 커밋, ECR 이미지가 한 줄로 이어지고 롤백 기준점이 된다 |
| 11/9 이후 수정 | `hotfix/{domain}-{작업}`을 main에서 따서 main으로 PR. 승인·CI 후 배포하고, 시연 뒤 main → dev PR로 되돌린다. 생기지 않는 것이 정상이다 |
| 로컬 문서 | 이 문서는 #200 PR로 dev에 올리고, 다음 승격 때 main에 들어간다 |
| 제출 시점 | 기본 브랜치를 main으로 바꿀지 팀이 정한다(11절). 그 뒤에는 PR이 없어 작업 흐름에 영향이 없다 |

### 5-1. 인증·전달 방식

워크플로가 AWS에 들어가는 방법(인증)과 이미지를 서버에 보내는 방법(전달)은 교체 방식(5-2)과 별개의 층이다. 두 조합을 비교했다.

| 항목 | OIDC + ECR + SSM (선택) | GHCR + SSH (대안) |
| --- | --- | --- |
| 장기 비밀 | 없음. 역할 신뢰 정책으로 이 레포·이 브랜치만 배포하도록 제한 | SSH 개인키를 GitHub Secrets에 장기 보관 |
| 서버 접속 포트 | 22번 닫음. 명령은 SSM Run Command, 접속은 Session Manager | 22번 개방. 러너 IP가 유동이라 전 세계에 열어야 함 |
| 서버 쪽 레지스트리 자격 | 없음. 인스턴스 프로파일로 pull | 비공개 이미지면 서버에 PAT 필요 |
| 추적 | CloudTrail에 배포 주체·시각 기록 | GitHub Actions 로그만 |
| 재사용 | ECS 전환(6절 4단계) 때 그대로 사용 | ECS로 가면 다시 만듦 |
| 설정 시간 | IAM 네 덩어리(OIDC 공급자, 역할 신뢰 정책, 역할 권한, 인스턴스 프로파일). 경험자 기준 반나절 | 30분 |
| 명령 실행 | SSM은 비동기. 완료 대기와 출력 수집 코드가 워크플로에 필요 | 명령 결과가 바로 돌아옴 |
| 디버깅 | IAM 권한이 없는 팀원은 원인을 볼 수 없다. 완화: 워크플로가 SSM 명령 출력을 Actions 로그로 가져오고, 팀원 IAM 사용자에 Session Manager 권한을 주면 브라우저 콘솔에서 설치 없이 셸을 연다. scp·IDE 원격이 필요하면 SSH over SSM으로 22번은 닫은 채 쓴다 | 전부 GitHub 안이라 누구나 로그 확인 |
| 평가 관점 | 배포용 시크릿 관리 근거가 선다 | 설명이 약함 |

담당자에게 OIDC 경험이 있어 설정 시간 단점이 작다. OIDC·IAM 설정이 10/28 목표를 위협하면 그날은 GHCR + SSH로 열고 11/2까지 전환한다. 서버 쪽 교체 스크립트는 두 경우에 같다.

### 5-2. 무중단 배포 방식

무중단의 조건은 새 인스턴스가 준비될 때까지 옛 인스턴스가 응답하는 겹침이지 블루그린이라는 이름이 아니다. 단일 호스트에서 겹침을 만드는 방법을 비교했다.

| 방식 | 중단 | 추가 도구 | 비고 |
| --- | --- | --- | --- |
| 컨테이너 재시작만 | Spring Boot 기동 시간만큼(10~30초) | 없음 | graceful shutdown을 켜도 기동 공백은 남는다. **첫 자동 파이프라인(10/30)은 이 방식**이다. dev 병합마다 수십 초 끊기는 것은 통합 환경에서 감수한다 |
| 블루그린 (nginx 업스트림 교체) | 없음 | 없음. nginx는 TLS 종단용으로 이미 둔다 | 두 이름이 고정되어 절차가 단순하고 되돌리기가 업스트림 한 줄이다. **고도화 1단계로 선택**. 필수 항목 착수 후 여유가 있을 때 도입하며 스케줄 작업 단일 실행 규칙이 선행 조건이다 |
| 롤링 (compose scale + Traefik 동적 라우팅) | 없음 | Traefik | 교체를 자동 감지하지만 도구가 하나 늘고 라우팅 문제를 추적하기 어렵다 |
| Swarm 롤링 업데이트 | 없음 | Swarm 모드 | compose 파일을 거의 그대로 쓰지만 단일 노드에는 과하다 |
| ECS 롤링, ALB 대상 그룹 | 없음 | ECS 또는 ALB | 플랫폼이 겹침을 만든다. 6절 3·4단계 |

GitHub OIDC는 무중단과 별개다. 워크플로가 장기 키 없이 AWS에 인증하는 방법이며, 어떤 배포 방식과도 같이 쓴다.

선택한 블루그린(교체를 직접 구현)과 플랫폼이 교체를 대신하는 ECS 롤링을 항목별로 비교하면 다음과 같다.

| 항목 | nginx 블루그린 (직접, 선택) | ECS 롤링 (플랫폼) |
| --- | --- | --- |
| 추가 비용 | 0 | ALB 월 2만원대 + 태스크 용량. ECS에 상태 저장 컨테이너를 두기 어려워 RDS·ElastiCache 분리가 사실상 따라온다 |
| 구축 시간 | 셸 스크립트 30줄 안팎, 하루 | 태스크 정의·IAM·VPC, 1주 이상 |
| 헬스·드레이닝·롤백 | 직접 구현. nginx reload가 기존 연결은 끝내 준다 | 플랫폼 제공. 서킷 브레이커가 실패 배포를 자동 롤백 |
| 호스트 장애 | 무력 | 여러 태스크·가용 영역으로 흡수 |
| 확장 | 두 번째 서버부터 ALB로 갈아타야 함 | 오토스케일 설정만 |
| 시연 설득력 | 교체 로직을 직접 설명할 수 있어 도전 항목 "배포 고도화" 근거로 강함 | 설정 화면을 보여주는 데 그침 |

CodeDeploy는 중간 선택지다. EC2에서 블루그린을 하려면 ALB가 필요하고 in-place 모드는 중단이 생기므로 단일 EC2에서는 이점이 거의 없다.

### 5-3. 블루그린 교체 절차

1. nginx 업스트림 파일을 읽어 현재 색을 알아내고 유휴 색을 정한다.
2. 유휴 색 서비스를 새 SHA 태그로 `up -d` 한다. 앱 포트는 호스트에 노출하지 않으므로 compose `healthcheck`를 쓴다.
3. 컨테이너 상태가 `healthy`가 될 때까지 기다린다. 시간 초과면 유휴 색을 내리고 워크플로를 실패시킨다. 서비스 중인 색은 건드리지 않는다.
4. 업스트림 파일을 새 색으로 다시 쓰고 `nginx -s reload` 한다. reload가 DNS를 다시 푸니 별도 resolver 설정은 필요 없다.
5. 전환 후 짧은 관찰 시간(헬스와 에러 로그 확인, 1~2분) 뒤 이전 색을 중지한다. 두 JVM을 상시로 띄우지 않는다. 이미지는 남겨 두어 롤백에 쓴다.

첫 배포(10/28)와 첫 자동 파이프라인(10/30)은 1~5 없이 앱 서비스 하나를 재시작하는 방식이다. 이 절차로 바꾸는 시점은 6절 1단계의 조건을 따른다. nginx는 첫날부터 둔다.

겹침 창에 스케줄 작업이 발화하면 두 컨테이너가 같은 작업을 두 번 돌린다. 요구사항에 탈퇴 해시 기록 삭제, 미확정 자동 장바구니 7일 정리, 감사 로그 1년 삭제, 갱신 결제 재시도 배치가 예정되어 있고, 갱신 결제는 이중 결제 위험이 있다. 관찰 시간을 짧게 잡아도 창은 남으므로 블루그린 도입 전에 "스케줄 작업은 락으로 단일 실행을 보장한다"를 컨벤션에 넣고 첫 스케줄러부터 적용한다. Redis가 이미 있으니 SET NX 기반 락이나 ShedLock이면 된다. 이 규칙은 ALB + 2대 단계에서도 그대로 필요하다.

### 5-4. 롤백

- 앱 문제: 재시작 방식에서는 이전 SHA의 이미지와 그 SHA의 설정 묶음(compose·nginx)으로 재기동한다. 이미지만 되돌리면 새 설정이 옛 이미지와 어긋날 수 있기 때문이다. 자동 배포는 기동 실패·nginx 설정 오류·헬스 실패·경유 응답 실패를 모두 같은 복구 절차로 처리하고, 복구 후에도 같은 검사를 한다. 블루그린에서는 관찰 시간 안이면 이전 색이 아직 떠 있으므로 업스트림만 되돌리고, 그 뒤라면 이전 색을 재기동해 헬스 통과 후 업스트림을 되돌린다. 이미지가 로컬에 남아 있어 수십 초다.
- 스키마는 되돌아가지 않는다. 새 색이 뜨면서 `ddl-auto: update`가 먼저 실행되므로 업스트림을 되돌려도 추가된 컬럼은 남는다. NOT NULL 컬럼이 추가된 뒤 이전 이미지로 돌아가면 INSERT가 실패할 수 있다. 이때는 수동으로 복구한다. 먼저 그 컬럼만 NULL 허용이나 기본값으로 고치고, 데이터가 깨졌을 때만 배포 전 덤프로 전체 복원한다(덤프 이후 데이터 유실). 절차는 `deploy/README.md` 7절.
- 재시작 방식의 한계: 새 앱이 뜨는 15~30초는 502가 날 수 있고, 헬스가 끝내 실패하면 제한 시간(3분)과 복구 시간 동안 응답이 없다. 블루그린이 이 공백을 없앤다.

## 6. 고도화 사다리

위에서부터 순서대로 고른다. 조건이 없으면 올라가지 않는다.

| 단계 | 내용 | 넘어가는 조건 | 얻는 것 | 비용·시간 |
| --- | --- | --- | --- | --- |
| 1 | 단일 호스트 블루그린 | 재시작 파이프라인이 돌고 필수 8~11(부하 테스트·병목·캐싱·모니터링)에 착수한 뒤 여유가 있을 때. 스케줄 작업 단일 실행 규칙과 메모리 실측(앱 두 개가 들어갈 여유)이 선행 | 무중단 배포, 빠른 롤백. 도전 항목 "배포 고도화"의 시연 대상이지만 선택한 도전은 429라 우선순위가 뒤다 | 0원, 1일 |
| 2 | MySQL → RDS | 시연 데이터 보호가 필요하거나 slow query 분석이 필요할 때 | 자동 백업·스냅샷, 부하 테스트 격리, Performance Insights | 월 2~4만원, 반나절 |
| 3 | ALB + EC2 2대 | 2단계 이후 부하 테스트에서 앱 CPU는 포화인데 DB는 여유일 때 | 호스트 장애 내성, 드레이닝으로 진행 중 요청 보호, 앱 처리량 2배, ACM 인증서로 TLS 종단 | 월 5~6만원, 1일 |
| 4 | ECS Fargate | 이번 기수 범위 밖 | 자동 확장 기본 제공 | 월 8만원 이상, 1주 이상 |

1단계 블루그린은 배포 중단은 없애지만 두 컨테이너가 한 커널·한 도커 데몬 위에 있어 호스트가 죽으면 둘 다 죽는다. 3단계가 그 한계를 넘는다. 다만 DB가 같은 박스에 있으면 DB가 먼저 막혀 3단계의 처리량 이점이 보이지 않으므로 2단계가 선행 조건이다. 재고·결제는 DB 비관적 락, 토큰과 로그인 실패 횟수는 Redis라 두 대가 동시에 돌아도 코드 변경은 없다. 스케줄러의 단일 실행 보장은 블루그린의 겹침 창에서도 필요하므로 2대 단계가 아니라 첫 스케줄러부터 적용한다(5-3).

| Redis 데이터 유실 | 리프레시 토큰·로그인 실패 횟수가 Redis에 있다. AOF를 1초 단위로 기록해 재시작 시 최대 1초만 잃는다. `maxmemory` 200mb + `noeviction`으로 컨테이너 상한 전에 쓰기를 실패시킨다. 토큰을 조용히 지워 강제 로그아웃시키는 것보다 오류로 드러나는 편이 낫다 |
| 교체 순간 메모리 경합 | 앱 두 개 + MySQL + Redis의 메모리 상한 합이 약 3.75GiB라 4GiB 서버에서 블루그린이 안전하다고 보지 않는다. 앱 1개·모니터링의 실제 사용량을 잰 뒤 판단한다(8절). 상시 이중 실행은 하지 않는다 |
| 스케줄 작업 이중 실행 | 블루그린 겹침 창과 2대 구성 모두 해당. 단일 실행 보장 규칙을 컨벤션에 넣고 첫 스케줄러부터 적용한다. 규칙 전에는 블루그린을 도입하지 않는다 |
| 루트 볼륨 부족 | 기본 8GB는 이미지 여러 개·MySQL 데이터·로그에 부족하다. 30GB gp3로 만들고 로그 로테이션과 오래된 이미지 정리를 둔다 |

| 리버스 프록시 뒤 감사 IP 오염 | forwarded 헤더 설정, nginx만 신뢰 |
| HTTPS 전 리프레시 쿠키·웹훅 등록 불가 | 도메인·DNS는 첫날 시작, HTTPS는 10/30까지. 10/28은 HTTP 응답 점검만 |
| 운영 설정에 락 대기 시간 누락 | 운영 프로필의 Hikari 초기화 SQL과 MySQL 옵션으로 5초를 맞추고 배포 후 검증 항목(10-1)에 넣는다 |
| DB·Redis 포트 외부 노출 | 운영 compose는 포트 매핑 없음, 보안 그룹 80·443, 서버 접속은 SSM |

### 10-1. 배포 후 검증 체크리스트

업무 전달 5절을 기준으로 하고 락 대기 시간과 무중단 항목을 더했다. 전부 통과해야 배포·CI/CD 항목을 완료로 본다.

| 확인 | 기준 |
| --- | --- |
| 외부 접근 | 인터넷에서 `POST /api/service-area/check`가 200 |
| 인증 | 회원 가입·로그인 후 HTTPS에서 `Set-Cookie`가 동작하고 토큰 재발급 성공 |
| 자동 배포 | dev 병합 후 서버가 새 이미지로 교체되고 헬스 체크 통과. 화면 기록을 남긴다 |
| 재배포 안전 | 재시작해도 시드가 중복되지 않고 기동 성공 |
| 락 대기 시간 | 운영 DB 세션의 `innodb_lock_wait_timeout`이 5 |
| 비밀 정보 | 저장소·이미지·로그에 시크릿 없음 |
| 웹훅 | PortOne 콘솔에 고정 주소의 `/api/webhooks/...` 등록 가능. 컨트롤러는 아직 없고 정윤 구현에 걸린다 |
| 관리자 | 운영 관리자 계정으로 관리자 로그인 성공 |
| 헬스 포트 | 메인 포트의 `/actuator/health`는 401, 관리 포트는 도커 네트워크 내부에서 200. 호스트 밖에서 관리 포트 접근 불가 |
| 로그·디스크 | 컨테이너 로그 로테이션 동작, 루트 볼륨 여유 확인 |
| 실패 복구 | 일부러 깨진 이미지·nginx 설정을 배포해 이전 태그와 설정으로 돌아오는지, 복구 후 nginx 경유 응답이 200인지 확인 |
| 중복 배포 | 배포 중 수동 배포가 "다른 배포가 진행 중"으로 중단 |
| 백업 | nightly가 S3에 올라가고 `restore-check.sh`로 복원 성공 |
| HTTPS | http는 301, 인증서 발급자·만료일, 리프레시 쿠키 `Secure`, 토큰 재발급 200 |
| 무중단 (블루그린 도입 후) | 교체 중 반복 호출에서 실패 0. 이전 색이 관찰 시간 뒤 중지되었는지 확인 |

## 11. 미결 사항

팀이 확정해야 하는 것. 확정되면 해당 절을 갱신한다.

- 서버 구성 최종 확정, 인스턴스 크기, 비용 상한
- 도메인 확보 방법(구매처·명의). HTTPS 시점은 10/30 제안
- 프록시와 인증서 자동 발급 방식: nginx + certbot 또는 Caddy. 블루그린 절차는 같다. certbot 경험자가 없으면 Caddy 권장
- 운영 관리자 계정 생성 방법. 업무 전달 권장은 서버에서 SQL로 한 번 생성(로컬 시드의 해시를 쓰지 않는다). `data-admin-local.sql`은 운영에서 실행되지 않는다
- `data.sql` 시연 시드(지역 2·마트 2)가 운영에서도 실행되는 것이 의도인지. 네 문장 모두 `WHERE NOT EXISTS`라 반복 실행은 안전하다(10/27 확인). 운영 관리자는 이와 별도로 SQL로 만든다
- Grafana 접근 방식. SSM 포트 포워딩을 권장한다. 외부에 아무것도 열지 않고 인증이 IAM으로 끝난다(`deploy/README.md` 8절). 시연 때 화면을 보여 줄 노트북에서 포워딩한다
- 스케줄 작업 단일 실행 보장 규칙을 컨벤션에 넣을지. 정윤의 갱신 결제 재시도와 직결되므로 3차 범위 논의와 함께 다룬다
- 블루그린 도입 시점. 필수 8~11 착수 후 여유를 보고 판단한다
- 제출 시 기본 브랜치를 dev에서 main으로 바꿀지
- AWS 계정은 준희 개인 계정(무료 크레딧 100달러)으로 진행(10/26, 콘솔 작업 순서는 `deploy/aws-setup.md`). 남은 것은 관리자 그룹의 대리 1명 지정과 비용 정산용 영수증 보관(지원금은 사비 선지출 후 정산)
