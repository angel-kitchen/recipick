## 1차

### 일반 회원

- **회원가입·로그인** (담당: 채빈)
    - 이메일 기반 일반 회원 가입·로그인
    - 가입 시 이름·휴대전화 입력, 이메일·휴대전화 중복 불가
    - 서비스 이용약관·개인정보 수집 동의 필수, 동의 일시 저장
    - 로그인 3회 연속 실패 시 10분 잠금
    - 액세스 토큰 30분, 리프레시 토큰 14일(HttpOnly 쿠키, Redis 저장), 로그아웃 시 폐기
    - 관리자는 별도 로그인
    - 본인의 장바구니·주문·결제·포인트 정보만 접근
- **비밀번호 변경** (담당: 채빈)
    - 로그인한 회원이 현재 비밀번호를 확인한 뒤 새 비밀번호로 변경
    - 새 비밀번호는 가입 때와 같은 규칙(8~20자, 영문·숫자·특수문자 포함, 공백 불가)으로 검증
    - 현재 비밀번호가 맞지 않으면 변경하지 않음
    - 변경하면 모든 기기의 리프레시 토큰을 폐기해 토큰 재발급을 차단하고, 이미 발급된 액세스 토큰은 만료(30분)까지 사용할 수 있음
    - 비밀번호 변경은 회원 행을 잠근 뒤 처리하고, 비밀번호 해시와 리프레시 세션 버전을 같은 DB 트랜잭션에서 변경해 동시 로그인·재발급의 이전 버전 토큰도 무효화
    - 변경 전 Redis 세션 키 목록을 확보하고 DB 커밋 뒤 해당 키만 정리하며, 정리가 실패하거나 늦게 저장된 이전 세션이 남아도 버전 검사로 재발급을 거절. 남은 키는 TTL로 만료
    - 비밀번호 오류·입력 검증 실패 시 비밀번호와 세션 버전을 변경하거나 Redis 세션을 삭제하지 않음
- **회원 탈퇴** (탈퇴 기능: 채빈, 주문·장바구니 연동: 준희, 결제·포인트 연동: 정윤, 찜 연동: 보민)
    - 로그인한 회원이 비밀번호를 다시 입력(재인증)해 탈퇴
    - 결제 대기·취소 처리 중인 주문, 정상 진행 중인 배송 미완료 주문, 미해결 결제·환불, 활성 멤버십(해지 예약 포함)·결제 대기 유료 이용권·전환 대기 체험 이용권이 있으면 탈퇴할 수 없으며 먼저 처리하도록 안내
    - 탈퇴 정산 확인은 3차까지 포함해 상품 결제(결과 불명·SYSTEM 환불·수동 확인), 멤버십 결제(구독·갱신·재시도·결과 불명·이용료 환불), 포인트(잔액 사전 안내·미정산 내역·소멸 처리), 자동결제(탈퇴 후 신규 청구 방지·결제수단 처리)를 확인 범위로 함
    - 각 영역의 실제 상태 판정과 정리 방식은 담당자와 합의해 연결하며, 일부 영역만 연결되거나 확인에 실패하면 탈퇴를 허용하지 않음. 장바구니·찜의 정리 계약도 별도로 확정
    - 외부 결제수단 정리가 필요하면 회원 잠금 트랜잭션 밖에서 별도 절차로 처리하고, 이미 시작된 거래의 후속 처리에는 탈퇴 검사를 추가하지 않음
    - 취소·환불이 완료되어 종료된 주문과 배송 완료 주문은 탈퇴를 제한하지 않음. 다만 관련 미해결 결제·환불이 남아 있으면 탈퇴 불가
    - 탈퇴와 탈퇴 제한 상태를 새로 만드는 작업은 같은 회원 행을 잠가 경합을 제어하며, 탈퇴는 잠금 후 탈퇴 여부·진행 중 주문·미해결 결제·환불·활성 멤버십을 확인
    - 탈퇴하면 로그인·토큰 재발급을 차단하고 모든 기기의 리프레시 토큰을 폐기하며, 기존 액세스 토큰으로 요청해도 회원 인증 시 탈퇴 여부를 확인해 접근을 거절
    - 회원 정보의 이메일·이름·휴대전화는 고유한 대체값으로 바꾸고, 현재 배송지 선택과 이용 마트를 해제한 뒤 배송지를 삭제
    - 주문에 기록된 수령인·연락처·배송 주소와 결제·멤버십 기록은 회원 정보 정리와 별개로 보관하며, 항목별 보존 근거·기간과 만료 후 파기 방식은 별도로 확정
    - 장바구니·찜·포인트·결제수단 등 다른 도메인 데이터의 정리 범위는 해당 담당과 정하며, 탈퇴로 소멸되는 포인트 잔액은 탈퇴 전에 안내
    - 탈퇴 전 실제 사용 가능 포인트를 안내하고, `POST /api/members/me/withdraw`에 `password`와 사용자가 확인한 `acknowledgedPointBalance`(필수, 0 이상의 Long, 잔액이 없으면 0)를 전달
    - 회원 쪽은 확인 잔액을 기본값으로 대체하지 않고 `WithdrawalSettlementChecker.requireSettled(memberId, acknowledgedPointBalance)`에 그대로 전달. POINTS 구현이 회원 잠금 이후 포인트를 잠그고 지연 만료·미정산 확인·실제 잔액 비교·소멸을 수행하며 다른 Scope는 확인 잔액을 사용하지 않아도 됨
    - 잔액만 있으면 탈퇴를 막지 않고 안내한 잔액과 실제 잔액이 같을 때 소멸 처리. 다르면 POINT-002(409)로 거절해 최신 잔액을 재확인하며 예외 시 지연 만료를 포함한 해당 트랜잭션 변경을 모두 롤백. 재안내용 잔액 조회도 유효기간을 반영
    - 포인트의 PENDING 적립·RESERVED 사용은 POINT-003(409)으로 탈퇴 차단. 포인트 잔액과 적립 원장의 합계가 맞지 않는 상태는 회원이 해결할 수 없는 문제라 409가 아닌 내부 오류(COMMON-500)로 차단하고 운영이 확인. CONFIRMED 사용 자체와 완료 이력만으로 차단하지 않으며 잔액이 0이어도 미정산 검사를 수행
    - 포인트 탈퇴 소멸은 자연 만료와 구분해 FORFEITED·WITHDRAWAL_FORFEITED로 기록하고 소멸 금액이 없으면 소멸 이력을 생성하지 않음(포인트 구현: 정윤)
    - 실제로 활성화된 멤버십 이용 이력(관리자 지급 포함, activated_at이 있는 이력)이 있는 회원이 탈퇴하면 휴대전화의 키 해시(HMAC-SHA-256)를 TRIAL_BLOCK에 탈퇴 시각부터 1년간 보관
    - 같은 번호로 재가입하면 가입·유료 구독은 가능하지만 차단 기간 중에는 무료체험을 받을 수 없으며, 만료된 차단 기록은 체험 자격을 제한하지 않음
    - 차단 기간 중 이용 이력 없이 재가입·재탈퇴하면 기존 만료일을 유지하고, 새 계정에 멤버십 이용 이력이 있으면 새 탈퇴 시각부터 1년으로 연장
    - 해시 보관 항목·사유·기간은 탈퇴 화면과 개인정보처리방침에 표시하고, 만료된 기록은 내부 배치가 삭제
    - 회원 쪽 탈퇴 기반을 먼저 준비하되 주문·결제·포인트 등 필요한 연동과 경합 검증이 끝나기 전에는 탈퇴 기능을 제공하지 않음
- **이용 가능 지역 판정** (담당: 채빈)
    - 현재 배송지의 법정동이 서비스 지역이면 그 지역의 마트를 이용 마트로 지정하고, 아니면 이용 마트 없음
    - 서비스 범위는 법정동 단위(지역당 마트 1곳)로 제한하며, 반경(2km) 기준은 구현 완료 후 도입
    - 위치 이용 동의 후 현재 위치로 주소를 설정하거나, 위치 거부·실패 시 주소를 직접 입력
    - 가입 전에 위치 동의와 주소 설정(핀 확정, 상세 주소 입력)을 먼저 받고, 서비스 가능 여부를 비로그인으로 확인한 뒤 가입·로그인 이후 배송지로 저장(위치 우선 가입 흐름)
    - 서비스 가능 지역 확인은 로그인 없이 호출할 수 있으며, 법정동 코드를 받아 가능 여부와 마트 이름만 응답하고 아무것도 저장하지 않음
    - 범위 밖이면 이용 불가 안내
    - 현재 위치 자체는 저장하지 않고 위치 동의 일시와 확정한 배송지, 이용 마트만 저장
    - 위치 이용에 처음 동의한 시각을 기록하며, 이후 배송지를 추가해도 기존 동의 시각을 덮어쓰지 않음
- **배송지 관리** (담당: 채빈)
    - 회원당 배송지를 여러 개 저장·수정·삭제하고, 이 중 1개를 현재 배송지로 선택(최대 5개)
    - 배송지는 명칭(선택)·주소·상세 주소(필수)·법정동 코드를 저장(위·경도는 저장하지 않음)
    - 본인 배송지만 조회하며, 현재 배송지를 먼저 표시하고 나머지는 최근 등록순으로 표시
    - 저장된 배송지가 없으면 빈 목록으로 표시
    - 배송지별로 해당 주소를 선택했을 때 서비스 이용이 가능한지 표시. 현재 이용 마트와 다른 지역도 운영 중인 마트가 있으면 이용 가능으로 안내
    - 첫 배송지는 자동으로 현재 배송지가 되며, 현재 배송지는 삭제할 수 없음
    - 현재 배송지를 삭제하려면 다른 배송지를 먼저 선택해야 하며, 삭제 후 나머지 배송지·현재 배송지·이용 마트는 유지
    - 새 배송지를 현재 배송지로 선택하지 않고 추가하면 기존 현재 배송지와 이용 마트를 유지
    - 배송지는 보낸 항목만 수정하며, 주소·상세 주소·법정동 코드는 함께 변경하고 명칭은 삭제 가능
    - 현재 배송지를 수정하면 이용 마트를 다시 판정하고, 다른 배송지를 수정하면 현재 배송지와 이용 마트는 유지
    - 이미 현재 배송지인 주소를 다시 선택해도 마트 운영 상태를 다시 판정하여 이용 마트를 갱신
    - 현재 배송지가 이용 마트를 결정하고, 현재 배송지를 바꾸면 이용 마트를 다시 판정(마트가 바뀌면 장바구니의 이전 마트 상품은 삭제하기 전에는 주문할 수 없음)
    - 동시에 배송지를 등록해도 최대 5개를 넘지 않으며, 처음 등록하는 배송지의 자동 선택은 한 건만 적용
    - 배송지 등록에 실패하면 기존 배송지 선택·이용 마트·위치 동의 기록은 변경하지 않음
    - 핀 위치가 입력한 주소와 다르면 경고 후 핀 기준으로 주소를 갱신하고 상세 주소를 다시 입력
    - 서비스 지역 밖 주소도 저장할 수 있고, 현재 배송지로 선택하면 이용 마트 없이 이용 불가 안내
    - 배송지 목록을 조회하는 것만으로 현재 배송지나 이용 마트를 변경하지 않음
    - 수령인 이름·연락처는 배송지에 저장하지 않고 주문마다 입력(기본값은 회원 이름·연락처)
- **상품 검색·조회** (담당: 태헌)
    - 상품명 검색, 상세 조회
    - 카테고리·가격 범위로 필터링하고 가격순·최신순으로 정렬
    - 상품 카테고리 목록은 로그인 없이 조회(상품 필터 선택지)
    - 가격·판매 상태·재고는 이용 마트 기준으로 표시
    - 판매 단위·품절 여부 표시
- **레시피 검색·조회** (담당: 보민)
    - 레시피명·카테고리 검색
    - 기본 인분·재료·조리법·조리 시간 확인
    - 재료 필요량은 1인분 필요량 × 선택 인분으로 환산해 표시
    - 관련 유튜브 영상 표시
    - 자동 장보기 가능 여부 표시
- **레시피 찜** (담당: 보민)
    - 레시피 찜·찜 해제, 찜 목록 조회
    - 같은 레시피는 한 번만 찜 가능
    - 찜 중복은 `UNIQUE(member_id, recipe_id)`로 동시 요청까지 최종 방어
    - 찜 해제는 찜이 없어도 성공 처리(멱등)
- **직접 장바구니** (담당: 준희)
    - 이용 마트에서 판매하는 상품을 장바구니에 담습니다. 담으려는 상품의 마트(PRODUCT.mart_id)가 현재 이용 마트와 다르면 담지 않습니다.
    - 동일 상품을 다시 담으면 기존 수량에 합산합니다.
    - 수량 변경, 개별 삭제, 선택 항목 삭제, 주문할 상품 선택을 제공합니다. 이전 마트 상품은 수량 변경과 선택을 막고 삭제만 허용합니다.
    - 주문할 상품 선택은 서버에 저장하지 않고, 주문 미리보기·생성 요청에 선택한 장바구니 항목 ID로 전달합니다.
    - 선택 항목 삭제는 본인 항목만 지우며, 이미 없거나 다른 회원의 항목 ID가 섞여 있으면 건너뛰고 성공 처리합니다(일괄 삭제에 한한 예외이며, 개별 삭제는 CART-001(404)).
    - 수량 변경은 변경 후 최종 수량을 전달하는 방식으로 처리합니다.
    - 항목 수량은 1~99개이며, 합산 결과가 99개를 넘으면 담지 않습니다(CART-003).
    - 판매 중지·품절 상품은 새로 담거나 수량을 변경할 수 없습니다(CART-004). 이미 담긴 상품이 판매 중지·품절되면 장바구니에 남기고 상태를 표시하며, 삭제만 허용합니다.
    - 동일 회원·상품은 `CART_ITEM`에 한 행만 존재하도록 복합 UNIQUE로 제한합니다.
    - 장바구니 항목의 마트는 상품의 마트(PRODUCT.mart_id)로 판단하며 별도로 저장하지 않습니다. 상품의 마트가 회원의 이용 마트(MEMBER.mart_id)와 다르면 '이전 마트 상품'입니다.
    - 상품 가격·판매 상태·재고는 해당 상품 정보로 표시하고, 이전 마트 상품은 '이전 마트 상품'으로 표시합니다.
    - 장바구니에 이전 마트 상품이 있으면 주문하기를 막고 삭제를 안내합니다.
    - 이전 마트 상품이 있는 상태에서 새 상품을 담으면 일괄 삭제 여부를 확인하고, 확인하면 이전 마트 상품을 삭제한 뒤 담습니다(선택 항목 삭제 → 담기). 이전 마트 상품이 남아 있으면 담기는 CART-006으로 거절합니다. 삭제된 상품의 담기 이력은 유지합니다.
    - 장바구니에 담거나 수량을 변경할 때 재고를 차감하지 않습니다.
    - 본인 장바구니만 조회·변경·삭제할 수 있습니다.
- **장바구니 담기 이력** (담당: 준희)
    - 직접 담기 성공 시 `CART_ADD_HISTORY`에 회원·상품·이번 추가 수량·담기 시각을 기록합니다.
    - 직접 담기는 `source=DIRECT`, 자동 담기는 `source=AUTO_CART`로 구분합니다.
    - 자동 담기는 해당 `auto_cart_request_id`를 함께 기록합니다.
    - 자동 구성 담당이 확정한 상품을 장바구니에 합산하고 이력을 기록할 수 있도록 연동합니다.
    - 장바구니에서 상품을 삭제해도 그 상품의 담기 이력은 지우지 않고 그대로 남깁니다.
    - 담기 이력은 담기에 성공했을 때만 생성합니다. 수량을 바꾸거나 상품을 장바구니에서 삭제할 때는 이력을 새로 만들지 않습니다.
- **주문 화면·배송지 확인** (담당: 준희)
    - 장바구니에서 선택한 상품만 주문 대상으로 구성합니다.
    - 회원의 이름·연락처(원문)·현재 배송지를 불러와 수령인·배송지 기본값으로 표시합니다. 수령인이 따로 있으면 이름·연락처를 수정할 수 있습니다.
    - 저장된 배송지 목록에서 다른 주소를 고르거나, 지도에서 핀으로 새 주소를 입력할 수 있습니다. 핀 위치가 주소와 다르면 경고 후 핀 기준으로 주소를 갱신하고 상세 주소를 다시 입력받습니다.
    - 주문서에서 고르거나 입력한 주소는 이번 주문에만 적용하며, 회원의 현재 배송지와 이용 마트는 바꾸지 않습니다.
    - 주문서는 배송 가능 상태(현재 이용 마트의 지역 / 다른 마트 지역 / 서비스 지역 밖)를 응답 필드로 알려 주며 오류로 처리하지 않습니다. 가능하지 않으면 결제하기를 비활성화하고, 다른 마트 지역이면 [현재 배송지 변경]으로 연결합니다. 현재 배송지를 바꾸면 이용 마트가 바뀌며, 장바구니의 이전 마트 상품은 주문할 수 없습니다.
    - 배송 가능 여부는 배송지 법정동이 이용 마트의 법정동(MART.region_id)과 같은지로 판정합니다.
    - 주문 생성 시 배송지 법정동 코드를 받으며, 서버에서 형식과 서비스 지역을 검증합니다(위도·경도는 받지 않음).
    - 주문 생성 요청에서 서버가 같은 기준으로 최종 검증하고, 맞지 않으면 주문을 만들지 않고 거절합니다(형식 오류 ORDER-006, 서비스 지역 밖 ORDER-008). 검증은 재고 차감 전에 합니다.
    - 이번 주문에서 입력·수정한 배송 정보는 회원의 배송지 목록에 자동 반영하지 않습니다.
- **주문 상품·금액 검증** (담당: 준희)
    - 선택한 장바구니 항목의 존재 여부·소유권·수량과 상품의 마트가 현재 이용 마트와 같은지를 확인합니다.
    - 현재 상품 가격·판매 상태·재고를 서버에서 다시 검증합니다.
    - 미리보기는 구매 불가 상품을 제외하고 제외 상품·사유를 안내합니다. 주문 생성은 구매 불가 상품이 하나라도 있으면 제외하지 않고 거절해, 사용자가 확인하지 않은 금액으로 결제가 만들어지지 않게 합니다(삭제 PRODUCT-001, 판매 중 아님 PRODUCT-003, 재고 부족 STOCK-001; 이전 마트 상품은 아래 CART-006 기준 적용).
    - 이전 마트 상품이 포함되면 제외하지 않고 주문을 막습니다. 미리보기는 주문 불가 상태로 응답하고, 주문 생성은 재고 차감 전에 거절합니다(CART-006).
    - 구매 가능한 상품이 하나도 없으면 주문·결제를 생성하지 않습니다.
    - 최종 주문 상품과 결제금액을 결제 전에 안내합니다.
    - 상품금액은 서버가 현재 단가와 주문 수량으로 계산하며 클라이언트가 전달한 금액을 그대로 신뢰하지 않습니다.
- **주문 생성 멱등성** (담당: 준희)
    - 주문 생성 요청은 `Idempotency-Key` 헤더가 필수입니다. 클라이언트는 주문하기를 누를 때마다 새 UUID를 만들고, 재시도할 때만 같은 키를 다시 보냅니다.
    - 키는 소문자로 정규화해 저장합니다(최대 64자). ORDERS에 `idempotency_key`와 `request_hash`를 저장하고, UNIQUE(member_id, idempotency_key)로 중복 생성을 막습니다.
    - `request_hash`는 선택한 장바구니 항목 ID(오름차순), 수령인·연락처·주소·상세 주소·배송지 법정동, 사용 포인트로 서버가 계산합니다(SHA-256, hex 64자). 금액은 서버가 계산하므로 해시에 넣지 않습니다.
    - 같은 키에 같은 요청이면 기존 주문의 현재 상태를 반환하고, 재고 차감·결제 생성을 다시 하지 않습니다.
    - 같은 키에 요청 내용이 다르면 COMMON-011(409)로 거절합니다.
    - 주문 생성이 실패해 롤백되면 키도 저장되지 않으므로, 같은 키로 재시도하면 처음부터 다시 검증합니다.
    - 같은 키로 동시에 요청이 들어와도 주문은 1건만 생성됩니다.
    - ORDERS.idempotency_key는 주문 생성 전용이며 취소 요청 키는 저장하지 않습니다. 취소·만료된 주문을 다시 주문할 때는 새 키를 사용합니다.
- **주문 생성** (담당: 준희)
    - 주문과 결제를 같은 DB 트랜잭션에서 생성합니다.
    - 첫 DB 작업으로 회원 행을 잠급니다. 회원 탈퇴와 동시에 와도 한쪽만 성공하고, 탈퇴한 회원은 회원 조회(MEMBER-001)에서 거절됩니다.
    - 주문은 `PENDING_PAYMENT`, 결제는 `IN_PROGRESS`, 주문의 마트 처리 상태는 `NONE`으로 시작합니다.
    - 주문 생성 시 실제 재고를 주문 수량만큼 즉시 차감합니다. 별도 예약 재고는 사용하지 않습니다.
    - 재고 차감은 상품·재고 담당의 원자적 차감 메서드를 호출합니다.
    - 상품 하나라도 차감에 실패하면 주문·결제·재고 변경을 모두 롤백합니다.
    - 사용자 표시용 고유 주문번호 `order_number`를 생성합니다. 내부 연동에는 `ORDERS.id`를 사용합니다.
    - 주문 당시 처리 마트와 최종 확정한 수령인·연락처·주소·상세 주소·배송지 법정동을 `ORDERS`에 저장합니다. 이후 회원의 배송지가 변경돼도 주문에 저장된 배송 정보는 변경하지 않습니다. 〔확인 필요〕
    - 상품명·단가·판매 단위·수량·줄 금액을 `ORDER_ITEM`에 주문 당시 값으로 저장합니다.
    - 회원 정보나 상품 정보가 변경돼도 이미 생성된 주문 정보는 바뀌지 않습니다.
- **결제 대기 주문 제한** (담당: 준희)
    - 회원당 결제 대기 주문은 1건만 허용합니다.
    - 같은 `Idempotency-Key`의 재시도는 결제 대기 제한보다 먼저 확인해, 오류 대신 기존 주문을 반환합니다.
    - 기존 `PENDING_PAYMENT` 주문이 있으면 새 주문 생성을 거절합니다.
    - 기존 결제를 계속하거나 기존 대기 주문을 명시적으로 취소하도록 안내합니다.
    - 새 주문 요청 때문에 기존 주문을 자동 종료하지 않습니다.
    - 기존 주문의 결제·취소·명확한 실패·5분 만료 처리가 끝나면 새 주문을 생성할 수 있습니다.
    - 종료된 주문·결제를 재사용하지 않습니다.
    - `pending_member_id`에 회원 ID를 저장하고 UNIQUE 제약으로 동시 생성 요청을 최종 방어합니다.
    - 주문이 결제 대기 상태를 벗어나면 `pending_member_id`를 해제합니다.
- **결제 결과에 따른 주문 처리** (담당: 준희)
    - 결제 도메인이 승인·실패·만료 결과를 확정하고 주문 메서드를 호출합니다.
    - 결제 성공 시 주문을 `PAID`, 주문의 마트 처리 상태를 `RECEIVED`로 변경합니다.
    - 결제 성공 시 `pending_member_id`를 해제하고 상태 이력을 저장합니다. 재고는 추가로 변경하지 않습니다.
    - 결제 전 취소·명확한 실패·5분 만료·금액 불일치 시 주문을 `CANCELED`로 종료합니다.
    - 종료 시 최초 차감 재고 복구, pending 해제, 사유·이력 저장을 같은 트랜잭션에서 처리합니다.
    - 회원 취소(결제 전·후)도 결제 Facade의 호출을 받아 주문 상태·재고·이력을 처리합니다. 결제 전은 `CANCELED`, 결제 후는 `CANCEL_REQUESTED` → `REFUNDED`로 전이합니다.
    - 같은 결과가 반복 전달돼도 재고와 상태를 중복 변경하지 않습니다.
    - 만료 후 늦은 승인은 결제 도메인이 시스템 환불만 처리합니다. 주문은 `CANCELED`로 유지하고 재고는 다시 변경하지 않습니다.
    - 외부 취소(PortOne 콘솔 등 시스템 밖의 전액 취소)가 확인되면 결제 Facade의 호출을 받아 `PAID` 주문을 `CANCEL_REQUESTED` 없이 바로 `REFUNDED`로 종료합니다. 마트 처리 상태는 바꾸지 않으며, 재고는 마트 처리 상태가 `RECEIVED`·`PREPARING`일 때만 복구하고 배송이 시작된 주문은 복구하지 않습니다. 이미 `CANCEL_REQUESTED`인 주문은 기존 환불 완료 처리로 끝냅니다.
- **주문 조회·상태 이력** (담당: 준희)
    - 본인 주문 목록과 상세를 조회합니다.
    - 주문번호·주문 상태·마트 처리 상태·상품·금액·배송지·취소 사유를 표시합니다.
    - 결제 대기 만료 시각과 결제·취소 가능 여부는 결제 담당의 조회 정보와 연동합니다.
    - 주문 및 마트 처리 상태 변경 시 이전·이후 상태, 처리 주체, 사유, 변경 시각을 기록합니다.
    - 회원 탈퇴 판단용으로 진행 중 주문 여부를 제공합니다. `CANCELED`, `REFUNDED`, 배송 완료(`PAID`+`DELIVERED`)를 뺀 주문이 하나라도 있으면 진행 중입니다.
    - 관리자 변경은 `changed_by_admin_id`도 기록합니다.
    - 취소 사유는 `cancel_reason_code`, `cancel_reason_detail`로 저장합니다.
    - 코드는 `MEMBER_CANCELED`, `PAYMENT_TIMEOUT`, `PAYMENT_FAILED`, `AMOUNT_MISMATCH`, `MART_REJECTED`, `EXTERNAL_CANCELED`를 사용합니다.
    - 중복 알림으로 최초 취소 사유를 덮어쓰지 않습니다.
- **상품 결제** (담당: 정윤)
    - PortOne 카드 결제
    - 주문 생성 트랜잭션에서 `ORDER`와 `PAYMENT(IN_PROGRESS)`를 함께 생성
    - 결제 유효시간은 주문·결제 생성 시점부터 **5분**
    - 서버가 PortOne 결제 상태·주문 식별자·결제 금액을 다시 조회해 검증한 뒤에만 결제 확정
    - PG 실제 결제 완료시각(`paidAt`)이 결제 만료시각(`expiresAt`) 이내인지 검증
    - 결제 성공 시 `PAYMENT = PAID` , `ORDER = PAID` , 마트 처리 상태를 `RECEIVED(접수중)` 로 같은 트랜잭션에서 반영
    - 웹훅도 동일한 검증·상태 전이 로직으로 처리
    - 결제 확정 API·웹훅·만료 큐가 동시에 들어와도 결제 성공은 한 번만 반영
- **결제 실패·만료** (담당: 정윤)
    - PG가 결제 실패를 명확히 확정하면 `PAYMENT = FAILED(PG_FAILED)` 처리
    - 5분 내 결제가 완료되지 않으면 지연 큐에서 `PAYMENT = FAILED(EXPIRED)` 처리
    - 실패·만료 시 주문을 `CANCELED`로 종료하고 주문 생성 시 차감한 재고 복구
    - 기존 실패 주문·결제를 다시 사용하지 않으며, 다시 결제하려면 **새 주문·새 결제 생성**
    - 기존 결제대기 주문이 있으면 새 주문 생성 불가
    - PG 응답이 불명확하면 실패로 단정하지 않고 기존 결제 상태를 조회해 결과 확인
    - 내부적으로 이미 종료된 결제에서 뒤늦은 PG 성공이 확인되면 주문을 되살리지 않고 시스템 자동 취소
- **결제 전 취소** (담당: 정윤)
    - `PAYMENT = IN_PROGRESS` 상태에서 회원이 결제를 취소할 수 있음
    - 결제 전·후 취소는 동일한 취소 API를 사용하며 `Idempotency-Key` 를 필수로 전달
    - 결제 전 취소는 PG 취소 호출과 `REFUND` 생성을 하지 않음
    - `PAYMENT = FAILED(CANCELED_BEFORE_PAY)` 처리
    - 주문 `CANCELED`, `pending_member_id` 해제
    - 주문 생성 시 차감한 재고 복구
    - 같은 종료 처리가 중복 실행되지 않도록 결제·주문 상태를 기준으로 멱등 처리
- **결제 후 취소** (담당: 정윤)
    - 결제 완료 후 마트 상태가 `RECEIVED(접수중)` 일 때만 회원 직접 전체 취소 가능
    - `PREPARING(배송준비중)` 부터는 회원 직접 취소·환불 불가
    - 부분 취소·부분 환불 없음
    - 취소 시작 시 `PAYMENT/ORDER = CANCEL_REQUESTED`, `REFUND = REQUESTED`를 먼저 저장
    - PortOne 취소 호출은 DB 트랜잭션 밖에서 수행
    - PG 취소 성공 시 `PAYMENT = CANCELED`, `ORDER = REFUNDED`, `REFUND = COMPLETED` 처리 및 재고 복구
    - PG 취소 결과가 불명확하면 `CANCEL_REQUESTED / REQUESTED` 상태를 유지하고 웹훅·재조회로 결과 확인
    - 회원 취소가 명확히 실패하면 결제·주문을 `PAID`, 마트 상태를 `RECEIVED`로 복구
- **환불 처리** (담당: 정윤)
    - PortOne 취소 성공을 확인한 뒤에만 환불 완료 처리
    - 환불 요청 주체 `MEMBER / ADMIN / SYSTEM / EXTERNAL` 기록
    - `Idempotency-Key`로 같은 PG 취소가 중복 실행되지 않도록 처리
    - 동일 환불이 진행 중이면 새 환불 요청을 중복 생성하지 않음
    - 만료·금액 불일치 후 PG 결제 성공이 확인되면 `SYSTEM` 환불 실행
    - 만료 시 이미 주문 종료·재고 복구가 완료됐으므로 늦은 승인 자동환불에서는 주문·재고를 다시 변경하지 않음
- **결제 내역 조회** (담당: 정윤)
    - 본인 주문별 결제 금액·결제 방식·결제 일시·결제 상태·실패 사유·취소 여부 조회
    - 결제 도메인은 주문 엔티티를 직접 조회하지 않고 주문 서비스의 소유 확인·조회 계약을 사용
    - 실패·취소된 결제도 이력으로 유지
    - 취소가 발생한 결제는 완료 환불 금액과 최근 환불 상태 표시
- **마이페이지** (담당: 채빈 화면 구성, 각 도메인 조회 제공)
    - 내 정보(이메일·이름·휴대전화(원문)·이용 마트·현재 배송지·멤버십 유형·만료일·무료체험 가능 여부)
    - 비밀번호 변경과 회원 탈퇴를 제공
    - 지정된 마트가 운영 중지여도 마트 정보는 표시하고, 현재 배송지의 이용 가능 여부는 별도로 안내
    - 현재 배송지 지역의 운영 마트와 지정 마트가 같을 때만 이용 가능으로 표시하며, 불일치하거나 지정 마트가 없으면 이용 불가 안내
    - 정보 조회만으로 저장된 배송지나 이용 마트를 변경하지 않음
    - 멤버십 혜택은 activated_at이 있고 활성화·시작 시각 이상이며 유예 종료 시각(없으면 이용 종료 시각) 미만이고 즉시 종료되지 않았을 때 제공. 결제 대기·전환 대기는 혜택이 없음
    - GET /api/memberships/me는 활성 이용권이 없으면 pending에 결제 대기(PAYMENT_PENDING)·전환 대기(CONVERSION_PENDING)를 반환. pending은 이용권 ID·유형·발급 경로·상태·시작/종료·자동갱신·해지 예약 시각을 포함하며 없으면 null
    - 멤버십은 이용 기간과 즉시 종료 여부를 기준으로 표시하며, 자동갱신을 해지 예약해도 남은 이용 기간에는 혜택 유지
    - 무료체험 가능 여부는 관리자 지급을 포함해 실제로 활성화된 멤버십 이용 이력이 없고, 휴대전화가 탈퇴 전 이력으로 차단 기간 중이 아닌 회원에게만 가능으로 표시
    - 주문 내역, 결제 내역, 취소·환불 내역을 한 화면에서 제공
- **멤버십 기능 제한** (담당: 채빈)
    - 자동 장바구니·AI 요청 시 멤버십 안내
    - 상품 검색·직접 장바구니·주문·결제는 이용 가능

### 유료 회원

> 유료 회원은 일반 회원 기능을 모두 포함하며, 체험 회원도 대상입니다. 자동 구성은 모두 **이용 마트의 상품·판매 단위·가격·재고**를 기준으로 계산합니다.
>
- **멤버십 활성 검증** (담당: 채빈)
    - 요청 시 서버에서 활성 여부와 유형(일반·체험·유료) 판정
    - 내 멤버십에서 현재 이용권의 유형·발급 경로·이용 기간·자동갱신·해지 예약과 무료체험 가능 여부를 확인
    - 시작 시각부터 종료 직전까지 혜택을 적용하며, 해지 예약은 남은 기간의 혜택을 유지하고 즉시 종료된 이용권은 제외
    - 주문 생성 시 getTypeAt(memberId, 기준시각)으로 혜택 유형을 판정해 적립률을 주문에 저장. 활성화·이용 기간·실제 종료 시각을 고려하되 과거 유예 이력 전체를 재현하는 조회 계약은 제공하지 않음
    - 해지 예약·환불 종료는 grace_end_at을 비우므로 이후 getTypeAt으로 과거 유예 구간을 다시 조회한 결과는 달라질 수 있음. 기존 주문의 적립률은 저장된 스냅샷을 사용하며 현재 멤버십으로 재계산하지 않음
- **메뉴·인분 선택** (담당: 보민)
    - 한 번의 요청에서 여러 메뉴와 메뉴별 인분 선택
    - 메뉴는 1~5개, 인분은 메뉴별 1~10, 같은 레시피 중복 선택 불가
- **수량 계산** (담당: 보민)
    - 1인분 필요량 × 선택 인분으로 환산
    - 동일 재료 합산
    - 이용 마트에서 그 재료에 해당하는 상품을 찾아 선택
    - 상품 선택 기준: 구매 가능 상품 우선 → 총 구매금액 낮은 순 → 예상 잔량 적은 순 → 가격·용량이 같으면 상품명 가나다순
    - 선택한 상품의 판매 단위로 한 번만 올림
    - 수량은 `DECIMAL`·`BigDecimal`로 계산하고 올림은 `CEILING` 사용(0.5개 등 소수 오차 방지)
    - 재고 비교는 장바구니에 이미 담긴 같은 상품 수량 + 이번 추가 수량 기준
    - 예상 잔량(총 구매량 − 총 필요량)은 저장하지 않고 미리보기 시점에 계산
- **필수·선택 재료** (담당: 보민)
    - 필수 재료는 기본 포함
    - 고명 등 선택 재료는 기본 제외 후 사용자가 선택
- **자동 구성 미리보기** (담당: 보민)
    - 담기 전에 이용 마트 기준으로 표시
    - 재료별 필요량·연결 상품·구매 수량·예상 잔량·가격·구매 불가 사유
    - 전체 합계 가격 표시
    - 미리보기 요청은 `PREVIEWED` 상태로 저장하고 요청 번호 반환
    - 미리보기 다시 조회 시 `PREVIEWED`는 현재 가격·재고로 재계산, `CONFIRMED`는 확정 시점 결과 반환
    - 재료별 연결 상품 후보를 함께 보여 주고 사용자가 원하는 상품(브랜드)을 고를 수 있음
    - 확정하지 않은 `PREVIEWED` 요청은 생성 7일 후 배치로 정리
    - 정리할 요청에 연결된 AI 요청 이력은 지우지 않고, 같은 트랜잭션에서 이력의 요청 연결을 먼저 비운 뒤 요청을 삭제
- **구매 불가 사유** (담당: 보민)
    - 이용 마트 미판매(그 재료의 상품 없음)
    - 판매 중지
    - 품절
    - 재고 부족(장바구니에 담긴 수량 + 이번 구매 수량이 재고보다 많음)
- **자동 구성 확정** (담당: 보민)
    - 확정 시 서버가 이용 마트 기준으로 가격·재고·수량 재계산
    - 구매 가능한 상품만 장바구니에 추가
    - 추가한 상품은 담기 이력에 자동 담기 경로와 요청 번호로 기록
    - 한 요청은 한 번만 확정 — `PREVIEWED → CONFIRMED` 조건부 갱신으로 연타·재전송 시 중복 합산 방지
    - 미리보기 이후 이용 마트가 바뀌었으면 확정 거부 후 다시 미리보기 안내
    - 구매 가능한 상품이 하나도 없으면 장바구니에 담지 않고 안내
    - 미리보기와 확정 시점 합계가 다르면 가격 변경 안내
- **자동 구성 기록** (담당: 보민)
    - 요청별로 계산 기준 마트와 함께 저장
    - 선택 메뉴·인분·선택 재료, 재료별 계산 결과(필요량·선택 상품·구매 수량·가격), 구매 불가 재료
    - 실제 추가 상품은 담기 이력으로 확인

### 관리자

- **관리자 로그인** (담당: 채빈)
    - 관리자 전용 로그인
    - 관리자 계정은 초기 데이터로만 생성(가입 불가)
    - 관리자 역할과 소속 마트 구분
    - 비활성 계정은 로그인 거부
    - 관리자 API는 관리자 토큰만 허용
    - 로그인 3회 연속 실패 시 10분 잠금(회원과 동일)
- **관리자 감사 로그** (공통 감사 기능: 채빈, 도메인별 기록 연동: 채빈·태헌·보민·준희·정윤)
    - 관리자가 수행한 등록·수정·삭제·상태 변경과 개인정보가 보이는 조회를 ADMIN_AUDIT_LOG에 기록
    - 기록 항목은 관리자·작업 종류·대상 종류와 ID·관련 마트·변경 전후 값(details)·접속 IP·기록 시각이며, 목록 조회의 대상 ID와 details는 비워 둘 수 있음
    - 내부 DB 변경은 작업과 감사 기록을 같은 쓰기 가능한 트랜잭션으로 처리하고 기록 실패 시 작업도 롤백
    - 개인정보가 보이는 조회도 조회와 감사 기록을 같은 쓰기 가능한 트랜잭션으로 처리하며, 기록에 실패하면 조회 결과를 반환하지 않음
    - 외부 결제사 호출이 필요한 관리자 작업은 요청 접수 상태와 감사 로그를 먼저 함께 저장·커밋한 뒤 외부 호출을 수행하고 최종 결과는 별도 트랜잭션으로 반영
    - 각 도메인은 global의 공통 기록 인터페이스 AdminAuditRecorder를 호출하고 구현은 회원 도메인이 제공하며, 원래 작업을 조립하는 위치에서 중복 없이 기록
    - details에는 필요한 변경 전후 값만 기록하고 기존 이력 표와 연결하지 않으며, 개인정보·비밀번호·비밀번호 해시·토큰·빌링키·비밀키는 넣지 않음
    - 조회 응답 본문·이메일·이름 검색어와 거절 사유 등 자유 입력 원문은 감사 로그에 복사하지 않음
    - 실제 변경이나 새 실행이 없는 쓰기 재요청은 기록하지 않고 개인정보 조회는 요청마다 기록
    - 환불 재처리는 새 실행을 시작하면 기록하되 같은 멱등 키의 재전송과 구분하며, 최종 기록 시점과 전달 항목은 결제 담당과 확정
    - 시스템 결제 만료·자동 취소 등 자동 처리는 별도의 관리자 행위로 기록하지 않음
    - 접속 IP는 서버가 직접 확인한 주소를 기본으로 하며, 배포 후에는 신뢰하도록 설정한 프록시가 정리해 전달한 헤더만 사용
    - 감사 로그는 추가만 가능하며 관리자 수정·삭제 API를 두지 않고, 생성 시각부터 1년이 지난 기록은 내부 배치가 삭제
    - 기록 대상
        - 회원·멤버십: 멤버십 지급, 회원 목록·회원별 멤버십 이력 조회
        - 마트·상품: 마트 등록·수정·운영 상태 변경, 카테고리 등록·수정·삭제, 상품 등록·수정·삭제·가격·판매 상태·재료 연결 변경, 관리자 수동 재고 조정
        - 레시피: 레시피 등록·수정·상태 변경, 레시피 재료 변경, 재료 등록·수정, 관리자의 자동 장보기 지정·해제
        - 주문: 주문 수락·거절·배송 상태 변경
        - 결제: 관리자 환불 재처리, 관리자 결제·포인트 조회
        - AI: 관리자 AI 요청 이력 조회
    - 슈퍼 관리자만 기간·관리자·작업 종류·대상 종류로 목록을 검색하고 상세를 조회
    - 감사 로그 조회는 GET /api/admin/audit-logs 및 /api/admin/audit-logs/{id}로 제공. 기간은 한국 시간 from 포함·to 미포함이며 생성 시각·ID 내림차순으로 페이지 조회(기본 20개, 최대 100개)
    - 회원 목록 조회는 검색어·응답 본문 없이 매 요청 기록하고, 멤버십 지급은 새 이용권 ID와 유형·발급 경로·시작·종료 시각·자동갱신의 변경 전후 값만 기록
    - 만료 감사 로그는 매일 04:20 KST에 생성 시각 기준 1년이 지난 건을 최대 1,000건씩 별도 트랜잭션으로 조건부 삭제. 중복 실행에 안전하므로 별도 분산 락·추가 환경변수는 사용하지 않음
- **마트 관리** (담당: 태헌)
    - 지역(법정동)별 마트 1곳, 시연은 서로 떨어진 두 동네의 마트 2곳
    - 마트 등록 요청에 지역 ID를 직접 입력하고, 없는 지역 ID는 거절(지역은 초기 데이터로 고정, 지역 조회 API는 두지 않음)
    - 마트 위도·경도·서비스 반경 관리(서비스 반경은 구현 완료 후 도입, 지금은 판정에 쓰지 않음)
    - 운영 상태(운영·중지) 관리. 마트 관리자는 본인 마트의 운영 상태만 변경할 수 있고, 위도·경도·서비스 반경은 슈퍼 관리자만 수정
- **상품 관리** (담당: 태헌)
    - 판매 단위는 g·ml·개 정량
    - 상품에 브랜드 등록
    - 판매 중지
    - 주문 이력이 있어도 상품을 삭제할 수 있음(소프트 삭제). 지난 주문은 주문 당시 값(`ORDER_ITEM`)으로 유지되고, 진행 중인 주문은 그대로 이어지며, 삭제된 상품은 회원 조회에서 제외되고 담기·주문이 막힘
    - 마트 관리자는 자기 마트 상품을 등록·수정·삭제하고 가격·재고·판매 상태를 변경할 수 있으며, 결제·환불 처리는 슈퍼 관리자와 시스템만 함
    - 각 마트의 상품은 무조건 해당 마트에 등록되어 있어야 하고, 다른 마트로 변경 불가
    - 같은 마트에서 삭제되지 않은 상품은 이름과 브랜드가 모두 같으면(브랜드 없음끼리도 이름이 같으면) 중복 등록·수정 불가
    - 카테고리는 슈퍼 관리자만 등록·이름 수정·삭제(소프트 삭제)하고, 삭제되지 않은 상품이 연결된 카테고리는 삭제할 수 없음. 삭제된 카테고리와 같은 이름으로 등록하면 기존 카테고리를 복구
- **재료·상품 연결** (담당: 태헌)
    - 상품 등록·수정 시 해당하는 재료 지정(재료 하나에 여러 상품 가능, 재료가 아닌 상품은 미지정). 수정 시 재료 연결 해제 가능
    - 재료 단위와 상품 판매 단위의 호환 여부 검증
- **재고 관리** (담당: 태헌)
    - 마트별 상품 재고 조회·증가·감소
    - 마트별 상품 등록·수정
    - 조정 시 조정 전 수량·증감 수량·사유·처리 관리자 기록
    - 상품별 재고 조정 이력을 최신순으로 조회
- **레시피 관리** (담당: 보민)
    - 레시피 100개(한식 70·양식 30) 등록·조회·수정·비활성화
    - 한식·양식, 요리 유형 설정
    - 기본 인분·조리 시간·난이도·맵기·조리 순서·유튜브 영상 관리
- **레시피 재료 관리** (담당: 보민)
    - 재료별 1인분 필요량과 g·ml·개 단위 등록
    - 필수·선택 재료 구분
    - 한 레시피에 같은 재료 중복 등록 불가 — `UNIQUE(recipe_id, ingredient_id)`
    - 단위는 재료(`INGREDIENT.unit`)에만 두고 레시피 재료는 재료 단위를 따름
    - 1인분 필요량은 0 초과, 소수 허용(`DECIMAL(10,2)`)
- **자동 장보기 지정** (담당: 보민)
    - 모든 필수 재료의 1인분 필요량·단위가 등록되고, 그 재료에 연결된 상품이 있는 레시피만 지정
    - 레시피 재료 변경으로 조건이 깨지면 자동 장보기 지정을 자동 해제
    - 관리자 레시피 목록에 "연결 상품 없는 필수 재료 수" 표시
- **멤버십 관리** (담당: 채빈)
    - 관리자 이용권 지급은 1차 시연·테스트용이며, 3차 구독 결제·자동갱신 구현 완료 후 테스트용으로 유지하거나 제거할 예정
    - 슈퍼 관리자만 테스트 회원에게 지급 시점부터 30일 이용권을 지급하며, 결제·자동갱신 없이 지급 관리자와 생성 시각을 기록
    - 체험·유료·해지 예약을 포함한 활성 멤버십이나 결제 대기·전환 대기 이용권이 있으면 지급하지 않으며, 동시 요청에도 한 건만 지급
    - 만료·즉시 종료 이력만 있는 회원은 다시 지급할 수 있고, 지급 이력은 무료체험 가능 여부에 반영
    - 슈퍼 관리자만 회원 목록에서 이메일·이름 부분 검색, 현재 활성 이용권 기준 멤버십 유형·발급 경로와 활성 여부 필터, 페이지·정렬을 사용해 회원별 유형·기간·체험 사용 이력을 조회하며 탈퇴한 회원은 제외
    - 회원 검색 조건은 함께 적용(AND)하며, 멤버십 유형·발급 경로는 현재 활성 이용권 기준으로 함께 검사. 비활성 필터와 유형·발급 경로를 동시에 지정하면 일치하는 회원 없음
    - 체험 사용 이력은 실제 체험 이용권 이력으로 판단하며, 관리자 지급 이력만 있는 경우와 구분
- **주문 조회·수락** (담당: 준희)
    - 마트 관리자는 본인 마트 주문만 조회·처리합니다.
    - 슈퍼 관리자는 권한 범위 내에서 전체 마트 주문을 조회·처리합니다.
    - 주문 목록·상세·수령인·배송지·상태 변경 이력을 제공합니다.
    - 주문이 `PAID`이고 마트 처리 상태가 `RECEIVED`일 때만 수락할 수 있습니다.
    - 수락하면 주문의 마트 처리 상태를 `PREPARING`으로 변경합니다.
    - 취소 진행 중이거나 종료된 주문은 수락할 수 없습니다.
    - 처리 관리자와 상태 변경 이력을 기록합니다.
    - 회원 취소와 동시에 들어오면 주문 행을 잠근 뒤 상태를 확인해 한쪽만 성공합니다.
- **마트 거절·환불 연동** (담당: 준희)
    - 주문이 `PAID`이고 마트 처리 상태가 `RECEIVED`일 때만 거절할 수 있습니다.
    - 결제 Facade를 통해 주문을 `CANCEL_REQUESTED`, 마트 처리 상태를 `REJECTED`로 변경합니다.
    - 거절 사유를 저장하며 접수 시 재고를 복구하지 않습니다.
    - PG 취소 성공 시 주문을 `REFUNDED`로 종료하고 재고를 복구합니다.
    - PG 취소 결과가 불명확하면 취소 진행·거절 상태를 유지합니다.
    - PG 취소가 명확히 실패해도 정상 접수 상태로 되돌리지 않습니다.
    - 관리자 환불 재처리는 결제 담당 기능과 연동하고, 최종 성공 시 주문 종료·재고 복구를 한 번만 반영합니다.
- **결제 조회** (담당: 정윤)
    - `SUPER_ADMIN` 전용
    - 회원·기간·결제 상태 조건으로 결제 목록 조회
    - 주문별 결제 금액·결제 상태·PortOne 결제 번호 확인
    - 결제 상세에서 모든 취소·환불 실행 이력 확인
    - 실패한 환불 실행 기록도 삭제하지 않고 운영 이력으로 유지

## 2차

### 일반 회원

- **주문 진행 상태 확인** (담당: 준희)
    - 접수중·배송 준비·배송중·배송완료·마트 거절 상태를 주문 상세에 표시합니다.
    - 주문 상태와 마트 처리 상태를 구분해 표시합니다.
    - 배송완료를 구매확정으로 처리합니다.
- **배송비** (담당: 준희)
    - 일반 회원은 포인트 사용 전 상품금액 40,000원 이상 무료배송, 미만이면 3,000원입니다.
    - 상품 제외 시 남은 상품금액으로 배송비를 다시 계산합니다.
    - 배송비는 서버에서 계산하고 주문 생성 시 확정해 저장합니다.
- **포인트 사용·적립 연동** (담당: 준희)
    - 결제·포인트 담당과 연동해 사용 포인트를 검증하고 주문에 `used_point`를 저장합니다.
    - 포인트는 상품금액까지만 사용할 수 있으며 배송비에는 사용할 수 없습니다.
    - 최종 외부 결제금액은 상품금액 + 배송비 − 사용 포인트로 계산합니다.
    - 포인트 사용 예약·확정·복원은 포인트 담당 기능과 연동합니다.
    - 외부 결제금액이 0원인 주문도 내부 결제 완료·취소 흐름을 일관되게 처리합니다.
    - 주문 생성 시 적용 적립률을 `point_rate`에 저장합니다.
    - 주문 생성 시 적립 예정 건 생성, 배송완료 시 적립 확정 처리를 포인트 담당과 연동합니다.
    - 배송완료 요청이 반복돼도 포인트가 중복 적립되지 않도록 처리합니다.
- **포인트 사용** (담당: 정윤)
    - 1포인트 = 1원
    - 1포인트부터 상품금액 전액까지 사용, 배송비에는 사용 불가
    - 만료일이 빠른 적립부터 사용
    - 한 주문에서 여러 적립 건의 포인트를 나누어 사용 가능
    - 주문 생성 시 `POINT_USAGE = RESERVED`
    - 예약 시 `MEMBER_POINT.balance`와 해당 `POINT_EARNING.remaining_amount` 차감
    - 결제 성공 시 `CONFIRMED`
    - 결제 실패·만료·취소 시 `RESTORED`
    - 주문 생성 당시 유효했던 예약 포인트는 5분 결제 대기 중 만료일이 지나도 해당 주문에서는 인정
    - 외부 결제금액이 0원이면 `PAYMENT`는 `payment_method = POINTS_ONLY`, `amount = 0`으로 생성하고 PG는 호출하지 않는다.
- **포인트 적립** (담당: 정윤)
    - 일반·체험 회원 적립률 0.5%
    - 적립액 = `(상품금액 − 사용 포인트) × 0.5%`
    - 배송비 제외, 소수점 이하 버림
    - 주문 생성 시 `POINT_EARNING = PENDING` 으로 적립 예정 건을 생성
    - **배송완료 시** `PENDING -> COMPLETED`로 적립 확정
    - 적립 확정 시 `MEMBER_POINT.balance` 증가
    - 주문당 적립 건 1개
    - 유효기간은 적립 확정일로부터 1년
    - `expires_on` 당일까지 사용 가능
- **취소 시 포인트 복원** (담당: 정윤)
    - 주문에서 사용한 포인트는 사용 당시 차감했던 원래 `POINT_EARNING` 적립 건으로 복원
    - 원래 `expires_on`은 연장하지 않음
    - 복원 시 이미 만료일이 지났다면 `RESTORED` 이력을 남긴 뒤 즉시 `EXPIRED` 처리
    - 이미 만료된 포인트는 `MEMBER_POINT.balance` 에 다시 추가하지 않음
    - 배송완료 전 주문이 종료되면 적립 예정 `POINT_EARNING` 은 `CANCELED`
    - 배송완료가 포인트 적립 확정이자 최종 거래 완료 시점이므로 **적립 완료 후 환불에 따른 포인트 회수(clawback)는 없음**
    - 포인트 전액결제 주문 취소 시 PG 호출 없이 내부적으로 사용 포인트 복원
- **포인트 조회** (담당: 정윤)
    - 회원별 현재 사용 가능 총 포인트 조회
    - 가장 가까운 만료 포인트와 만료일 조회
    - 주문별 적립 예정·적립 완료·사용 예약·사용 확정·복원·만료 이력 조회
    - 적립 건별 최초 적립량·남은 포인트·만료일 조회
    - 포인트 보유 이력이 없는 회원은 404가 아니라 잔액 0·빈 목록 반환

### 유료 회원

- **AI 자연어 장보기** (담당: 보민)
    - 문장(1~200자)에서 메뉴·인분을 추출해 자동 구성 미리보기 제공
    - 추출한 메뉴가 모두 자동 장보기 가능 레시피로 확인되면 바로 미리보기 생성
    - 일부 메뉴만 확인되거나 모호하면 미리보기를 만들지 않고, 확인된 메뉴와 후보를 보여 주고 사용자가 고르게 함
    - 결과는 오류가 아니라 상태로 응답: `PREVIEWED`(미리보기 생성), `NEEDS_SELECTION`(사용자 선택 필요), `NO_MATCH`(맞는 레시피 없음), `FALLBACK`(AI 장애로 레시피명 검색 결과 제공)
- **AI 조건 추천** (담당: 보민)
    - 문장(1~200자)에서 조건(종류·요리 구분·최대 조리 시간·최대 맵기·제외 재료)을 분석해 등록 레시피 100개 안에서 최대 5개 추천
    - 처리 순서: ① AI가 문장을 위 조건 항목으로 정리 → ② 서버가 조건 값을 검증하고 레시피 검색 조건으로 적용해 후보를 거름 → ③ AI가 그 후보 안에서만 고르고 추천 이유를 작성
    - AI 장애 시 대체(`FALLBACK`): ①에서 실패하면 결과 없이 조건으로 직접 검색하도록 안내, ③에서 실패하면 서버가 거른 후보 중 최대 5개를 추천 이유 없이 제공
    - 결과는 상태로 응답: `RECOMMENDED`, `NO_MATCH`(분석한 조건이 없음, 조건을 만족하는 레시피 없음, AI가 후보 중 맞는 레시피가 없다고 판단), `FALLBACK`
    - 분석한 조건이 하나도 없으면(검증에서 버려진 값 포함) 전체 레시피를 후보로 삼지 않고 ③을 호출하지 않은 채 `NO_MATCH`
    - ③에서 AI가 빈 목록을 주면 `NO_MATCH`, 후보 밖 ID만 주면 응답 오류로 보고 `FALLBACK`
- **AI 처리 기준** (담당: 보민)
    - AI는 메뉴·인분·조건만 분석
    - 재료량·수량·가격·재고·멤버십은 서버가 검증
    - AI가 고른 레시피는 서버가 존재·활성 여부를 다시 확인하고, 후보 밖 레시피는 결과에서 제외
        - AI 자연어 장보기: 자동 장보기 가능 여부와 메뉴 1~5개·인분 1~10·중복 금지도 확인
        - AI 조건 추천: 최대 5개까지만 남김
    - AI 호출은 DB 트랜잭션 밖에서 함
    - 외부 AI 서비스가 응답 지연·장애·요청 한도 초과로 실패하면 500 오류(`COMMON-008`·`COMMON-009`)가 아니라 성공 응답의 `FALLBACK` 상태로 응답하고 직접 레시피를 고르도록 안내(AI 자연어 장보기는 레시피명 검색 결과 제공, AI 조건 추천은 위 대체 기준)
    - 회원별 AI 요청은 1분에 5회로 제한하고, 초과하면 AI를 호출하지 않고 403 오류(`AI-001`)로 거절
    - 성공·실패 모두 요청 이력 저장(요청 유형, 원문, 분석 결과, 연결 레시피, 결과 상태, 모델, 입력·출력·캐시 토큰, 응답 시간, 실패 사유)
        - 성공 여부는 AI 응답을 받아 결과에 썼는지로 판단: `PREVIEWED`·`NEEDS_SELECTION`·`NO_MATCH`·`RECOMMENDED`는 성공, `FALLBACK`은 실패(실패 사유 기록)
        - AI 조건 추천은 두 번 호출한 토큰·응답 시간을 합산
        - 분석 결과·토큰은 AI 응답을 받은 만큼만 기록하고, 응답을 하나도 받지 못하면 비움
        - 연결 레시피는 응답에 담은 레시피만 기록하고, 없으면 비움
        - 회원별 한도 초과로 거절한 요청은 AI를 호출하지 않으므로 이력을 남기지 않음
- **배송비 혜택** (담당: 준희)

    - 미만 시 3,000원

- **마트 주문 거절·자동 환불** (담당: 준희·정윤)
    - 마트 관리자는 본인 마트의 주문이 `PAID` 이고 마트 처리 상태가 `RECEIVED` 일 때만 주문을 거절할 수 있습니다.

    - 거절 접수 시점에는 재고와 사용 포인트를 복구하지 않습니다.

    - PG 취소가 명확히 실패하면 `PAYMENT = PAID`로 복귀하지만 `ORDER = CANCEL_REQUESTED`, 마트 처리 상태 `REJECTED`는 유지하고 관리자 재처리 대상으로 관리합니다.

    - 체험: 첫 자동 결제 중단, 남은 체험 기간 유지 후 일반 전환
    - 유료: 다음 자동 결제 중단, 결제한 기간 유지 후 만료 시 일반 전환
    - `POST /api/memberships/{membershipId}/cancel-reservation`로 본인의 활성 체험·구독·체험 전환 이용권과 결제 대기 유료·전환 대기 체험 이용권에 해지 예약하며 요청 본문은 없음
    - 회원 행을 첫 DB 작업으로 잠그고 탈퇴 여부를 검사한 뒤 지정 이용권을 소유 회원 조건으로 잠가 확인·변경. 타인·없는 이용권과 해지 예약 대상이 아닌 미시작·만료·즉시 종료 이용권은 `MEMBERSHIP-006`, 관리자 지급 이용권은 `MEMBERSHIP-007`로 거절
    - `autoRenew=false`와 최초 `cancelReservedAt`을 반영하고 grace_end_at은 null로 비우며 이용 기간·유형·발급 경로·월 갱신 기준일·결제 동의·즉시 종료 시각은 유지. 활성 기간 안의 재요청·동시 요청은 최초 예약 시각을 유지하며 성공
    - 성공 시 이용권 ID·변경 후 상태·자동갱신 여부·이용 종료 시각·해지 예약 시각을 응답. 정상 이용기간에는 CANCEL_RESERVED로 남은 혜택을 유지하고, 결제 대기는 PAYMENT_PENDING 유지, 전환 대기·유예 중 해지 예약은 EXPIRED로 혜택 종료. 유예 중 예약 화면에는 즉시 종료됨을 안내
    - 이용권 ID를 지정하므로 종료된 이전 이용권의 재요청이 이후 생성된 이용권을 해지하지 않음. 포트원·환불·빌링키 변경과 관리자 감사 기록은 수행하지 않음
    - 자동청구 대상에서는 예약된 이용권을 제외해야 하며 실제 청구·재시도 경합은 결제 담당과 별도 연동·검증(회원 API만으로 이미 시작된 외부 결제의 취소를 보장하지 않음)
    - 청구 접수와 해지 예약은 회원 → 이용권 순서로 같은 행을 잠가 순서를 정함. 청구는 잠금 후 자동갱신·해지 예약·동의 상태를 재확인하고, 이용권·이용기간별 회차와 회차·시도 번호별 시도 및 해당 시도의 고정 PG 결제 식별자(portonePaymentId)를 접수와 함께 저장·커밋한 뒤 PG 호출. 회차와 시도를 구분해 갱신의 명확한 실패 재시도를 금지하지 않음
    - 해지 예약보다 청구 접수가 먼저 확정됐다면 해당 시도는 진행. 성공하면 이번 결제 이용기간을 적용하되 해지 예약과 autoRenew=false를 유지해 다음 갱신부터 중단
    - 해지 예약보다 먼저 접수된 청구가 명확히 실패하면 추가 청구 재시도 없이 해당 시도를 종료하되 이미 남은 이용기간은 유지. 접수 커밋 후 중단돼도 기존 회차·시도와 고정 PG 결제 식별자를 복구 기준으로 사용하고, 중단만을 이유로 새 시도·새 식별자를 만들지 않음
    - 기존 시도가 READY이면 결제 도메인의 선점 절차로 같은 시도를 이어서 실행하며, 발송 여부나 결과가 불명확한 DISPATCHING·UNKNOWN·MANUAL_REVIEW는 기존 PG 결제 식별자로 결과를 재조회. 재조회 전 새 결제 호출·새 시도·새 식별자 생성으로 복구하지 않으며, PG 재호출 허용 여부는 결제 도메인의 확정 상태 전이·멱등 정책과 검증에 따름
- **즉시 해지** (담당: 채빈, 환불 처리: 정윤)
    - 유료 멤버십 회원은 이용기간 중 즉시 해지 및 환불을 요청할 수 있습니다.
    - 즉시 해지 요청 API는 멤버십 도메인이 소유합니다.
    - 요청 시 `Idempotency-Key`를 필수로 받고 결제 도메인의 이용료 환불 서비스를 호출합니다.
    - 환불 처리 중에는 멤버십을 `ACTIVE`로 유지합니다.
    - 환불이 `COMPLETED`된 경우에만 멤버십을 즉시 종료합니다.
    - 환불이 명확히 실패하면 멤버십을 `ACTIVE`로 유지합니다.
    - 환불 결과가 불명확하면 `REQUESTED` 상태와 멤버십 `ACTIVE`를 유지하고 웹훅·재조회로 결과를 확인합니다.
    - 결과 불명 건이 나중에 환불 성공으로 확인되면 `즉시 해지 환불 완료 반영`을 통해 멤버십을 종료합니다.
    - 같은 `Idempotency-Key`로 다시 요청하면 새 환불을 만들지 않고 기존 결과를 반환합니다.
    - 같은 이용권에 결과 확인 중인 `REQUESTED` 환불이 있으면 다른 키의 새 요청은 거절합니다.
    - 명확한 실패가 `FAILED`로 확정된 뒤에는 새 `Idempotency-Key`로 다시 요청할 수 있습니다.
- **결제 결과에 따른 전환** (담당: 채빈)
    - 결제 연동은 MembershipBillingService의 공개 계약과 DTO(BillingMembershipData, MembershipConsent, MembershipBillingTarget, MembershipBillingResult)로 제공하며 엔티티를 다른 도메인에 반환하지 않음
    - 변경 계약은 쓰기 가능한 바깥 트랜잭션(MANDATORY) 안에서만 실행. 호출자는 회원 → 빌링키 → 이용권 PK → 결제 회차 → 시도 → 환불 순서로 필요한 행을 잠그고 소유권·현재 회차·반영 여부를 검사하며 과거·확정 회차 결과는 반영 계약에 전달하지 않음
    - 이용권 잠금·전체 ID·차단 여부·커서 기반 전환/갱신 대상 조회, 결제 대기 구독/전환 생성, 첫 결제 성공/실패·갱신 성공/중단·카드 없는 전환 종료·환불 완료 반영을 제공. 계약 내부에서 현재 시각이나 외부 PG 호출을 만들지 않음
    - 이미 반영됨·상태 충돌은 결과 enum으로 반환하며 예외는 호출자에게 전파해 결제 결과 기록과 함께 롤백. 결제 대기 유료의 임시 이용 기간·기준일은 첫 결제 성공 시 PG 결제 시각으로 교체
    - 갱신은 종료 시각을 줄이지 않고 해지 예약·자동갱신 중단을 되돌리지 않음. 전환 접수 시 체험 행의 autoRenew만 false로 바꾸고 별도 유료 행을 만들어 체험 이력을 보존
    - 미해결 결제로 구독·지급·체험을 거절할 오류는 MEMBERSHIP-009(409), 진행 중 결제로 즉시 해지를 보류할 오류는 MEMBERSHIP-010(409). 결제 도메인 실제 호출 연결은 후속 작업
    - 갱신 최종 실패는 자동갱신을 중단하되 유예 종료 시각까지 혜택을 유지하고 이후 일반 전환. 체험 종료 시 카드가 없으면 결제 없이 일반 전환
    - 즉시 해지 환불이 `COMPLETED`된 경우에만 유료 멤버십 종료
    - 같은 요청 안에서 환불 완료가 확인되면 멤버십 도메인이 즉시 종료
    - 결과 불명 후 나중에 성공이 확인되면 결제 도메인의 `즉시 해지 환불 완료 반영` 계약을 통해 종료
    - 환불액이 0원인 경우에도 `COMPLETED` 처리 후 멤버십 종료
- **자동 결제 동의** (담당: 정윤 안내, 채빈 저장)
    - 체험·유료 구독 시작 전 결제 금액·첫 결제일·월 갱신 주기·자동갱신 해지·즉시 해지 방법 안내
    - 동의 금액·동의 문구 버전·동의 일시를 멤버십에 저장
    - 자동 청구 시 멤버십 도메인에 자동청구 대상·동의 여부 확인
- **카드 등록** (담당: 정윤)
    - 카드번호·CVC는 저장하지 않고 PortOne 빌링키만 관리
    - 회원당 `ACTIVE` BillingKey 최대 1개
    - 새 카드 등록 시 기존 ACTIVE 키는 `REPLACED`, 새 키는 `ACTIVE`
    - 동일 ACTIVE BillingKey 재등록은 새 행을 만들지 않고 기존 결과 반환
    - 자동결제 customer 개인정보(name/email/phone)는 BillingKey에 중복 저장하지 않음
    - 실제 자동결제 시 MemberService의 결제용 회원정보 조회를 통해 원문을 받아 Customer DTO 구성
- **멤버십 결제** (담당: 정윤)
    - 월 이용료 3,900원
    - 체험 종료 또는 일반회원의 유료 구독 시작 시 첫 자동 결제
    - 이후 첫 유료 결제일을 기준으로 매월 같은 날짜에 자동청구
    - 해당 날짜가 없는 달은 말일 청구
    - 청구 대상은 멤버십 서비스에서 조회
    - 동일 이용권의 같은 이용기간 회차 결제는 한 번만 생성
    - `UNIQUE(membership_id, period_start_date)`로 회차 중복 생성 방지
    - PortOne 자동결제 성공 후 멤버십 도메인에 결과 반영
- **첫 유료 결제 실패** (담당: 정윤)
    - 체험 종료 후 첫 결제가 명확히 실패하면 `FAILED` 결과 전달
    - 멤버십 도메인은 유료 전환하지 않고 일반 회원으로 전환
    - PG 결과가 불명확하면 즉시 실패로 단정하지 않고 `UNKNOWN` 상태로 조회해 결과 확정
- **갱신 결제 실패** (담당: 정윤)
    - 기존 유료 멤버십 갱신 실패 시 3일 유예
    - 갱신일에 1회, 이후 하루 1회씩 2회 추가해 총 3회 시도
    - 재시도 대기 상태는 `RETRY_WAITING`
    - 결과 불명(`UNKNOWN`)은 새 결제 시도보다 기존 PG 결과 조회를 우선
    - 최종 실패 시 멤버십 도메인에 최종 실패 결과 전달
- **갱신 시 카드 없음** (담당: 정윤)
    - 갱신일에 활성 BillingKey가 없으면 `PAYMENT_METHOD_REQUIRED` 3일간 카드 등록 대기
    - 유예기간 내 카드 등록 시 한 번 청구
    - 기간 종료까지 카드가 없으면 최종 실패 결과 전달
- **이용료 환불** (담당: 정윤)
    - 유료 멤버십 즉시 해지 요청의 내부 처리로 실행
    - 회원이 멤버십 결제 환불 API를 직접 호출하지 않음
    - 멤버십은 환불 결과가 확정될 때까지 `ACTIVE` 유지
    - 환불액 = `max(0, 결제금액 - 이용일수 요금 - 위약금)`
    - 이용일수 요금 = `floor(결제금액 x 이용일수 / 해당 결제기간 실제 일수)`
    - 위약금 = 결제금액의 20%
    - 이용일수는 이용 시작일과 환불 요청일을 모두 포함
    - 이용일수·이용일수 요금·위약금·환불금액을 `MEMBERSHIP_REFUND`에 저장
    - 환불 요청 시 `MEMBERSHIP_REFUND = REQUESTED`를 먼저 저장·커밋한 뒤 PortOne 환불 호출
    - 환불 성공 시 `COMPLETED` 처리 후 멤버십 종료
    - 명확한 실패 시 `FAILED`, 멤버십 `ACTIVE` 유지, 새 요청 가능
    - 결과 불명 시 `REQUESTED` 유지, 멤버십 `ACTIVE` 유지 후 웹훅·재조회로 확인
    - 결과 불명 건이 나중에 성공으로 확인되면 `COMPLETED` 처리 후 멤버십의 즉시 해지 환불 완료 반영 호출
    - 환불액이 0원이면 PG 호출 없이 `COMPLETED` 처리 후 멤버십 종료
    - 동일 요청은 `Idempotency-Key`로 중복 환불 방지
- **적립률 차등** (담당: 정윤)
    - 유료 멤버십 1%, 체험 0.5%(일반 회원 0.5%)
    - 적립률은 **주문 생성 시점의 회원 상태**로 결정해 주문에 스냅샷
    - 주문 조립 단계에서 동일 기준시각을 정해 MembershipService.getTypeAt(memberId, 기준시각)으로 혜택 유형을 조회하고 포인트 정책에 전달. 결제 전 이용권은 제외하고 갱신 유예 중에는 혜택을 유지하는 기준을 3차 이용권 생명주기에 반영
    - getTypeAt은 activated_at이 없는 결제 대기를 제외하고 활성화 시각부터 유예 종료 시각까지 혜택 유형을 반환. 결제 결과 반영은 MembershipBillingService 계약으로 제공하며 결제 도메인 호출 및 주문 포인트 정책의 실제 연결은 후속 구현
    - 실제 포인트 지급은 배송완료 시점
    - 이후 회원 멤버십 상태가 바뀌어도 해당 주문의 적립률은 변경하지 않음

### 관리자

- **멤버십 결제 조회** (담당: 정윤)
    - `SUPER_ADMIN` 전용
    - 첫 결제·월 정기결제·실패·재시도·결제수단 필요·결과 불명 상태 조회
    - 청구일·이용기간·시도 횟수·다음 재시도 시각·실패 사유 확인
    - 결제별 전체 `MEMBERSHIP_REFUND` 실행 이력 확인
    - 환불 금액·이용일수·이용요금·위약금·처리상태·실패사유 확인
- **회원별 멤버십 이력 조회** (담당: 채빈)
    - `SUPER_ADMIN` 전용
    - 회원의 모든 이용권(체험·유료 전환·구독·관리자 지급)과 상태(이용 중·해지 예약·만료·즉시 해지·결제 대기·전환 대기) 조회
    - `GET /api/admin/members/{memberId}/memberships`로 조회하며 `page`는 0부터(기본 0), `size`는 1~100(기본 20), 등록 시각·ID 내림차순으로 정렬
    - 이용권 ID·유형·발급 경로·상태·이용 기간·자동갱신·월 갱신 기준일·해지 예약/즉시 종료 시각·지급 관리자 ID·등록 시각을 응답하고 개인정보·결제수단 정보는 포함하지 않음
    - 상태는 조회 시점의 판정 규칙을 사용. 미활성 유료는 PAYMENT_PENDING, 체험 종료 후 전환 대기는 CONVERSION_PENDING으로 표시하고 활성화된 이용권의 이용 시작 전 이력은 status를 null로 응답
    - 이력이 없는 회원과 범위를 벗어난 페이지는 정상 빈 목록이며 없는 회원·탈퇴 회원은 기존 회원 조회와 같이 `MEMBER-001`로 거절
    - 매 조회를 `MEMBER_MEMBERSHIP_HISTORY_VIEW`로 기록(대상은 회원 ID, 관련 마트는 현재 회원 마트, details는 비움)하며 조회와 감사 기록은 같은 쓰기 트랜잭션으로 처리하고 기록 실패 시 결과를 반환하지 않음
